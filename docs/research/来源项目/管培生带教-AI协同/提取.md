## 1. 业务内容（最重要）

### 1.1 目标与定位

- **培养目标**：管培生能独立理解业务问题、形成判断并推进小项目（`源/管培生带教-AI协同-业务共识-v1.0.md:9`）。
- **机器人只做四件事**：知识支持、提醒、完成确认、事实汇总。它不是培养达成的证据：不能用机器人回复数、入库量、选择题正确率来证明能力提升（`同上:11`、`:154`）。
- **明确不做**：全过程业务方案指导、替管培生做业务决策、专业成果评阅（`同上:13`）。实施规格补充的范围外事项还有：项目自动回写、细任务分解、复杂督办、绩效排名、简答或重型考核、催答、临时投放未审题、知识自动过审、私聊监控、机器人入会（`源/实施规格-v1.0.md:405-407`，即「## 12. 范围外」）。
- **项目推进是核心板块**，明确结果是三条：周报准确、进度随时可查、重点事项可提醒（`源/管培生带教-AI协同-业务共识-v1.0.md:13`）。
- **主职能**：2026-09-09 常浩明确「机械邪龙兽长期聚焦管培生带教，其他职能为附带；营销战役、战略协同等计划由常浩迁回原生多维表格智能体」（`源/CONTEXT.md:77`）。但 09-20 又把营销物料协同并入了同一个 Worker（见 3.7）。

### 1.3 六类流程（业务共识 v1.0 原定）及其后的修订

下面每个流程先写原定规则，再写后来的修订和现行口径。

#### A. 答疑：每次问答都要审核、可纠正、能沉淀

- **原定链路**：提问 → 检索依据并回答 → 送带教群审核 → 通过或纠正 → 确认归档及知识整理 → 入库留档（`源/管培生带教-AI协同-业务共识-v1.0.md:50-61`）。
- **纠正规则**（Grill Q8①）：
  - 常浩给出完整的最终答案时，机器人直接落实，不再让他重复审核同一内容。
  - 常浩只给出错因或原则时，机器人改稿后再审。
  - 答案被否决时，先在原入口提示「相关结论已被否决、正在纠正」；最终纠正回到原入口，并写明替代的是哪条旧答复（`同上:55-56`；`源/Grill-下一轮问题清单-Q8-Q12.md:13-38`）。
- **待审期间能不能用**（Q3①）：有明确有效的已审依据、且不涉及新判断的部分，可以日常执行；推断、依据不足或有冲突的部分，要等常浩确认（`源/管培生带教-AI协同-业务共识-v1.0.md:54`）。
- **待审不会自动通过**：没收到确认就一直保持待审，不因时间经过而通过（`同上:134`）。
- **现行口径**（多次纠正后的最终状态）：
  1. **入口只有两个**：一是唯一答疑群（测试群）里白名单成员**实际 @机械邪龙兽**的提问，二是飞书文档评论里白名单成员实际 @机械邪龙兽的提问。**私聊于 09-16 退出审核链**，变回普通机器人对话：不记录、不审核、不入库（`源/CONTEXT.md:3-7`；`源/阶段状态.md:3-11`）。
  2. **只记录、不重答**：机器人按既有设置正常回答一次；本项目只捕获「真实问题 + 实际送达的完整答案 + 送达位置」，不为了记账再生成或重发一遍（`源/阶段状态.md:316-319`；`源/docs/adr/0001-first-chain-isolation.md:7`）。
  3. **评论入口有两种问法**：
     - 白名单成员选中原文后只评论「@机械邪龙兽 回答问题」：引用的原文就是正式问题。
     - 评论里本身就写了具体问题：用评论文字作问题，引用只作上下文（`源/阶段状态.md:49-51`）。
  4. **审核卡（09-13 起）**：
     - 群内的普通长度答案，就地把机器人的回答消息更新成一张审核卡，卡里有完整问题、完整回答、「提问人 / 知识类型 / 价值评级」三个色块、修改建议框，以及「通过入库」「退回修改」两个按钮，退回必须填意见。
     - 评论入口在原评论处回答，审核卡另发到测试群。
     - 答案超过单张卡安全体积时，发紧凑审核卡，保留全文（`源/阶段状态.md:59-61`）。
  5. **一步入库（09-13 起）**：点「通过入库」后直接追加到固定 Q&A 合集并更新原卡，不再出第二张「确认本方案入库」卡（`源/config/more-entries.json:992-1013`，`requires_collection_write_confirmation=false`）。之前的两步做法见 `源/使用说明.md:11-33`（历史）。
  6. **审核要绑死版本**：同一案件、答案版本、内容哈希、知识类型、价值评级、发布方案要对得上。旧卡、版本不对、内容不对、重复回调都不能推进（`源/config/more-entries.json:992-1013`）。
  7. **入库的格式**：问题用自动编号的一级标题；答案放进带 ✅ 的高亮块，完整段落作为子块，保留加粗、编号、分段（`源/CONTEXT.md:21`）。
  8. **合集里只放问题和最终答案**：不放审核人、时间、编号、日志、JSON；过程信息留在后台（`源/docs/adr/0002-reader-facing-qa-collection.md:20-27`）。常浩原话：「我只要问题和回答，不要……过程信息」（`同上:16`）。
  9. **问答归档 ≠ 正式知识发布**，`knowledge_published=false`（`源/CONTEXT.md:60`）。
  10. **长定稿**：卡片输入框上限 1000 字。超过时回复审核卡，首行写「@机械邪龙兽 定稿」，下一行起粘贴全文（`源/使用说明.md:35-45`）。
- **答案元数据**由规则自动判定，不额外调用模型：
  - 知识类型（7 类）：方法论与工具、工作流程、业务知识、规范与标准、项目与任务信息、案例复盘、系统操作。
  - 价值评级（4 档）：S 核心必会、A 高价值、B 实用参考、C 情境记录。
  - 判定规则：涉及红线、合规、保密的定为 S；当前项目信息定为 C；方法论、流程、规范类定为 A；其余定为 B（`源/trainee/answer_metadata.py:5-20`、`:69` 起；已复制）。

#### B. 知识入库：只做「归位」

#### D. 日报 / 周报

- **原定（Q18①）**：按约定时间和范围**自动发布事实汇总，不逐次审批**；保留来源，区分已通过、待审、待补充；写进报告的待审内容不会因此变成已审；发现错误时可要求纠正（`源/管培生带教-AI协同-业务共识-v1.0.md:89-95`；`源/Grill-发布与反馈-Q18-Q19.md:15-36`）。
- **内容分工**：日报侧重问答、入库、任务等单点内容；周报再加上项目表里的进度（`同上:91`）。
- **统计口径**：按稳定对象 ID 和时间范围去重，同一问答改三次不算三个问题；项目表读取失败时必须写明「缺失」，不能当成零（`源/实施规格-v1.0.md:255-265`，§6.4）。
- **项目周报卡（v2.1 口径，09-15）**：
  - 要回答 6 个问题：总体发生了什么、哪些结果推进了、各项目在哪、已发生和可能发生的风险、下周关键动作、哪些需要常浩介入（`源/work/project-weekly-report-card-design-20260915/project-weekly-report-card-spec-v2.md:5-27`）。
  - **时间口径**：本周成果按上一自然周（周一 00:00 至周日 23:59）、且「是否完成=true」并有「实际完成时间」的任务统计；当前进度和风险按生成时点；下周重点取下一自然周的排期（`同上:28-39`）。
  - **全局标签**：红「存在风险」> 橙「需要关注」> 蓝「信息待补」> 绿「推进正常」（`同上:42-60`）。
  - **4 个指标**：推进中项目数、总体完成度（已完成数 ÷ 总数，不对各项目百分比求平均）、本周完成数、关注信号数（逾期加 3 日内到期）（`同上:77-93`）。
  - **风险分两层**：已发生风险（任务已逾期、里程碑已过）和预警信号（3 日内到期、7 日内的里程碑、同一负责人或同一天集中交付、下周无排期）。定性风险没有字段依据，不由 AI 猜（`同上:94-128`）。
  - **其他模块**：分项目进展、下周管理重点（最多 3 项，常浩需要参与的标「需你介入」）、数据说明（最多 2 条，读取失败必须写明）（`同上:129-188`）。
  - **AI 能做 / 不能做**：可以归纳成果、指出临期和集中交付、给出轻量核验建议；不能把完成文档说成业务效果，不能评价能力或意愿，不能把缺填写说成延期，不能改优先级、负责人或状态（`同上:200-218`）。
  - **容量**：单卡最多 4 个项目；每个项目成果最多 2 条、下周重点最多 3 条；风险最多 3 条（`同上:219-227`）。
- **日报卡样式（「AI管培项目日报」，09-15，由常浩那边发出）**：每个项目显示进度条、完成数/总数、进行中、今日完成、逾期、本周事项（@负责人）、明日到期、里程碑倒计时、更新状态（如「已连续 N 天无新完成任务」）、项目文档链接，加一个风险提示区，比如「已填实际完成时间但未勾选完成」（`源/work/daily-card-json-recovery-20260916/AI管培项目日报-09-15-最终确认版.json`，含 open_id，未复制）。09-20 机器人仿照它实现了日报渲染器 `render_project_daily_report_cards`（`源/trainee/cards.py:985`）。**日报是否真的自动或手动发过，待核。**

### 1.4 状态规则：几个维度各自独立，不合并成一个「完成」

出处：`源/实施规格-v1.0.md:185-196`（§5.2）、`:110`。

| 维度 | 状态流转 |
|---|---|
| 答案 | 草稿 → 待审 → 通过；或 待审 → 否决待纠正 → 新版本待审；导师给完整定稿时直接形成已确认版 |
| 归档 / 知识方案 | 待生成 → 待审（有冲突则待解决）→ 位置和内容都通过后才可写入 |
| 写入 / 送达 | 待执行 → 执行中 → 已成功；失败另记；结果不明时记待核验，不凭猜测重放 |
| 题目 | 草稿 → 待审 → 可投放；变更后停投、重审 |
| 作答 | 未答 / 已答；未答不是答错 |
| 周期实例 | 未声明 → 已声明待审 → 通过；被退回 → 待补做 → 再次声明（新版本） |

**底线**：不能把「审核通过」「已实际入库」「已送达」「项目已更新」合成一个笼统的「完成」（`源/实施规格-v1.0.md:183`）。

### 1.5 共同规则与异常边界

出处：`源/管培生带教-AI协同-业务共识-v1.0.md:128-140`。
- **待审状态**：不会因时间经过自动通过。
- **来源不充分**：说明缺什么依据、权限或更新，不编造事实，不声称已处理成功。
- **知识冲突**：争议答案等待确认；冲突资料整份处理清楚后再统一入库（后被 B 节的「只归位」覆盖）。
- **数据不一致**：区分本人报告、审核结果、表内事实，并列出待核对项。
- **操作失败**：如实保留结果，不把「审核通过」冒充成「已入库」或「已送达」。

### 1.8 考核与述职口径

1. **季度复盘 / 阶段答辩的「4+1 核心主线」**（这是带教方反馈里的通用口径，出自含个人评价的文件，只摘通用部分，原文件未复制，`源/work/content-slice-20260909/quarter-feedback-text.txt:3-70`）：

   - ② **用户与服务链路认知**：服务的用户是谁、核心问题和需求、业务流程和触点、链路断点、自己理解的变化、「用户侧链路重塑」的完整结论和交付物。该文档是**季度成果证据**，不只是答辩素材。

   - ④ **营销线**：营销与用户理解、产品表达、业务交付的关系；参与的实际事项；形成的新判断；还没验证的假设和能力缺口。
   - ⑤（+1）**AI 使用与人机协同**：贯穿前四条，不是工具展示。要说明：
     - 使用方式的变化；AI 在哪些环节起作用；
     - 能否明确目标、提供上下文、拆分人机职责、设定验收标准；
     - 提效、返工或结果的证据；AI 是否放大过错误，自己怎么核验和纠偏；
     - 沉淀了哪些工作流、模板、Skill；还有哪些能力缺口。

     目标是从「让 AI 帮我完成任务」进步到「能设计人机协作方式，用 AI 放大正确的业务判断，并对结果负责」。

   - **必须有真实产物支撑**：结果文档、推进过程、评价反馈、实际影响。「我学到了」之类只算主观声明。
   - **总体判断用的证据链**：事实证据 → 我的判断 → 我的取舍 → 我推动的动作 → 产生的变化 → 如何证明 → 没有我会有什么不同（`同上:270`）。评分只针对答辩材料体现的能力，**不等同于完整绩效评价**（`同上:265`）。

### 3.5 提醒规则（已实现，从未开启自动）

### 5.2 失败过的做法和教训

1. **工程开销远大于业务产出。** 每次上线都要走不可变候选、联合切换、两次跨 30 秒健康核验、两轴审查；部署常因 SQLite WAL 物理收拢、Worker 瞬时忙碌等原因被安全门禁中止，然后重开一次（如 `源/阶段状态.md:19`、`:31`、`:67`）。三周 113 次提交，大部分是部署和恢复，真人业务只有十几次。**对工作台的启示**：机器人只做推送和对话，状态放进工作台数据库，不要再在 Mac 本机维护一套带多个 SQLite 的持久工作流。
2. **本机承载**：电脑休眠、关机、断网时不保证处理；`launchd` 环境下找不到 lark-cli 或 node 的 PATH（`源/.scratch/trainee-collab/issues/08-automation-reliability.md:14`）；应用更新后 Codex CLI 路径变了（09-28 `c7c2f8d`）。
3. **代理多次擅自扩大需求**：知识入库被做成正文加工；周期提醒被设计成定时扫描。常浩每次都要纠正。凡是「已确认规则以外的东西」都必须先问。
4. **两步审核太重**（答案审核 + 入库位置确认），后来合并为一步。
5. **把「真人验收」设为关票门槛**，结果 Ticket01、02、03、07 都停在 in-progress，等「自然发生的真实问题」，一直没关。
6. **审核卡的展示坑**：正文首行「本次答案待导师审核」被写进了已批准的正文，造成歧义（`源/阶段状态.md:376`）；卡片输入框上限 1000 字，只能另开回复入口。
7. **周报口径错误**：示例曾用 9 月 8 日至 14 日（不是自然周），把 9 月 14 日的完成项算进本周（`源/work/project-weekly-report-card-design-20260915/project-weekly-report-card-spec-v2.md:3`）。工作台按自然周和工作日日历统计时要注意。
8. **提醒验收**：真实数据没命中时只能发标注「模拟预览」的卡，**不能为了验收修改 Base 去制造业务状态**（`源/.scratch/trainee-collab/issues/04-project-reports.md:29`）。
