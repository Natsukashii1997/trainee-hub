# 旧营销战役能力迁移审计

审计时间：2026-09-20  
审计对象：`营销战役AI协同MVP` 仓库、旧营销 Base 绑定、已安装运行入口与暂停状态  
审计方式：只读源码、配置、既有验收证据和本机运行状态；未写 Base、未启停服务、未发送消息、未修改代码

## 一、结论

本次合并应采用“迁移能力机制，重新绑定统一业务对象”的方式，不能直接搬迁旧系统。

可复用的核心有四组：

1. Release 驱动、可补偿、可回读的标准任务初始化机制；
2. 内容物料从正式提需到制作、审核、指定交接的卡片状态机；
3. 月度折扣按“月份 × 业务线 × SKU”识别、校验、upsert、回读和留痕的处理机制；
4. 来源事件幂等、状态版本校验、业务写回与卡片投影分离、最小 AI 执行记录等可靠性规则。

必须废弃或重做的部分包括：旧 Base token、全部旧表和字段 ID、旧记录 ID、旧 SQLite 运行状态、旧营销专属群与专属身份隔离、旧营销独立周报调度、旧九表模型，以及任何把“审核通过”等同于“物料完成”的历史实现。

新的权威结构应是：

- `工作项目`：营销战役作为项目类型之一；
- `任务事项`：由“标准模版-营销战役推进”生成项目任务；
- `营销战役推进`：承载营销专属策划和推进事实，并关联 `工作项目`；
- `产品SKU目录`：统一 SKU 字典；
- `内容物料`：承载提需、制作、审核、交接全流程，并关联项目/战役；
- `月度折扣同步记录`：承载按月变化的价格与促销事实，不能把月度历史覆盖进 SKU 目录；
- 统一的 `AI执行记录` 或自动化运行记录：承载动作、来源事件、回读和恢复点；
- 既有项目日报、周报：营销只作为进行中项目的一种，不再单独发送营销周报。

## 三、能力到统一底座的迁移映射

### 3.1 标准化新建

**旧能力**

旧入口以战役名称、负责人、开始时间为最低前置条件，锁定不可变模板 Release 后创建任务、补齐前置关系，并对最终任务集合及关系做权威回读。当前 Release 为 `MKT-CAMPAIGN-TASKS-v3.0-init-r1`，含五项主任务：

1. 提交策略分析输入；
2. 形成并确认本场策略；
3. 提交主题与节奏；
4. 提交应交清单与制作输入；
5. 完成本场物料交付。

依赖关系是 T1 → T2 → T3，T3 分别指向 T4、T5；T4 与 T5 可以并行，单份物料输入齐备即可先制作。

**统一底座落点**

| 目标表 | 必要业务字段 | 必要技术字段 |
|---|---|---|
| 标准模版-营销战役推进 | 模板名称、任务名称、阶段、负责角色、默认排期规则、验收标准、是否里程碑、前置步骤 | 模板 ID、模板版本、步骤 ID、流程序号、启用状态、内容摘要/Release 摘要 |
| 工作项目 | 项目名称、项目类型=营销战役、负责人、开始时间、结束时间、阶段、下一动作、关联营销战役推进 | 模板版本、Release ID、初始化状态、初始化说明、初始化周期、状态版本 |
| 任务事项 | 所属项目、任务名称、负责人、计划起止、状态、优先级、验收标准、阻塞原因、下一动作 | 模板步骤 ID、前置步骤 ID、前置任务关联、周期序号、流程序号、实例化幂等键、来源项目记录 ID |

**触发事件**

当 `工作项目` 满足以下条件时进入初始化候选：

- 项目类型为营销战役；
- 选择“标准模版-营销战役推进”；
- 项目名称、负责人、开始时间均非空；
- 初始化状态为未初始化或需补偿；
- 当前模板 Release 与项目锁定版本一致。

可采用 Base 按钮/Workflow 发出事件，也可采用有界轮询作为补偿。无论入口如何，最终只允许同一初始化服务写入。

**可迁移代码接点**

- `task_initialization_orchestrator.py`：两阶段增量对账、任务与依赖回读；
- `task_initialization_operation_ledger.py`：同一业务键幂等、本地单实例租约；
- `task_initialization_recovery.py`：先只读预检、绑定计划摘要、再显式补偿；
- `task_initialization_poller.py`：有界候选发现和串行初始化。

**必须重写**

- `task_initialization_base_gateway.py` 的 Base/table/field 绑定；
- `build_business_key()` 中硬编码的旧 Base 与旧战役表坐标；
- 旧战役表的初始化字段写回路径；
- 五任务内容是否原样采用，要以新 Base 中用户已经建立的“标准模版-营销战役推进”回读为准，旧 Release 仅作语义对照，不能覆盖新模板。

### 3.2 项目日报、周报

**旧能力**

旧营销周报每周一 10:00 主执行，10:10、10:30 静默补偿；同自然周只成功发送一次。报告读取营销战役、任务、主题、物料，区分来源事实、确定性规则判断、AI 建议和数据缺口。任一核心表读取失败时不把未知解释成“无风险”。

**统一底座落点**

- 直接使用现有项目推进管理的日报、周报生成器；
- 查询 `工作项目` 中仍在进行、项目类型为营销战役的记录；
- 任务、风险、DDL、待决策和下一动作统一来自 `任务事项` 与项目表；
- 物料待审核、逾期和阻塞可作为营销项目的附加板块；
- 无进行中营销战役时不增加空板块。

**可复用逻辑**

- 进行中对象过滤；
- 逾期、本周到期、待审核、风险等级、待决策、Todo 计算；
- 数据缺口显式报告；
- 事实/规则判断/建议分层；
- 周期幂等键。

**禁止迁移**

- 不恢复 `cn.lumiedu.marketing-campaign-ai-weekly`；
- 不再向旧营销群单独推送周报；
- 不复制旧四表聚合入口；
- 旧实现只有周报，不能被描述为已具备统一日报能力；日报由现有管培项目报告链路提供。

### 3.3 月度折扣同步记录

**旧能力**

旧实现识别完整月度方案或多消息批次，以“月份 × 业务线 × SKU”为自然键，先核验 SKU、业务线和字段完整性，再对单个 SKU 记录执行新建或更新，并逐字段回读。事实字段为试听价格、正价价格、新签活动、续费活动；保留同步人、同步时间和来源消息。批次层已有消息快照、租约、检查点、密封和隔离损坏 JSON 的机制。

**统一底座落点**

必须保留独立的 `月度折扣同步记录` 逻辑表；如果新 Base 尚无此表，应在“营销战役策划”目录中创建。`产品SKU目录` 只保存稳定 SKU 身份和属性，不能用“当前折扣”字段覆盖历史月份。

必要字段：

- 记录名称；
- 所属月份；
- 业务线；
- SKU 关联；
- 试听价格；
- 正价价格；
- 新签活动；
- 续费活动；
- 同步人；
- 同步时间；
- 来源消息 ID/来源事件；
- 数据环境或业务范围；
- 同步幂等键；
- 最近回读状态/异常说明。

**事件与动作**

机械邪龙兽收到合法月度方案 → 识别批次 → 整批预校验 → 以自然键查重 → upsert → 逐字段回读 → 写 AI 执行记录 → 回复一张结果卡或结果消息。

**可迁移代码接点**

- `parse_monthly_strategy_sync()` 与月度多消息批次解析；
- `_preflight_monthly_strategy()`；
- `_monthly_discount_fields()`；
- `_validate_monthly_readback()`；
- RuntimeStore 中 monthly batch 的消息、租约、检查点和完成状态。

**迁移时必须修正**

旧 `_execute_monthly_strategy()` 在预检后逐项写入，运行中间失败仍可能产生部分成功；统一底座应把“整批校验通过”与“逐项可恢复写入”明确区分。不能把部分成功报告成整批成功；恢复只能根据每个自然键的回读结果补未完成项，不能整批盲目重放。

### 3.4 内容物料提需—制作—审核—真实交付

**当前正确状态机**

```text
待制作 → 制作中 → 待审核 → 待交接 → 已完成
                    └─退回→ 制作中
```

审核通过只到 `待交接`。只有指定交接已发送、返回消息身份，并且回读的接收目标、成果版本与发送记录一致，才进入 `已完成`。不增加负责人二次签收。

**统一底座落点**

`内容物料` 至少需要以下字段组：

| 字段组 | 必要字段 |
|---|---|
| 归属 | 物料名称、所属工作项目、所属营销战役推进、应交项稳定 ID、主题/策略/SKU 关联（按新表实际结构取舍） |
| 提需 | 使用场景、需求正文/需求文档、参考附件、物料规格、人工 DDL、优先级、提需人、物料对接人 |
| 制作 | 制作负责人、当前状态、当前成果附件/链接、成果版本摘要、提交审核人、提交审核时间 |
| 审核 | 审核人、审核动作、审核时间、修改意见、审核所针对的成果摘要 |
| 交接 | 指定交接类型、目标、实际接收人、发送消息 ID、交接成果摘要、回读回执、交接完成时间 |
| 治理 | 状态版本、下一动作、阻塞原因、卡片消息 ID、来源事件 ID、动作幂等键、数据环境/业务范围 |

**角色与卡片动作**

| 状态 | 允许动作 | 有权角色 | 成功条件 |
|---|---|---|---|
| 待制作 | 开始制作 | 制作负责人或物料对接人 | 当前制作输入版本有效，写回制作中并回读 |
| 制作中 | 提交当前成果审核 | 制作负责人或物料对接人 | 终版可访问、形成成果摘要、审核人已明确 |
| 待审核 | 审核通过 | 当前审核人 | 审核绑定当前成果摘要，进入待交接 |
| 待审核 | 填写意见并退回 | 当前审核人 | 修改意见非空，退回制作中 |
| 待交接 | 完成指定交接 | 物料对接人或提需人 | 发送与回读均确认，目标和成果版本一致 |

卡片必须携带对象身份、动作、来源群、预期业务状态、预期状态版本和幂等键；旧卡版本不能覆盖新事实。业务写回是提交点，随后更新原卡；卡片更新失败只恢复卡片投影，不能重新执行已经完成的业务状态迁移。

**可迁移代码接点**

- `human_submission_flow.py`：主题、应交清单和逐份制作输入的正式提交与版本固化；
- `material_delivery_flow.py`：制作、审核、交接、整场查漏；
- `campaign_material_adapter.py`：机械邪龙兽卡片按钮接入、原卡更新、主卡同步和 AI 执行记录；
- `material_delivery_artifacts.py`：成果摘要、交接目标解析、发送与回执核验。

**禁止复用**

- `delivery_contract.py` 整包不能复用；其旧清单覆盖和旧任务/角色规则不符合五任务新口径；
- `v4_runtime.py` 中旧的“审核通过即已完成”物料路径不能进入新链路；
- 不能把已有物料记录反推为完整应交清单；范围必须来自负责人正式提交；
- 不能把附件上传、消息发送成功或卡片变绿单独解释为真实交付完成。

### 3.5 幂等、状态版本、回读与 AI 执行记录

这些机制应作为统一底座标准能力保留：

| 机制 | 新底座要求 |
|---|---|
| 来源事件幂等 | 同一按钮回调、Workflow 事件、消息或定时周期只处理一次；事件内容变化必须使用新事件 |
| 业务幂等 | 初始化按“项目 + Release + 周期”唯一；月促销按“月份 + 业务线 + SKU”唯一；物料交接按“物料绑定 + 成果摘要 + 目标”唯一 |
| 状态版本 | 卡片携带预期版本，旧按钮不能推进已变化对象 |
| 写后回读 | 创建/更新后重新读取目标字段；未回读一致不得报告业务完成 |
| 检查点恢复 | 只补最后可信检查点之后的动作；发送结果不明时禁止自动重发 |
| 业务与界面分离 | Base 写回成功后卡片更新失败，只恢复卡片，不重做业务动作 |
| 最小执行记录 | 记录动作、对象、操作人、来源事件/消息、幂等键、结果、回读、错误和环境；日志失败不能触发业务重写 |

若统一工作台已有公共执行记录表，应直接复用；若没有，应建立统一表，而不是再建一张营销专属日志表。业务字段保持人类可读，技术 JSON/检查点放隐藏治理字段或统一运行记录中。

## 四、明确不在本次迁移范围的旧能力

1. 独立营销专属智能体身份和“目标群排他、禁止回退带教上下文”规则。现在统一由机械邪龙兽处理，应该按项目类型和对象路由，而不是按两个机器人或两个孤立人格路由。
2. 独立营销周报 LaunchAgent。日报、周报统一由项目推进管理生成。
3. 旧九表中的策略、主题、结果复盘整套结构。用户当前明确保留的功能先落到现有新表；除非新工作台现有字段无法承载已确认业务事实，不应为复制旧模型而新建多张表。
4. DeepSeek 策略 Worker、旧策略主流程和旧知识文档读取。用户本轮未要求恢复策略生成，且旧凭据与正式知识接入曾未完成。
5. 旧外部设计需求台账双写。当前要求是统一 Base 内的内容物料流程，未经再次确认不恢复第二主表。
6. 旧 UAT 数据、旧卡片、旧来源消息、旧本地 SQLite 事件和历史 retryable 批次。保留只读证据，不迁移为新系统待执行任务。

## 五、安全迁移边界

1. 旧六项自动化保持 disabled；新链路未验收前不恢复任何旧 label。
2. 新旧系统不能同时扫描同一业务事件，不能出现两个初始化器、两个物料巡检或两个周报发送器。
3. 不复制旧 Base 的 record ID、field ID、view ID、role ID 或 chat ID；所有新绑定必须以新 Base 回读结果生成。
4. 不复制旧 SQLite 数据库，不重放旧 pending/retryable 事件；新运行库从空状态开始。
5. 不直接把 `.53` 候选部署到机械邪龙兽；它绑定旧 Base 和旧营销专属场景，只能作为源码迁移源。
6. 新模板内容以新 Base 的“标准模版-营销战役推进”为准；旧五任务 Release 只用于逐项核对，不自动覆盖。
7. 切换机械邪龙兽路由前，先验证管培主流程不受影响，并保证营销卡片只作用于 `项目类型=营销战役` 的对象。
8. 任何真实群卡片、月度折扣写入和交接发送都须在新 Base UAT 样本通过后再启用；本审计没有授权或执行这些动作。

## 六、推荐迁移顺序与验收

### 阶段 1：绑定统一事实源

- 回读新 Base 的目标表、字段、类型、关联方向、按钮/Workflow 和现有日报周报入口；
- 建立逻辑字段到真实字段 ID 的单一配置；
- 补齐缺失的 `月度折扣同步记录` 与统一执行记录能力；
- 验收：所有字段类型、关联目标和必选项回读一致，仍保持零业务写入。

### 阶段 2：标准化新建

- 迁移初始化器并绑定 `工作项目`、`任务事项`、新模板；
- 用一条明确 UAT 项目验证首次创建、重复触发、部分失败补偿和最终回读；
- 验收：只生成一套任务，关系正确，重复触发零重复，初始化状态与实际任务一致。

### 阶段 3：内容物料纵向闭环

- 先跑一份物料：提需 → 开始制作 → 提交当前成果 → 退回 → 再提交 → 审核通过 → 指定交接 → 回读；
- 再跑两份应交清单，验证 A 可先交付、B 未完成时整场任务不完成，B 完成后整场收口；
- 验收：旧按钮无效、版本变化使旧审核失效、交接不明不重发、卡片恢复不重做业务写回。

### 阶段 4：月度折扣同步

- 用两个 SKU 做同月首写和重复提交；
- 验证同一自然键更新而非重复创建、单项失败不会被报告为整批成功、恢复只补未完成项；
- 验收：全部业务字段、同步人、来源消息和环境回读一致。

### 阶段 5：并入日报周报与单机器人入口

- 让统一日报、周报读取一条进行中的营销项目；
- 验证营销只出现一次，无营销项目时不出现空板块；
- 将机械邪龙兽现有路由增加营销对象分支，避免创建第二机器人和第二周报；
- 验收：管培项目与营销项目均可正常处理，互不误写，旧六项自动化继续保持 disabled。

## 七、验证证据

- 2026-09-20 实时回查：六项旧 LaunchAgent 均未加载且均禁用。
- 当前相关离线测试：237 项通过，覆盖任务初始化、初始化账本与恢复、人工提交、物料交付、物料卡片适配和旧 V4 运行器。
