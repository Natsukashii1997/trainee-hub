# 营销战役 AI 协同 MVP：运维与失败恢复说明

> [!IMPORTANT]
> **当前机械邪龙兽阶段适用。**本轮 UAT 只使用机械邪龙兽在「数码宝贝世界」群内的营销战役第二身份；企业机器人/DeepSeek listener 已暂停，不得启动。以下 Bridge 与恢复约束是当前技术基线，但“进程正常/本地测试通过”不等于第二身份真实 UAT 已通过。测试顺序见[第二身份 UAT 手册](./机械邪龙兽_营销战役第二身份_UAT测试手册.md)。

> [!CAUTION]
> **月度策略同步也只能在「数码宝贝世界」做施工和 UAT。**不得向「月度策略同步」群发送任何测试消息、测试卡片或模拟数据。该群未来放行后只接受常浩发布的正式月度方案；机器人只能回复那条原消息，不得把该群作为主动推送、定时广播或测试目标。

## 1. 不可破坏的运行约束

机械邪龙兽 `codex` Bridge 是本场景唯一的飞书 WebSocket 事件消费者。所有群消息和交互卡片点击都必须先经过它。Bridge 的统一业务入口是项目根目录的 `intake.py`，不是 `service.py`。

禁止运行：

```text
python3 service.py listen
lark-cli event consume card.action.trigger
```

旧的 `cn.lumiedu.marketing-campaign-ai-mvp` LaunchAgent 会启动第二个 listener，因此已从项目删除。`install-recovery` 还会检查用户 LaunchAgents 目录：若发现遗留副本，先卸载，再改名为 `.disabled`，保留可追溯副本而不再自动启动。

月度策略同步是普通群消息入口的唯一特殊路由：

- 普通 UAT 消息仍必须在「数码宝贝世界」真正 `@机械邪龙兽`；
- 只有正式「月度策略同步」群中的常浩本人可以不 `@` 触发；系统识别消息中的明确月份、至少一个业务线段落、SKU 块和方案字段，不要求固定首行；
- 在「数码宝贝世界」测试时，即使内容符合月度方案结构也仍须真正 `@机械邪龙兽`；其他发送人、私聊、图片消息和其他群均不得触发；
- 「月度策略同步」群未来只作为正式消息输入和原消息回执位置，绝不能成为系统主动发送目标。

## 2. 事件从消息或点击到完成的路径

```text
飞书普通群消息
  → 机械邪龙兽 codex Bridge
  → intake.py message-event
     ├── 设计提需：intake.py
     ├── 月度策略同步：v4_runtime.py message-event
     └── 七类标准业务动作：group_scene_actions.py

飞书卡片点击
  → 机械邪龙兽 codex Bridge
  → intake.py bridge-event
     ├── 提需预览卡：intake.py 直接处理
     ├── 七类业务动作预览卡：group_scene_actions.py
     └── 物料流转卡：service.py bridge-event
                        → SQLite event_inbox 持久化
                        → Base 状态校验与写入
                        → Base 回读
                        → AI 执行记录
                        → 原卡片就地更新
```

月度策略同步的独立执行路径为：

```text
常浩在「数码宝贝世界」@机器人测试，或在正式「月度策略同步」群直接发送方案
  → Bridge 按发送人、群、消息类型和结构特征做 fail-closed 路由
  → v4_runtime.py message-event
  → 解析月份、本条消息实际出现的业务线和每个 SKU 的四类事实
  → 对本条消息整批预校验
     ├── 任一错误：固定失败 Markdown → 月度折扣表 0 写入、AI 执行记录 0 写入
     └── 全部通过：按“月份 × 业务线 × SKU”直接 upsert
                    → 每条逐字段回读
                    ├── 全部一致：固定成功 Markdown
                    └── 执行或回读任一失败：固定失败 Markdown
  → 两种结果均通过 reply-in-thread 进入原消息“1 条回复”话题
  → 话题中只保留一条回执，不发卡片、不发明细、不发第二条
```

结构要求：一条消息可以只提交 `【大学辅导】`、只提交 `【国际课程（国课）】`，也兼容同时提交两条业务线；实际业务默认分成两条消息分别发送。系统只校验和写入本条消息出现的业务线，未出现的另一业务线是 **no-op**：不报缺失、不清空、不修改历史数据。每个 SKU 独立一块、独立一行。方案统一落入 `试听价格`、`正价价格`、`新签活动`、`续费活动` 四类字段。价格按 SKU 规则校验：不适用的价格留空；未提供的新签活动或续费活动自动写入字面值 `无`。例如「论文稳Pass」没有试听价格，其 `试听价格` 必须留空。方案正文允许标题样式、emoji、换行、项目符号、代码块和中英文冒号；月份、业务线、SKU 归属和事实边界必须可识别，但不要求固定模板。

月度策略同步没有预览确认卡。完整消息本身就是常浩的执行确认；系统必须先完成整批预校验，才允许产生任何业务写入。

Bridge 只负责把事件通过 stdin 交给 `intake.py`。设计提需使用消息事件表、稳定业务键、草稿和回读防重。七类标准业务动作使用独立的消息/草稿/回调账本、SHA-256 请求摘要一致性校验、发起人和草稿版本校验，正式状态机仍由 `scene_actions.py` 执行。该摘要用于本地一致性与防串单，不是带密钥的 HMAC，也不是公网请求验签。只有物料流转卡回调转交 `service.py bridge-event` 后，才会在访问 Base 或飞书网络前把原始事件和标准化事件写入 `runtime/state.sqlite3`。

`confirm_delivery` 还有一个受控副作用：物料写为“已交付”并回读成功后，系统幂等确保一条草稿复盘存在。若建复盘失败，交付不回滚，AI 执行记录标记“部分完成”，并给出 `scene_actions.py recap-create --material-id ... --confirm` 补建命令；此时禁止重复点击交付确认。

七类标准动作如果业务尚未写入就失败，可以修正原因后重新发起；如果已经发生或疑似发生部分业务写入，会把该动作草稿置为 `manual_review`，不得自动重复执行业务动作。若只是“业务已完成但原卡更新失败”，恢复队列只允许补更新原卡，不重复写 Base。恢复任务只主动扫描七类标准动作的群消息和回调；若在无法证明是否已发卡/写业务的 `processing` 状态停留 300 秒，无需等待飞书重投就会转 `manual_review`，且不补发预览卡、禁止自动重放。它不扫描设计提需原始消息。普通营销问答必须进入独立营销会话、默认只读且不写营销战役 Base；严禁回落到管培生带教上下文。

同一张预览卡只有一个有效决策。第一笔确认、取消或返回补充会在业务写入前原子占用草稿；后续相反按钮、不同事件 ID 或并发双击都会被拒绝。陈旧巡检不会覆盖 `completed`、`cancelled`、`business_completed`、`card_update_pending` 等真实终态。

## 3. 三类恢复队列与规则

`service.py` 的 inbox 适用于物料流转卡回调：

| 状态 | 含义 | 恢复处理 |
| --- | --- | --- |
| `pending` | 已持久化，未完成业务处理 | 下一轮自动处理 |
| `processing` | 已被某个进程领取 | 300 秒未更新则视为中断并回收 |
| `completed` | 业务处理成功或已幂等完成 | 不再处理 |
| `failed` | 尚未产生业务写入的可恢复失败，保留了原因 | 尝试次数小于 5 时可重试 |
| `manual_review` | 已发生或疑似发生部分业务写入，无法安全自动判断下一步 | 永不自动重试；人工回读 Base 与 AI 执行记录后处理 |

恢复 LaunchAgent 每 60 秒执行一次 `bash manage.sh recover`，内部依次执行：

```text
service.py recover-inbox --max-items 20 --max-attempts 5 --stale-after 300
intake.py recover-cards --limit 20
group_scene_actions.py recover-cards --limit 20
```

三者只执行一轮后退出，不监听飞书、不创建 WebSocket、不扫描 Base 业务表。服务 inbox 只在能证明安全时继续处理，单条最多 5 次；`intake.py` 只补设计提需结果卡、预览/待补充消息对应的 AI 日志投影，单条最多 3 次；`group_scene_actions.py` 只补七类群动作的原结果卡，并主动收敛停滞的群消息/回调，单条卡片投影最多 3 次。后两者不会重放 Base 写入。超限或事实不明统一进入 `manual_review`。

### 3.1 月度策略同步的恢复与幂等

- 写入键固定为“月份 × 业务线 × SKU”：不存在则新建，唯一存在则更新；若同月同业务线同 SKU 已有多条，本条消息整批预校验失败并保持 0 写入，必须先人工合并重复记录。
- 每条成功写入后必须回读月份、业务线、SKU、四类事实、同步人、来源消息、同步时间和数据环境；没有完成一致性回读，不能回绿色成功卡。
- 飞书对同一来源消息 ID 重投时，不执行第二次 upsert，也不发送第二张卡。人工复制相同文字再次发送会产生新的消息 ID，不属于幂等重投。
- 预校验失败没有可恢复写入：修正本业务线消息中的全部问题后，由常浩重新发送该业务线的完整消息即可，不需要把另一业务线合并进来。
- 预校验通过后如出现部分执行或回读失败，已成功 SKU 保留，对外只回复固定失败 Markdown，不列 SKU 明细；不得宣称整批成功，也不得盲目重发整批或自动回滚。维护人员应在 Base 与 AI 执行记录中核对成功项和失败项，再决定只修复失败项还是人工校正。

## 4. 首次安装和日常巡检

业务人员正常使用不需要打开终端或执行命令。下面的命令只供维护人员使用；月度策略 UAT 的业务操作顺序见[使用手册 V4 的“月度策略同步”章节](./营销战役AI协同MVP_使用手册_V4.md#5-月度策略同步)。

首次执行：

```bash
cd "/Users/nat/Documents/AI 项目/营销战役AI协同MVP"
bash manage.sh test
bash manage.sh preflight
bash manage.sh install-recovery
bash manage.sh status
```

日常只需执行：

```bash
bash manage.sh status
```

`status` 要同时满足：

- 机械邪龙兽 `codex` Bridge 正常；
- Bridge 补丁和 `campaign-collab/1.1` 协议校验通过；
- 恢复 LaunchAgent 已加载；
- 旧 listener 未运行。

## 5. 手动恢复与日志

不想等待下一个 60 秒周期时，执行：

```bash
bash manage.sh recover
```

查看这两个文件：

- `runtime/recovery.stdout.log`：恢复结果；
- `runtime/recovery.stderr.log`：错误详情。

若某条尚未写业务的服务事件已尝试 5 次仍失败，或某个设计提需/群动作投影已尝试 3 次仍失败，自动任务会停止重试并转人工，避免无限发消息。任何检测到部分业务写入或无法证明是否写入的事件会直接进入 `manual_review`，不等待次数耗尽。所有情况都会保留错误时间和恢复日志，交给维护人员回读 Base 与 AI 执行记录。

## 6. 安全卸载和重启

```bash
bash manage.sh uninstall-recovery
```

这只会卸载恢复任务并删除 `~/Library/LaunchAgents` 中的安装副本；项目内 plist 模板保留，可再次安装。它不会停止机械邪龙兽 Bridge，也不会恢复旧 listener。

只有在 Bridge 补丁、配置或进程需要重新加载时，才执行：

```bash
bash manage.sh restart-bridge
```

该命令固定使用 `--profile codex`，只重启机械邪龙兽，不会切换到其他机器人。

## 7. 异常处理边界

- 只有 `service.py` 能证明尚未发生业务写入或已有精确恢复检查点时，才允许有限恢复；
- 设计提需恢复只补结果卡及相关消息的 AI 日志投影；七类群动作恢复只补结果卡投影；两者都不重发预览卡、不重做 Base 业务；
- 如果 Base 已有部分写入、但下一步已无法安全自动判定，系统会进入 `manual_review`，既不伪装成功，也不继续自动推进；
- 当前不提供完整 Saga 回滚、`saga_id` 或 `resume_saga`；危险的部分写入需要人工核对 Base 和 AI 执行记录；
- 不要通过删除 SQLite 或手工改状态来「重试」，这会破坏幂等和审计链；
- 飞书真实端到端验收必须在「数码宝贝世界」使用专用 UAT 记录，不要拿正式物料做测试。
- 月度策略施工与 UAT 的全部消息、单条文字回执和模拟记录也必须来自「数码宝贝世界」；严禁为了排查“无回复”而转去「月度策略同步」群试发。
- 月度策略整批预校验失败必须同时满足：原消息“1 条回复”话题中只出现固定失败 Markdown、月度折扣表 0 写入、AI 执行记录 0 写入；不能用“稍后补写”代替原子失败。
- 月度策略部分失败只允许发生在预校验通过后的执行或回读阶段；群内仍只返回固定失败 Markdown，不显示 SKU 明细，不得以成功文字或“全部完成”掩盖失败。具体失败项只在 Base、AI 执行记录和运行日志中核对。
- 当前 Bridge 与恢复守护部署在这台 Mac，依赖登录、联网和本机进程；若需要 7×24 小时与全公司使用，应把同一入口协议迁往持续在线的托管运行环境。

## 8. 当前动作边界

- 群消息识别设计提需，以及七类明确标准动作：提交设计版本、确认复盘、验证资产、登记资产同步、登记口径、确认口径、解除口径冲突；
- 群入口可靠处理文字和可访问链接，不自动读取图片或文件正文；涉及附件时需把关键事实粘贴为文字并附链接；
- 物料流程卡支持 10 项：`confirm_intake`、`request_intake_revision`、`confirm_request`、`request_revision`、`accept_design`、`reject_design`、`approve_audit`、`reject_audit`、`confirm_delivery`、`reject_delivery`；
- 七类标准动作的预览卡共用 `confirm_group_scene_action` 和 `cancel_group_scene_action`，回调必须来自原消息发起人；
- 维护备用的 8 个本地命令为：`submit-version`、`fact-resolve-conflict`、`recap-create`、`recap-confirm`、`asset-verify`、`asset-sync`、`fact-register`、`fact-confirm`；默认只预览，必须加 `--confirm` 才写入；
- `recap-create` 会复用终稿确认时已经生成的未归档复盘；只有不存在时才补建草稿，不会直接创建资产。

月度策略同步只有两种固定文字回执：

| 回执 | 必须表达的事实 | 后续动作 |
| --- | --- | --- |
| `月度促销方案同步成功 \| [营销战役表](https://vm94j8bzy7.feishu.cn/base/LgqpbDFz8a9XmNs3TxccAP0Hn7b?table=tblaUHNEhPhYjfJw)` | 本条消息中的全部 SKU 已按月份 × 业务线 × SKU 写入且逐字段回读一致 | 点击蓝色“营销战役表”链接抽查，不重复发送 |
| `月度促销方案同步失败 \| [营销战役表](https://vm94j8bzy7.feishu.cn/base/LgqpbDFz8a9XmNs3TxccAP0Hn7b?table=tblaUHNEhPhYjfJw)` | 预校验、执行或回读至少一项失败；群回执不展示具体明细 | 停止盲目重试，由维护人员核对 Base、AI 执行记录和运行日志 |

两种回执都必须通过 `reply-in-thread` 进入常浩原促销方案消息的“1 条回复”话题，话题内只保留这一条固定 Markdown；不发卡片、不追加明细、不发第二条，也不得另发独立广播。

## 9. 一个最常见的报错

**现象：** `bash manage.sh status` 显示“恢复任务未安装”。

**处理：**

```bash
bash manage.sh install-recovery
bash manage.sh status
```

成功时应同时看到机械邪龙兽 Bridge 正常、每 60 秒恢复任务已加载、旧 Listener 未运行。不要为了修复该报错启动 `service.py listen`。

若 `preflight` 不是 `ok: true`，按输出中 `ok: false` 的具体检查项处理，不要手改正式业务记录。当前设计检查使用专用“待设计接单”记录 `recvt9Ahiwamye`；若它未来被继续推进，应由维护人员新建下一条 UAT 记录并更新预检夹具，而不是把旧记录倒退状态。
