## 2. 一句话说明怎么使用

业务人员只需要在群里发完整请求并查看结果卡；设计提需不再经过预览确认。设计人员在外部设计需求表处理需求，并把终稿上传到营销战役多维表格；机器人在已经验收的范围内完成双表同步、状态推进、只读汇总和异常留痕。设计提需“双表同步”纵向切片与内容物料代表性“退回—换稿—重审—通过”全链均有真实证据；发生实质版本变化时，只按影响层级补做与版本/hash绑定的验收。

正常业务人员不需要安装软件，不需要打开终端，也不需要阅读代码。

## 5. 最终业务规则

### 5.1 战役与策略

- 战役目标单独记录，不与待办事项混在一起。
- 用户策略采用四个清晰问题：
  - `WHO｜目标用户`；
  - `WHY｜待办事项`；
  - `WHAT｜主推SKU`；
  - `WHEN｜战役起止日期`。
- 不保留牵强的 WHERE / 主要渠道字段。
- 同一战役可以有多个目标用户；同一目标用户可以有多个待办事项；每个待办事项可以关联不同 SKU。

### 5.2 任务、主题与物料

- 任务事项是内部推进线，不能把设计物料塞入任务表。
- 任务事项采用 Base 手填最短路径：机器人收到新建、补充、改派或状态维护请求时，只返回任务事项表直达链接，不建草稿、不写任务、不写 AI 执行记录、不提供任务状态按钮。
- 营销主题是按周组织传播节奏的单元，一场战役可以有多个主题。
- 一个主题可以关联多个 SKU，也可以产生多套内容物料。
- 内容物料只收真实协作需要的信息，不要求提需人填写完整策略分析。
- Brief 是内容物料里的字段与角色视图，不是第二张事实表。
- 审核只记录当前结果；本期不记录每轮修改、每版意见和复杂版本历史。
- 物料分“营销物料”和“常规物料”；折扣版本统一进入月度折扣表。
- 是否值得沉淀，只在物料完成后勾选“需入中台”；本期不建设独立资产流程。
- 内容物料跨部门对接链路中的业务日期统一到日：交付DDL、外部设计需求期望交付日期、催办到期日、审核业务日期、终稿交付日期和完成回执日期只保存或展示年月日。内容物料表的`交付DDL`、`设计完成时间`、`审核时间`、`完成时间`及外部表的`期望交付时间`均以`yyyy/MM/dd`显示；卡片用`8月31日`这类日期。系统提需时间、消息/卡片发送时间、同步时间、AI运行/审计时间和状态更新时间仍可保留时分。任务事项DDL不受本规则影响。

设计提需 V2 的输入契约固定如下：

- 支持带明确语义的自然语言，不要求用户记忆字段顺序；
- 5 项必填：`物料名称`、`使用场景`、`物料规格`、`交付DDL`、`提需文档链接`；
- `使用场景`只能是：`朋友圈`、`私信`、`其他`；
- `物料规格`只能是：`海报`、`单图`、`九宫格`、`六宫格`、`三宫格`、`其他`；
- 3 项选填：`优先级`（未提供时默认 `P1`）、`关联SKU`、`所属主题`；
- 物料大类由使用场景确定性派生：朋友圈 → 营销物料，私信 → 常规物料，其他 → 其他；用户不能另行覆盖；
- 交付DDL只保留日期；消息即使包含几点几分或“下班前”也忽略时间，只提取明确、唯一的交付日；没有明确日期或无法唯一确定日期时，仍属于必填信息缺失或歧义；
- 任一必填项缺失、歧义或非法时，一次列全所有问题，并保持零写入；
- 完整且合法的原始消息直接执行，不再增加预览或二次确认；只有双表写入成功，并对全部输入字段、派生字段和系统默认字段逐字段回读一致，才可发送成功卡。内容物料表的`交付DDL`与设计需求表的`期望交付时间`必须回读为同一天。

旧字段`物料形式`、`使用场景/规格`、`需求说明`已经退出 V2，不再展示、不再要求填写，也不能代替任何必填项。

### 5.3 月度折扣

- 唯一键是“月份 × 业务线 × SKU”。
- 同月同业务线同 SKU 已存在时更新原记录，不新建重复行。
- 大学辅导和国际课程通常分两条消息发送；系统只处理本条消息出现的业务线，另一业务线不报错、不清空、不改历史。
- 一条消息可以包含多个 SKU，但每个 SKU 必须独立成块、独立一行。
- 本条消息中的每个 SKU 都以归一化后的四类事实覆盖当月记录；未提供的新签活动或续费活动写“无”，不沿用旧值。
- 同月同业务线同 SKU 已经存在重复记录时，停止自动写入，先人工合并。

月度折扣记录的身份边界固定为：`方案编号`是稳定、只读的业务身份，`方案名称`是可修改标题，`record_id`是技术主键，隐藏自动序号源是系统字段。Agent、机器人、Workflow 与人工业务操作只写获准的标题和业务字段，不写公式编号或隐藏序号源，也不执行“最大编号 + 1”。

设计提需只使用三类结果卡片：

1. **信息不完整卡**：黄色，一次列全缺失、歧义和非法项；明确“本轮零写入”，不提供确认按钮；
2. **同步失败卡**：红色或橙色，如实显示主表、外部表、回读或回执中的真实失败阶段，不伪装成功；
3. **需求提报完成卡**：绿色，仅在双表完整逐字段回读一致后出现；交付DDL只显示日期，例如`8月31日`，不显示时分；展示物料名称、类型需求和交付DDL，并保留“查看设计提需文档”。

## 7. 两条核心状态机

### 7.1 内容物料

```text
待设计接单
→ 制作中
→ 待审核
→ 已完成
```

- 不发送设计接单卡或“我来接单”按钮；设计团队在外部设计需求表承接需求，设计负责人直接在 Base 人员字段中确定。
- 设计负责人手动把最终文件放入“终稿附件”。
- 系统只判断附件是否存在，不读图、不替代审核。
- 制作催办、送审、审核、终稿交付和完成回执中出现的业务日期只到年月日；精确事件时间只保留在系统审计层。
- 审核人通过后直接进入已完成；原审核卡收口为不可操作的绿色完成态，不再生成提需人二次确认卡。
- 审核退回回到制作中；设计人员上传新终稿后重新进入待审核。
- 改派不设计复杂规则，直接修改多维表格里的人员字段。

### 7.2 内部任务

```text
待开始 → 进行中 → 待验收 → 已完成
                    └─ 退回 → 进行中
```

- 使用者直接在 Base 新建、补充、改派和维护状态；
- 机器人收到任何任务维护请求时，只返回[04｜任务事项](https://vm94j8bzy7.feishu.cn/base/LgqpbDFz8a9XmNs3TxccAP0Hn7b?table=tblMK7GxGkyQUviP)直达链接；
- 不生成任务草稿，不创建或修改记录，不写 AI 执行记录，不提供开始、提交验收或验收结果按钮；
- 任务与物料保持两条独立业务线。

## 8. 自动化与固定节奏

> 本节 8.1 和 8.2 描述冻结的自动化规则。`status` 已确认终稿附件巡检与周度任务调度健康且运行包为已取证版本；非卡片周度消息格式已经完成真实群 UAT。内容物料代表性全链已有真实历史证据；如实现、规则或视觉发生实质变化，技术运行健康不能替代受影响层及其下游的版本化现场复核。

### 8.1 终稿附件巡检

- 目标触发频率为每 60 秒一次；
- 只检查当前状态为制作中且“终稿附件”非空的物料；
- 新附件成功识别后推进到待审核，并向群里发送审核卡；
- 同一附件指纹不能重复送审；
- 机器人不读取或分析终稿内容；审核结论必须由审核人作出。
- 审核卡中的终稿交付日期、审核截止日期或审核业务日期只显示年月日；主表`设计完成时间`和后续`审核时间`均以`yyyy/MM/dd`显示，底层巡检与审计时间可保留时分。

### 8.2 战役周度总览

- 每周一 10:00（Asia/Shanghai）主执行并推送到“数码宝贝世界”，10:10、10:30 仅在前序未成功时静默补偿；无需任何人 `@` 或发送触发词；
- 固定只读`02｜营销战役`、`04｜任务事项`、`05｜营销主题与节奏`、`06｜内容物料`四张核心表，不改变任何业务记录；
- 只发送一条完整飞书 Markdown / 富文本消息；不是卡片、不使用卡片色块、不提供任何按钮；
- 消息依次包含：标题与统计周期、数据截止时间和事实源、核心数据、战役情况、风险与阻塞、待决策事项、Todo、AI 建议、数据缺口、Base/看板链接；
- 任务 KPI 固定为有效任务总数、已完成、未完成和完成率；`已取消`不进入分母；有效任务为 0 时显示`0/0（—）`；风险任务仍单独展示；
- Base 已确认事实、AI 分析/建议和数据缺口必须分层。关键来源读取失败时明确写出缺口和受影响结论，不得用空数据判断“整体正常”；
- 同一自然周最多一条成功总览。人工运行或补发也复用相同幂等键；已有成功消息时返回已有结果，不重复刷群。

### 8.3 每日综合 DDL 汇总（待配置）

预期范围为任务、物料、逾期和战役关键节点 T-3，但当前未配置、未启用，也没有可承诺的每日发送时间。未来若启用，物料催办到期日只展示年月日；触发与发送时间属于系统时间，可以保留时分；任务事项 DDL 仍按任务表自身规则展示。战役关键节点事实源和发送时间需在最终结构冻结后确认，完成配置与真实群验收前不得对用户宣称已经运行。详见[待最终配置能力清单](./待最终配置能力清单.md)。

### 8.4 健康判断

1. 未结束对象存在阻塞原因：阻塞；
2. 否则存在已逾期、48 小时内到期或战役待决策事项：需关注；
3. 其余：正常。

## 9. 角色、工作面与权限

V4 最终保留 5 个自定义角色工作面。角色名称和视图可以按实际组织适配，但以下原则不变：

| 角色 | 只需关心 |
|---|---|
| 战役管理者 | 战役、策略、节奏、风险、复盘和整体看板 |
| 内部执行者 | 在任务事项表直接维护自己负责的任务、DDL、完成说明和状态 |
| 设计协作者 | 待接单物料、需求、参考资料、终稿附件和当前状态 |
| 审核人 | 待审核物料、需求、终稿和审核按钮 |
| 协同查看者 | 被授权的只读信息、进度和结果 |

当前 UAT 的提需人、设计负责人、审核人、任务负责人和验收人先统一使用常浩账号。这是单人验收方式，不是正式组织权限模型。扩大使用前，需要至少用不同真实账号再跑一次角色 UAT。

共同权限原则：

- 业务角色只看自己需要的字段与记录；
- 系统字段、幂等键、卡片消息 ID 和附件指纹不暴露给普通业务人员；
- 设计提需无写入前预览或二次确认；其他带按钮的高影响动作只允许当前合法角色操作；
- 设计负责人由 Base 人员字段确定；审核和提需确认校验当前角色；任务推进和验收由使用者在 Base 手工维护；
- 删除、表结构修改和权限修改不由普通群消息直接执行。

## 10. 卡片交付标准

卡片按“状态—指标—关键事实—判断—链接—动作”的顺序排布，不是简单照搬表格。

强制规则：

- 设计提需结果卡中的**物料名称、类型需求、交付DDL**的字段名和值必须黑色加粗；
- 进入角色流转后，**提需人、设计负责人、审核人**的字段名和值也必须黑色加粗；
- KPI 值突出，KPI 小标签可以使用浅灰小字；
- 当前判断、验收标准和下一步保持黑色高对比；
- 系统时间、来源、环境、状态版本和系统说明使用浅灰小字；内容物料业务日期保持清晰可读并只到年月日；
- 同一类卡片允许组合相容浅色块，不要求单一颜色；
- 一张卡最多一个最强主操作；
- 退回使用危险样式和二次确认；
- 链接文案说明打开后能做什么，不显示裸 URL 或记录 ID；
- 信息不完整卡和提需完成卡提供清晰的提需文档链接；当前绿色完成卡底部固定为“写入状态：已写入 | 查看设计提需文档”；
- 正常流转优先更新原卡，不重复发送同内容摘要。
- 提需、设计同步、催办、审核、终稿交付和完成回执卡中的业务日期一律不显示时分；只有系统运行和审计时间可以显示时分。

完整视觉规则见[卡片视觉与交互规范 V4](./卡片视觉与交互规范_V4.md)。

## 11. 安全、幂等与失败恢复

一次动作只有同时满足以下条件才算成功：

1. 操作者身份正确；
2. 当前业务状态允许该动作；
3. 状态版本与卡片一致；
4. 多维表格写入成功；
5. 写后回读与预期一致；
6. 卡片进入新状态或明确给出恢复结果；
7. 业务结果确认后尽力留下最小 AI执行记录，用于审计与异常回查；日志失败不反向改变已经由业务写入和回读确认的结果。

这套成功条件只适用于机器人实际获准执行的动作。任务事项请求的正确结果只是返回任务表直达链接，不存在机器人任务写入、成功卡或 AI 执行记录。

其中，设计提需的成功卡只以双表写入和回读为闸门，第 5 条不是抽样回读：必须逐字段核对 5 项必填、用户提供的选填项、默认优先级和派生物料大类；交付DDL只按日期比较，并要求内容物料表与设计需求表回读为同一天。任一字段不一致，都只能返回“创建未确认成功/转人工核对”，不能发送绿色成功卡。最小 AI执行记录在该业务完成后补充，不参与绿色成功卡判定。

防错规则：

- 来源消息、确认动作和业务唯一键共同防止重复创建；
- 第一笔有效按钮动作占用当前状态，重复点击或并发点击不能重复推进；
- 同月同业务线同 SKU 使用 upsert，SKU 按“业务线 + SKU标准名称”匹配，不以标题模糊匹配；
- 卡片与 Base 不一致时，以 Base 为准，停止继续点击旧卡；
- 无法确认是否已写入时，不自动重做业务写入，转人工核对；
- Secret、API Key、验证码、客户隐私、人员 ID 和内部 Prompt 不进入群卡片或公开日志。

## 12. 日常使用与异常处理

### 日常人员

正常只做四件事：

1. 在群里发送完整请求；
2. 查看机器人返回的信息不完整卡、同步失败卡或需求提报完成卡；
3. 进入审核时，只有审核人点击“审核通过”或“退回修改”；审核通过后不再存在提需人确认按钮；
4. 设计终稿手动上传到多维表格“终稿附件”。

### 卡片没有回复

1. 确认在“数码宝贝世界”；
2. 确认真的 @ 到机械邪龙兽；
3. 确认使用了标准消息开头并把字段写在同一条消息；
4. 等待一分钟；仍无回复再交维护人员检查。

不要连续发送相同请求。

### 卡片提示信息不足

本轮没有写表。按照卡片列出的缺失项，一次补齐后重新发送完整消息。

### 旧卡、状态变化或错人

打开卡片里的多维表格记录，确认当前状态和人员，只操作最新卡。如需改派，直接修改人员字段。

### Base 已变化但卡片没更新

停止点击，以 Base 为准。把截图、发生时间、对象名称、记录链接和点击动作交给维护人员。

## 13. 维护人员只保留五条命令

正常业务人员不需要敲命令。维护人员在项目目录只使用：

```bash
cd "/Users/nat/Documents/AI 项目/营销战役AI协同MVP"
bash manage.sh status
bash manage.sh test
bash manage.sh recover
bash manage.sh weekly-overview
bash manage.sh final-acceptance
```

- `status`：检查事件入口、终稿巡检、恢复任务和周度任务调度状态；
- `test`：运行本地回归，不应向群发送消息或修改业务数据；
- `recover`：只处理可以证明安全的待恢复事件；事实不明则转人工；
- `weekly-overview`：立即人工运行一次与定时任务同格式的完整 Markdown / 富文本周度总览，仅用于预览、运维核对或受控补发；同一自然周仍遵守幂等，不得产生第二条成功消息；
- `final-acceptance`：执行当前版本的只读最终验收；当前九表 V4 旧合同结果为 `ok=false`、111 项通过、17 项失败，且无外部写入。旧 `ok=true`、116 项通过只作 revision 112 迁移前历史快照。

最常见问题：状态显示某个服务未运行。先执行 `recover`，再执行 `status`；如果仍异常，把完整输出交给维护者，不要自行修改配置或运行旧 Python 文件。

## 16. 下一阶段：从 MVP 到可复用底座

下一步不是继续给营销场景加表，而是选择第二个真实场景，例如项目推进或管培生培养，重复同一搭建方法：

```text
1. 用提问澄清业务对象、角色、状态、事实源和完成标准
2. 区分必须统一的底座能力与必须场景适配的业务规则
3. 先建最小对象模型和角色工作面
4. 跑通一条真实“请求—确认—写入—推进—完成—回查”纵向链路
5. 对比营销场景与第二场景，提炼稳定协议和可配置项
6. 再封装为供其他团队使用的最终 Skill
```

预计可以直接复用：

- 与风险匹配的确认机制（普通写操作默认写入前预览与人工确认，场景可定义严格直写例外）；
- 对象 ID、来源消息和幂等协议；
- 角色、状态、版本和旧卡校验；
- 写后回读；
- 即时只读查询与定时周度分析框架；
- 卡片信息层级与颜色语义；
- 最小执行记录与失败转人工；
- “确定性自动化 + Agent 判断”的分工。

必须按场景重新定义：

- 业务对象和字段；
- 状态机；
- 角色与权限；
- 必填信息；
- 专业知识和判断标准；
- 业务卡片内容；
- 提醒节奏与完成标准。

第二场景迁移成功后，才能严谨地把成果定义为“企业级 AI 协同底座”，并进一步生成供其他团队通过问答完成场景适配的最终 Skill。
