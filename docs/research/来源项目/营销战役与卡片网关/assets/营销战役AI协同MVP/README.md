## 业务结构

V4 严格使用 9 张表：

```text
SKU目录
├─ 战役—用户策略 ← 营销战役
└─ 月度折扣方案

营销战役
├─ 任务事项                 内部推进线
├─ 营销主题与节奏
│  └─ 内容物料             跨部门生产与确认线
└─ 结果与复盘               学习线

AI执行记录                 最小运行与异常回查
```

关键边界：

- 战役目标单独记录；用户策略按“战役 × 目标用户 × 待办事项 × SKU”拆行。
- 任务事项只管内部推进，不承载设计物料。
- 任务事项由使用者直接在 Base 手工填写和维护；机器人收到新建、补充、改派或状态维护请求时只返回任务事项表直达链接，不建草稿、不写任务、不写 AI 执行记录，也不提供任务状态按钮。
- 营销主题按周组织传播节奏，内容物料才是实际设计交付对象。
- Brief 是内容物料的字段与角色工作面，不另建 Brief 表。
- 审核只保留当前结果，不记录每轮修改历史。
- 审核通过即完成物料流程，不再增加提需人二次确认阶段或卡片；审核退回回到制作中，上传新终稿后重新送审。
- 内容物料跨部门对接链路的业务日期统一到“日”：提需交付 DDL、外部设计需求期望交付日期、物料催办到期日、审核业务日期、终稿交付日期和完成回执日期均只保存或展示年月日。Base 日期字段统一显示为`yyyy/MM/dd`，卡片使用`8月31日`这类业务化日期；输入带时分时忽略时分。系统自动生成的提需时间、消息/卡片发送时间、同步时间、AI 运行/审计时间和状态更新时间仍可保留时分。`04｜任务事项`的 DDL 继续按任务表自身规则处理。
- 不建发布任务表、不建独立资产表；可复用物料只在内容物料中勾选“需入中台”。
- 月度策略按“月份 × 业务线 × SKU”唯一记录；大学辅导与国际课程通常分开发、同条也兼容，只处理本条出现的业务线，缺席业务线不报错、不清空、不修改历史。每个 SKU 的四个事实字段固定为`试听价格`、`正价价格`、`新签活动`、`续费活动`；不适用价格留空，缺失活动写字面值`无`。整批写入并回读一致时，通过 `reply-in-thread` 进入原促销方案消息的“1 条回复”话题并发送`月度促销方案同步成功 | 营销战役表`；预校验失败、字段缺失、部分执行失败或回读失败时，以同样方式发送`月度促销方案同步失败 | 营销战役表`。两种回执中的“营销战役表”均为蓝色可点击链接；话题内均只保留这一条固定 Markdown，不发送卡片、不追加明细、不重复回复。
- AI 执行记录只用于业务完成后的最小留痕和异常回查，不替代业务事实，也不参与设计提需的双表成功判定；日志写入失败不得反向阻塞已经完成的双表同步。

### 设计提需当前冻结协议

设计提需支持自然语言入口，但必须能明确解析出以下 5 项：

1. **物料名称**；
2. **使用场景**：精确选择 `朋友圈`、`私信`、`其他` 之一；
3. **物料规格**：精确选择 `海报`、`单图`、`九宫格`、`六宫格`、`三宫格`、`其他` 之一；
4. **交付 DDL**：只需明确年月日，或在上下文中可唯一解析的月日；
5. **提需文档链接**：可访问的 `http://` 或 `https://` 链接。

选填项只有优先级、SKU、主题；优先级未填时默认 P1。物料大类不由用户填写，而是由使用场景确定：`朋友圈 → 营销物料`、`私信 → 常规物料`、`其他 → 其他`。设计提需的交付 DDL 只保留日期：消息带几点几分时忽略时间，只写入日期；“下班前”不再映射为 18:30，仍只取消息中明确的日期。未提供年份的月日必须能结合当前上下文唯一解析，否则按 DDL 不完整处理。主表“交付DDL”和外部表“期望交付时间”统一以`yyyy/MM/dd`显示。该日期粒度沿用到后续物料催办、审核、终稿交付与完成回执；系统运行/审计时间可保留时分，任务事项 DDL 不受影响。

任一必填项缺失、含糊或不在允许值内，机器人必须在一张黄色卡片中一次列全问题，本轮两张 Base 均零写入。5 项全部合法时，不再发送写入前预览卡，也不要求用户再次确认；原始完整消息就是本次执行依据。

完整提需的固定事务为：

```text
写入营销战役 AI 协同台并回读
→ 读取主表自动生成的“提需时间”，按 Asia/Shanghai 取创建月份（业务简称“上表月份”）
→ 精确定位外部「{M}月营销组需求表」
→ 同步需求内容、需求人、期望交付时间、相关需求物料、项目场景
→ 外部逐字段回读
→ 双表一致后发送绿色成功卡
```

外部字段映射固定为：`物料名称 → 需求内容`、`提需人 → 需求人`、`交付 DDL → 期望交付时间`、`提需文档 → 相关需求物料`、`使用场景 → 项目场景`；主表和外部表的两个日期字段都只保存日期，并统一以`yyyy/MM/dd`显示。项目场景值转换为`朋友圈 → 朋友圈`、`私信 → 私信海报`、`其他 → 其他`。文中“上表月份”只是业务简称，来源只能是主表自动生成的“提需时间”按 Asia/Shanghai 取创建月份，不是独立可写字段；不能用交付 DDL 月份替代或猜测。

建单结果严格只有三类卡片：黄色信息不完整卡、绿色需求提报完成卡、红色或橙色同步失败卡。绿色卡标题固定为`已确认 | 完成提需并同步多维表格`，唯一闸门是双表写入和回读全部成功；卡内一行展示三个等宽信息块：物料名称、类型需求（使用场景 + 物料规格）、交付 DDL，其中 DDL 只显示日期，例如`8月31日`；底部固定为`写入状态：已写入 | 查看设计提需文档`，文档文字链接到本次提需文档。没有额外设计领取卡或领取按钮。最小 AI 执行记录在业务完成后留痕，日志失败不撤销成功，也不阻止绿色卡。

如果主表已成功、外部设计需求表失败，主表记录必须保留并标记为待重试；系统只能重试尚未完成的外部同步，不得重复创建主表记录，也不得发送绿色成功卡。

## 日常使用的完成标准

一次由机器人执行的写操作只有同时满足以下条件，才算完成。任务事项不适用这条写入链，因为当前规则是 Base 手工维护、机器人只返回直达链接：

1. 当前角色和当前状态允许该动作；
2. 涉及设计提需时，主表和按“提需时间”创建月份定位的外部设计需求表均已写入；
3. 系统对所有目标表的回读结果与预期一致；
4. 卡片已更新到下一状态或完成状态；
5. 业务完成后尽力留下最小 AI 执行记录；记录失败进入异常回查，但不反向改变已经由双表写入和回读确认的成功结果。

如果卡片与多维表格不一致，以多维表格为准，并停止继续点击旧卡。

- `final-acceptance`：执行当前九表旧合同的只读最终验收；2026-08-29 最新结果为 `ok=false`、111 项检查通过、17 项失败、`external_write=false`。这反映旧合同与当前手工重构结构之间的漂移，不推翻 07 revision `112` 的定向迁移验收结论。
