# 角色深挖：管理员与同事

- 方法：AI 落地三步法「深挖」（七个差异维度、每个业务单元追六层、量结果不量代理）＋数据本体论（对象、属性、关系、状态、事件）。
- 读过的材料：`docs/PRD.md`（v1.0，235 行）；原型 `web/src/pages/Home.tsx`、`Admin.tsx`、`Team.tsx`、`AI.tsx`、`Growth.tsx`（只看结构），`web/src/data/mock.ts`、`api.ts`、`types.ts`、`components/Layout.tsx`、`main.tsx`。
- 没法访谈真人，下文的「访谈」由我扮演常浩和同事自问自答。依据只分三类：
  - **PRD 原文（第 N 行）**：`docs/PRD.md` 的行号；
  - **原型现状（文件名:行号）**：路径相对 `web/src/`；
  - **推演（待常浩确认）**：我的推断，不是事实，也没有编任何业务数据。原型里的人名、日期都是示例数据（`data/mock.ts:1` 注明虚构），引用时只当结构样例，不当业务事实。
- 演示时刻：北京时间 2026-11-05 周四 10:24，第 45 周（`data/mock.ts:10`）。

## 1. 角色画像与差异维度

### 1.1 管理员：常浩

| 项 | 内容 | 依据 |
|---|---|---|
| 身份 | 管培生培养负责人，同时是 AIBP（推公司 AI 落地） | 任务说明；原型现状（data/mock.ts:21，line 字段为 AIBP） |
| 权限 | 维护全部内容与路径模板、审核贡献、看全局数据、分配角色 | PRD 原文（第 24 行） |
| 工作量结构 | 内容一个人维护；带教人只能提建议；维护节奏未定 | PRD 原文（第 16 行、第 183 行） |
| 两顶帽子的读者 | 培养这顶帽子对管培生、带教人、公司领导负责；AIBP 这顶帽子对全公司的 AI 使用负责。两者在同一个首页上争注意力 | PRD 原文（第 15 行「对管理员，AI 赋能同样重要」）；推演（待常浩确认）：领导是汇报读者但不是工作台用户 |
| 规模 | 一期约 12 人；原型示例 6 人 | PRD 原文（第 14 行）；原型现状（data/mock.ts:12-18） |
| 一期周期 | 入职 7 天 + 通识 14 天 + 轮岗 84 天（六站×14 天）+ 定岗 75 天 = 180 天 | 原型现状（data/mock.ts:25-30）；这是示例数据，正式内容待常浩整理（PRD 原文第 186 行） |

**画像一句话（推演，待常浩确认）**：常浩不是“每天点开看一眼”的管理员，而是这套培养体系的**排期者 + 唯一编辑 + 对上汇报人**。他最怕的不是某个人某天逾期，而是“排期出问题而他没提前看到”：两个人同时挤进一个岗位、带教人那周出差、轮岗切换周没人交接、答辩那周撞上春节。现在的原型把他当成“审核员 + 看指标的人”，排期这件事几乎没有落点。

### 1.2 同事：全公司其他人

| 项 | 内容 | 依据 |
|---|---|---|
| 权限 | 浏览公开内容（AI 资产库、资料、作品集），可贡献；看不到培训私有数据；第一版可与带教人合并，但定义上单列 | PRD 原文（第 25 行） |
| 来源 | 新登录的人默认是“同事” | PRD 原文（第 29 行） |
| 规模 | 全公司版不在本期；数据结构预留“团队/部门”维度 | PRD 原文（第 14 行） |
| 三种情境 | 偶尔来逛（找 AI 资产、看作品集）；被邀请做分享会主讲；从同事转成某一站的带教人 | 任务说明；PRD 原文（第 111 行活动、第 117 行“担任分享会主讲”计分、第 29 行角色由管理员指定） |

**画像一句话（推演，待常浩确认）**：同事不是工作台的“常住用户”，而是**被链接带进来的过客**：飞书群里有人甩了一个资产链接、常浩发了分享会邀请、或者被指派带下一站。他第一次进来时要在 10 秒内知道“这里和我有什么关系、我该做什么”，而原型的同事首页只回答了“这里有什么”。

### 1.3 七个差异维度逐个过

| 维度 | 假设：这里可能有什么不同 | 证据 | 结论：真假，落在哪层 |
|---|---|---|---|
| **角色** | ① “带教人”其实是两种人：贯穿全期的主带教（导师）和只带一站的站带教。② 管理员一人身兼培养负责人和 AIBP。③ 有工作台外的读者：公司领导（看汇报）、答辩评委。④ 机器人是一个“做事的角色”（推送、收周报、出轻测）。 | PRD 第 65 行写“每个模块的带教人”，第 129 行 `user` 又有单个“带教人”字段，两处并存；原型 `types.ts:36` 每站有 mentorId，但看板和可见性只用 `user.mentorId`（`data/api.ts:186`、`pages/Team.tsx:49`） | **真，落在数据模型和规则层**：带教关系要拆成“主带教”和“站带教”两个关系，可见性规则要说清按哪个算。评委、领导是新角色，落在页面层（只读汇报或答辩页），不必进角色枚举。见 A-03、A-17。 |
| **熟练度和程度** | ① 常浩带第一期和带第三期时要的东西不同：第一期要“从零搭排期”，以后要“复用模板、对比上期”。② 新带教人（同事刚转来）和老带教人：新的要交接包和“怎么点评”的说明，老的要“别漏掉谁”。③ 同事里 AI 新手和老手：Skill 要在 Claude Code 里安装，新手用不了，只能用 Prompt。 | PRD 第 103 行 Skill 存 SKILL.md、给安装指令；原型 `pages/AI.tsx:101` 只给安装命令；`data/mock.ts:19` 示例带教人“带过三期”（虚构） | **真**。①落在**整套流程**（期次启动向导、跨期复用，见 A-02、A-13）；②落在**页面**（接任带教的交接包，A-17）；③落在**字段 + 页面**（资产加“上手难度/需要什么工具”字段，同事首页按难度推荐，A-15）。 |
| **业务线和产品** | 老师线、客户线、市场三条线的站，任务产出形式不同（录音、路演、表格），带教人按线分；全公司扩展后，部门远不止三条线。 | PRD 第 95 行岗位标签只有老师线、客户线、市场；原型 `data/mock.ts:35-40` 六站分三条线，`data/mock.ts:53-63` 产出形式有录音、路演 | **部分真**。培养内部：差异落在**字段**（模块的 line、站带教按线分配），不需要分套流程。全公司：岗位标签不够用，落在**标签维护**层，三期以后再扩（A-23）。 |
| **服务对象** | 管理员服务四类人：管培生（被培养）、带教人（被调度）、同事（AI 推广对象）、领导（汇报对象）。同事服务的对象是“自己手头的工作”，不是管培生。 | PRD 第 12 行“管培生、带教人和管理员每天都用”，没提领导；PRD 第 179 行辅助指标没有任何“对外/对上”口径 | **真，落在页面层**：管理员需要一个“汇报”视图（A-12）；同事首页要按“我的岗位/部门”推荐，而不是团队视角（A-15）。 |
| **情境** | 期初（建期次、排轮岗）、轮岗切换周、阶段末（评估）、期末（答辩）、跨期；节假日（国庆、春节）；人员异动（管培生请假/延期/离职，带教人出差/离职）；业务旺季。 | 原型示例轮岗第一站从 10-01 开始（`data/mock.ts:68`），正好是国庆假期；示例整期到 2027-03-08（`data/mock.ts:73`），横跨 2027 年春节；PRD 全文没有“请假、延期、节假日、改期”的字样 | **真，落在规则 + 页面**：排期要有工作日日历和改期记录（A-08、A-09）；人员异动要定指标分母怎么处理（A-22）。原型日期是示例，但它恰好说明“排期撞假期”在现有设计里没人会发现。 |
| **结果** | 培养的结果是“定岗成功、能独立干活、留下来”；AI 的结果是“别人真用上了、省了时间”。按时提交率、上架数、登录活跃都是代理。 | PRD 第 178-179 行主指标是“阶段产出按时提交率”，辅助指标是进度差距、上架数、周活跃；原型 `data/api.ts:200-208` 的实现把草稿提交也算按时 | **真，落在指标定义层**：主指标要改口径或配结果指标（A-05、A-06、A-18），详见第 3 节问 5–8。 |
| **现有工具** | 常浩现在手上补的东西：多维表格 `project_base`（项目、任务、成员）、会议笔记里的培养路径、带教机器人、飞书日历；轮岗排期很可能在某张表或脑子里。 | PRD 第 157 行导入 `project_base`；第 186 行路径内容散落在会议笔记；第 111 行活动日程读飞书日历 | **真，但细节要查**：多维表格里有没有“轮岗排期表”、有没有“带教人分配表”，决定一期要不要做甘特（推演，待常浩确认）。按三步法“补的就是系统缺的”，如果常浩现在用表格排轮岗，甘特就是一期必需。 |

## 2. 时间轴走查

格式：**时刻 → 要知道什么 / 要做什么 → 现在哪个页面能回答 → 缺什么**。

### 2.1 管理员

#### 一天（早上 9 点打开工作台）

| 时刻 | 要知道 / 要做 | 现在哪里能回答 | 缺什么 |

| 9:05 | 有没有带教人压着没点评（管培生交了，卡在带教人那里） | 没有。全员进度表只有“本周提交、最近评价、逾期”（`pages/Home.tsx:215`） | **待点评积压按带教人汇总**：谁手上压了几份、最久的压了几天。逾期的根源可能在带教人，不在管培生（推演，待常浩确认）。 |

| 周五 | 发公告 | 没有（二期，`components/Layout.tsx:45`） | 二期范围，可接受。 |

### 2.2 排期专题：现在在哪看、在哪改

| 排期对象 | 应该在哪看 | 应该在哪改 | 原型现状 | 数据从哪来 |
|---|---|---|---|---|
| 轮岗（谁哪天在哪站） | 成长 › 轮岗日历（全员甘特）；首页“本周换站” | 管理员在甘特上直接调，或从甘特点进个人路径 | 没有轮岗日历页；`growthTabs` 里也没有（`pages/Growth.tsx:10-14`）；只能在后台逐人改顺序，日期不能改（`pages/Admin.tsx:130-169`） | `personal_path` / `personal_module` 汇总（PRD 第 66 行、第 131 行） |

| 活动（分享会、路演、读书会） | 团队 › 活动；轮岗日历上叠一层 | 飞书日历里建，工作台补主讲、主题 | 只有一场写死的“下一场”（`data/mock.ts:186`），“加入日历”按钮无动作（`pages/Home.tsx:26`） | 飞书日历（PRD 第 111 行），但哪个日历未定 |

## 3. 自问自答记录

**问 1：工作台为什么没有日历视图？**
- 答：PRD 列了“轮岗日历”，也说了它由个人路径汇总生成，但分期表没写它属于哪期，原型按分期表做，就漏了。不是有意砍掉。
- 依据：PRD 原文（第 39 行、第 66 行、第 172 行）；原型现状（main.tsx:24-28 成长只有路径总览、我的路径、任务详情、带教看板四个路由；pages/Growth.tsx:10-14）。
- 对需求的影响：分期表补一行，明确轮岗日历的期次（推荐一期只读 + 管理员可调，见第 6 节问题 3）。

**问 2：常浩排轮岗时最怕什么？**
- 答（推演）：怕冲突看不见——同一岗位同时挤进太多人、带教人同时带太多、换站撞假期、某人延期后后面全乱。
- 依据：推演（待常浩确认）；原型示例第一站两人同在教研（data/mock.ts:83-88），说明随手排就会出现，而现有页面看不出来；国庆从 10-01 开始，示例第一站恰好从 10-01 开始（data/mock.ts:68）。
- 对需求的影响：轮岗日历至少要有“按人”和“按岗位”两种排法，并标出容量冲突和非工作日（A-01、A-09）。

**问 3：轮岗日历只看还是能改？在哪改？**
- 答（推演）：常浩是唯一编辑，最顺手的是“在甘特上看到问题就地改”，而不是看甘特、记下来、再去后台逐人改。现在后台逐人改，且日期不能改。
- 依据：PRD 原文（第 16 行一人维护）；原型现状（pages/Admin.tsx:145 只能调顺序和带教人，:154 日期来自原路径，:147 一次选一个人）。
- 对需求的影响：管理员视角下的轮岗日历就是编辑器；“个人路径分配”页降为甘特的侧栏详情。其他角色只读（A-01）。

**问 4：带教人到底是“一个人一个”还是“一站一个”？**
- 答：PRD 两种都写了，原型两种都存了，但只用了前一种。
- 依据：PRD 原文（第 65 行“每个模块的带教人”；第 109 行、第 129 行 user 有“带教人”）；原型现状（data/types.ts:36 每站 mentorId；data/api.ts:186 看板按 user.mentorId；pages/Team.tsx:49 可见性按 user.mentorId；data/mock.ts:71 示例把六站带教都设成同一人，所以示例里一位客户线带教人在带教研岗）。
- 对需求的影响：这是数据模型的矛盾，一期必须定（A-03，第 6 节问题 2）。它决定可见性规则在服务端怎么写（PRD 第 30 行）。

**问 5：主指标“按时提交率”量的是结果还是代理？**
- 答：是代理。它量的是“交没交、交得准不准时”，不量“交的东西行不行”“人有没有培养出来”。按三步法“量结果不量代理”，它适合当**周过程指标**，不适合当整期的**主指标**。
- 依据：PRD 原文（第 178 行）；deep-dig 第 3 节“量结果，不量代理”；推演（待常浩确认）：培养的结果是阶段评估达标、定岗成功、留任。
- 对需求的影响：主指标拆成两层：周看“按时达标率”（过程），期看“阶段评估达标率 + 定岗结果”（结果）（A-05、A-06，第 6 节问题 1）。

**问 6：现在的按时提交率算法有什么具体问题？**
- 答：① 所有任务都算，包括周报、轻测、月度物料，而 PRD 写的是“阶段产出”；② 截止前有任何一次提交就算按时，草稿也算——示例里有一份草稿提交（data/mock.ts:147、:154 注明草稿不算正式提交），但提交记录没有草稿标记（data/types.ts:57），算法分不出来；③ 被退回“需修改”的也算按时；④ 截止日被改过怎么算没定义。
- 依据：原型现状（data/api.ts:200-208，第 202 行取全部到期任务，第 204 行只看提交时间）；PRD 原文（第 73 行状态流转没有“草稿”，第 178 行“阶段产出”）。
- 对需求的影响：一期就要写清口径：分母 = 统计周期内截止的路径任务（不含周期任务）；分子 = 截止前正式提交且最终通过；截止日以“最初计划日”为准，改期另计（A-05）。

**问 7：12 个人一周算一次比率，数字靠得住吗？**
- 答（推演）：按示例节奏，每人一周大约一两项路径任务到期，分母可能只有十几，一项就差好几个百分点，周环比会大起大落，容易误读。
- 依据：推演（待常浩确认）；PRD 原文（第 14 行约 12 人）；原型现状（pages/Home.tsx:265 只显示百分比和环比，不显示分子分母）。
- 对需求的影响：指标旁边显示“n / N 项”；趋势用滚动四周（A-05）。

**问 8：管理员首页其他三个指标是不是代理？**
- 答：都是。“本周活跃”= 本周登录过（data/api.ts:46），登录不等于用；“本月新上架资产”量供给不量使用；“平均进度”按日历天数算的是时间过了多少，不是事情做了多少。AIBP 这顶帽子真正要的是“资产被作者以外的人用了多少、哪些部门在用”。
- 依据：原型现状（data/api.ts:46；pages/Home.tsx:268-269；pages/Team.tsx:50 timeProgress）；PRD 原文（第 179 行）；推演（待常浩确认）。

- 依据：PRD 原文（第 111 行第一版不做报名；第 117 行主讲计分）；原型现状（pages/Home.tsx:20-29 只有一张活动卡，按钮无动作；data/api.ts:256 把“下一场主讲”直接算贡献）。
- 对需求的影响：活动详情页（主题、时间、主讲、听众当前所在阶段分布、相关资产、回放）；贡献在会后确认才记（A-16）。

**问 23：同事接任带教，能看到这个人前面的点评吗？**
- 答：现在看不到（可见性只认主带教）。但不看就没法接着带。
- 依据：原型现状（pages/Team.tsx:49）；PRD 原文（第 85 行“本人、带教人和管理员”没说哪个带教人）。
- 对需求的影响：定可见性范围（第 6 节问题 2）；给站带教生成交接包（A-17）。

**问 24：同事和带教人在一期合并，会出什么问题？**
- 答（推演）：合并后，所有同事都有带教人的入口和看板，但看板是空的；反过来，接任带教的同事没有明确的“生效日”。
- 依据：PRD 原文（第 25 行第一版可合并）；原型现状（pages/Home.tsx:320 同事和带教人共用“上架资产”主按钮，但首页分开）。
- 对需求的影响：角色保持四种不合并；“带教人”由站带教关系推出（某段时间有站带教关系 = 这段时间有带教权限），不再靠手工改角色（A-03、A-17）。

## 5. 对信息架构和视图的建议

### 5.1 管理员：排期视图（轮岗日历）

- **位置**：成长 › 轮岗日历（所有角色可看，视角不同）；管理员侧栏“排期”直达。
- **形态**：甘特。横轴是周（期次开始到结束，约 26 周，标 W 编号，今天一条竖线，法定假期灰带）；纵轴按视角切换：
  - **按人**（默认）：12 行，每行是这个人的阶段和六站色块，颜色按业务线；色块上标站带教的头像；阶段末一个菱形“评估节点”，期末一个“答辩”节点。
  - **按岗位**：6 行（六站），格子里是这一周在这站的人；超过容量标红。
  - **按带教人**：每位带教人一行，格子里是这周带几人、待点评几份。
  - 叠加层（二期）：活动竖线（来自飞书日历）、任务截止密度。
- **编辑**（只有管理员）：拖动色块改日期或顺序；点色块在右侧抽屉里换站带教、顺延、写原因。每次改动生成一条改期记录，影响到的任务截止日一起预览，确认后保存。已开始的站只能顺延不能换顺序（沿用原型 pages/Admin.tsx:157 的规则）。
- **其他角色**：管培生只读，自己那行高亮；带教人只读，自己带的那几段高亮；同事只看到“谁在哪站”（进度状态公开，PRD 第 84 行）。
- 这一页取代现在的“个人路径分配”页：逐人分配变成甘特的抽屉。

### 5.2 管理员：后台按工作节奏组织

把现在平铺的四个标签（pages/Admin.tsx:10-13）改成按“什么时候用”分组：

| 分组 | 内容 | 期 |
|---|---|---|
| 期次 | 期次列表、新建期次向导（选模板版本 → 导入成员 → 设开学日 → 生成轮岗 → 分配站带教 → 甘特预览 → 发布）、成员与角色 | 一期 |
| 排期 | 轮岗日历编辑、改期记录、工作日日历 | 一期 |
| 日常 | 审核队列、逾期跟进（催办、改期、跟进记录）、公告 | 一期（公告二期） |
| 评估 | 阶段评估确认、答辩排期与材料包 | 二期 |
| 汇报 | 指标（含分子分母和口径说明）、期次对比、导出飞书文档 | 二期 |
| 设置 | 路径模板（带版本）、标签、积分规则、同步、接口密钥 | 一期起逐步 |

### 5.3 管理员：首页怎么变

现首页（pages/Home.tsx:233-296）保留骨架，调整三处：

1. **焦点卡**：从“审核队列 + 有逾期的人”改成“今天要你拍板的事”：① 审核积压；② 逾期和今明两天将到期（合并成一张，按人排）；③ 点评积压（按带教人）。超过两张时按紧急度取前两张，其余进列表。
2. **指标条**：主指标显示“按时达标率 n/N”，悬停看口径；第二格换成“计划进度差距”；“本周活跃”“本月上架”降级到 AI 区。
3. **新增“本周排期”块**（替换“连接状态”的位置，连接状态收进后台设置或只在异常时出现）：本周和下周换站的人、评估节点、活动，点进轮岗日历。
4. AIBP 那顶帽子：贡献榜换成“本月资产使用（按部门）”，更贴近 AI 落地的结果。

### 5.4 同事：入口

- **首页**按三种情境排：
  1. “你可能用得上”：按同事所在部门/岗位推荐资产，标“需要什么工具”；
  2. “你的事”：只在有时出现——被邀请主讲的活动、被指派的带教（含开始日期和交接包入口）；
  3. “最近活动”：本月分享会列表（可加入飞书日历），往期回放。
  贡献榜和“团队动态”往下放。
- **侧栏**加“活动”；被指派带教后自动出现“我的带教安排”，不需要管理员手工改角色（带教权限由带教关系的起止日推出）。
- **落地页**：从飞书链接进入资产详情时，顶部一行说明“这是管培生团队沉淀的 AI 资产，你也可以贡献”，不强迫先到首页。

## 6. 待常浩拍板的问题

**问题 1：主指标怎么定？**
- 推荐：周看“阶段产出按时达标率”（只算路径任务；截止前正式提交且最终通过；截止日按最初计划日；显示 n/N），期看“阶段评估达标率 + 定岗结果”。
- 理由：现在的按时提交率是代理，草稿和被退回的都算按时（data/api.ts:204），结论会偏乐观；三步法要求量结果。

**问题 2：带教关系按人还是按站？站带教能看到什么？**
- 推荐：两层。每站有站带教，负责这一站的点评；可另设一位主带教贯穿全期（不设时默认管理员）。站带教在带教期内能看这个人**此前所有站的点评摘要和当前站全部内容**，站结束后保留只读。
- 理由：PRD 第 65 行已经是按站，原型可见性却按人（pages/Team.tsx:49），不定下来服务端规则没法写；不让站带教看前几站，交接就断了。

**问题 3：轮岗日历放一期吗？做到什么程度？**
- 推荐：放一期，做甘特三视角（按人、按岗位、按带教人）+ 管理员就地调整 + 法定假期灰带 + 评估节点；活动叠加和任务截止密度放二期。同时取消单独的“个人路径分配”页。
- 理由：排期是管理员最核心、最高频出错的工作，现在完全没有落点；数据（个人路径）一期已经有，日历只是汇总视图，成本主要在拖拽编辑。

**问题 4：一期要不要建“期次”对象和模板版本？**
- 推荐：要。一期建 `cohort` 和模板版本号，界面只做最简的新建期次向导；期次对比、跨期回看放三期。
- 理由：现在期次只是 `team` 上的一个字段（PRD 第 128 行），一旦一期数据按“没有期次”存进去，第二期开始时要迁移；模型先立起来成本很低。

**问题 5：活动日程从哪读，主讲贡献怎么记？**
- 推荐：建一个共享的“管培生活动”飞书日历，工作台只读这个日历；主讲、主题、关联资产在工作台补录；活动结束并挂上妙记链接后，管理员确认一次，才记主讲贡献。
- 理由：PRD 第 111 行只说“读飞书日历”，没说哪个；飞书日程本身没有“主讲”字段；原型现在把“将要主讲”直接算成贡献（data/api.ts:256），与“只奖励对团队的贡献”的原则（PRD 第 117 行）不一致。
