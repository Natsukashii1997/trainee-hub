# 角色走查：带教人

- 方法：AI 落地三步法·深挖（七个差异维度、业务单元追六层、量结果不量代理）+ 数据本体论（对象 → 事件 → 规则 → 待办 → 呈现 → 写回）。
- 读过的材料：`docs/PRD.md`（v1.0）；原型 `web/src/pages/Home.tsx`、`Growth.tsx`、`Admin.tsx`、`Team.tsx`，`web/src/data/mock.ts`、`api.ts`、`types.ts`。
- 依据只分三类：**PRD 原文（第 N 行）**、**原型现状（文件:行号）**、**推演（待常浩确认）**。没访谈过真人带教，凡是"带教人会这样做"的判断都是推演。
- 旁证说明：带教机器人项目（`~/Documents/AI 项目/outputs/管培生带教-AI协同/`）里有已定的业务共识。引用时一律标成「推演（待常浩确认）」，并注明旁证出处，不算本项目的事实。其中一条要先知道：机器人项目记录的现状是"导师为常浩"、管培生 2 人（`CONTEXT.md` 第 31 行）。也就是说，**"每站一位带教人"这种分工还没有真人跑过**，下面关于站带教的判断全部是推演。
- 原型里的人名、日期、提交时间都是示例数据（`mock.ts` 第 1 行），只用来说明结构，不当业务数据。

## 1. 角色画像与差异维度

### 1.1 一句话画像（推演）

带教人是业务线上的骨干或负责人，本职工作排第一。轮岗期他**只负责一站，约两周**，同时带 1–3 位管培生。按"约 12 人一期、六站"（PRD 第 14 行，`mock.ts:28`）推算：只要每位管培生六站都轮一遍，**每位站带教在 12 周轮岗期里会先后带完全部约 12 人，每两周换一批，每批约 2 人**。所以他面对的不是"带固定几个人走完全程"，而是"一条一直在流动的队列"：上一批刚交接出去，这一批正在带，下一批快要来了。这三种状态会同时出现。

### 1.2 七个差异维度

| 维度 | 假设：这里可能有什么不同 | 证据 | 结论：落在哪一层 |
|---|---|---|---|
| **角色** | "带教人"至少有四种：①**站带教**（只带一站）；②**线负责人**（可能兼管同一条线的两站，比如客服和销售都属客户线）；③**全程或阶段带教**（入职、通识、定岗三段谁带，PRD 没写）；④**跟岗师傅**（推演：线负责人很可能把日常跟岗交给一线员工，自己只做点评）。另外管理员也能点评（`api.ts:167`）。 | PRD 第 65、131 行：带教人按模块挂。原型却是一人一个固定带教（`mock.ts:70-79` 所有模块都用同一个 `mentorId`；`api.ts:41-44`、`186`）。`mock.ts:19` 周颖是"客户线负责人"，技能写的是客服管理和销售 | **数据关系 + 规则**。带教关系以 `personal_module.mentor` 为唯一来源；同一个人能不能挂多站要拍板（见第 6 节 Q1）。跟岗师傅一期不建角色，只在带教安排里写名字（推演） |
| **熟练度** | 第一次带的人缺的是"标准"：达标长什么样、两周要安排哪些事、评语怎么写。带过多期的人缺的是"效率和不漏人"：批量处理、跨期对比，交接周别漏了尾巴任务 | 原型点评区只有一句占位提示（`Growth.tsx:174`）和任务要求列表（`Growth.tsx:156`），没有三档样例。`mock.ts:19` 周颖带过三期，`mock.ts:20` 吴桐没写带教经历 | **页面 + 内容**。新手：任务模板附三档样例和"本站带教清单"。老手：看板批量操作、历史期次（依赖 PRD 第 157 行的历史导入）。都不需要另做一套流程 |
| **业务线和产品** | 三条线的产出和点评方式不一样。客户线：录音、跟单（`mock.ts:56`、`58`），点评要听录音，可能涉及客户隐私。老师线：试讲（`mock.ts:53`），要先约到真实课堂，点评多半是现场看。市场线：选题、推文、投放数据（`mock.ts:60-62`），要开账号权限。各线忙闲时段也不同（推演：教育行业晚上和周末是上课、接家长电话的高峰） | 原型对所有线一视同仁，产出只存飞书链接（PRD 第 72 行） | **字段 + 规则**。任务模板加"点评方式"（看文档、听录音、现场观察）和"开站前要准备的权限"；不用分线做流程。录音的隐私问题要单独确认（推演） |
| **服务对象** | 管培生有强有弱。另外，**这个人以后会不会定岗到我这条线**会改变带教投入（推演：线负责人想把好苗子留在本线） | PRD 第 64 行有定岗阶段，没写定岗怎么匹配。原型没有相关字段 | **字段（待定）**。站评里要不要加"是否推荐定岗到本线"，二期和考核一起定 |
| **情境** | ①三种在带状态：本站正在带、刚交接出去（还有尾巴任务没评）、下一站要接；②所有人同一天换站，交接集中在同一天（`mock.ts:68-69` 所有人共用同一组换站日期）；③本职高峰期、出差、请假要人代带；④临时让管培生顶业务，原来的截止日期就不合理了；⑤带教空窗期（两批之间没人可带） | 原型首页只认"当前在带"（`api.ts:186`，按 `u.mentorId` 过滤）。PRD 没有延期，也没有代理带教 | **规则 + 页面**。首页和看板按三种状态分组（第 5 节），延期和代理带教补规则 |
| **结果** | 带教做成了，看的是：①点评**及时**，并且**让产出变好**（需修改后再交通过了）；②交接要点被下一站**用上**；③站评能支撑阶段评估和定岗。**不能**拿点评条数、登录次数、评语字数来代替 | PRD 第 178 行的主指标"按时提交率"管的是管培生这一侧，带教这一侧没有结果指标。旁证：机器人共识强调"不以系统活动量代替"（业务共识第 154 行） | **指标**。带教侧加两个结果量：点评时效达标率、需修改后再交的通过率；"交接要点已读"只当辅助（第 3 节 Q22） |
| **现有工具** | 推演：带教人现在大概率是①**直接在飞书文档里写批注**；②用飞书日历约 1:1 和跟岗；③在聊天里催进度；④多维表格 `project_base` 记项目（PRD 第 157 行）。工作台的点评如果要求把批注再抄一遍，就会被绕开 | PRD 第 72 行：产出只存链接。原型点评是独立的文字加三档（`Growth.tsx:171-178`） | **规则**。工作台里的点评定位成"三档 + 总评，详见文档批注"，不重复录入。日程留在飞书，工作台只读不存 |

### 1.3 七个差异各落在哪一层

- **整套流程层**：没有。三条线、新手老手都走同一条"接人 → 带 → 评 → 交接"流程，不同点放进字段和规则就够了（推演）。
- **数据关系层**：带教关系按站挂（这一条最根本）；跨站可见性；交接要点和站评是新对象。
- **规则层**：点评时效、尾巴任务归谁评、周期任务评不评、延期、代理带教。
- **页面层**：首页按三种在带状态重排；带教日历；看板加站内进度。

## 3. 自问自答记录

> 依据格式：〔PRD〕= PRD 原文；〔原型〕= 原型现状；〔推演〕= 推演（待常浩确认）。

**Q1 带教人和管培生是"一人一位固定带教"，还是"每站一位带教"？**
- 答：PRD 定的是每站一位：个人路径带"每个模块的带教人"。原型实际是一人一位固定带教，换带教时整人转走。PRD 自己也前后不一：`user` 表有"带教人"字段，任务字段里也有"带教人"，但 `task_instance` 的关键字段里没有。
- 依据：〔PRD〕第 65、131 行（按模块）；第 109、129 行（`user` 表有带教人）；第 70 行和第 132 行（任务字段不一致）。〔原型〕`mock.ts:70-79`、`api.ts:41-44`（`setMentor` 改整个人）、`api.ts:107-112`（`assignRotation` 改每站，但看板和任务不跟着改）、`Admin.tsx:70` 和 `Admin.tsx:145-156`（后台两处都能改带教人，互相打架）。
- 对需求的影响：**带教关系只有一个来源：`personal_module.mentor`**。`user.带教人` 改成派生字段（取当前所在站的带教人），或者干脆删掉。任务的带教人在任务生成时按所属站固定下来。看板、待点评和可见性都按这条关系重写。

**Q2 原型里周颖带赵一然合理吗？**
- 答：不合理。示例中赵一然本站在内容岗（市场线），带教却是客户线负责人周颖；陈默在投放岗，带教是老师线的吴桐。周颖还点评了林夏的行研和教研岗产出。演示会让人以为一位带教带全程。
- 依据：〔原型〕`mock.ts:15`、`19`、`85`（赵一然第三站是 m-nr）；`mock.ts:16`、`20`、`86`；`mock.ts:157-159`（周颖点评了 tt-2、tt-4、tt-6）。
- 对需求的影响：示例数据按"每站一位带教"重排，补一位市场线带教和一位第一次带教的人，这样新手、老手两种首页都能演示。

**Q3 我一周大概要评多少份？**
- 答：路径任务约每人每站 2–3 份，2 人一批，两周约 4–6 份，加上返工。真正决定工作量的是周期任务要不要评：日报如果也要评，量会翻好几倍。
- 依据：〔原型〕`mock.ts:56-64`（每站 2–3 个任务模板）；`mock.ts:126` 和 `api.ts:176-182`（周报进了待点评）。〔PRD〕第 71、73 行。〔推演〕具体数字。
- 对需求的影响：定下"哪些任务类型要带教人评"（第 6 节 Q4）。待点评队列只放要评的类型。

**Q4 点评多久算晚？**
- 答：PRD 没写。原型显示"已等待 N 天"，但没有阈值；示例里有一份 10-24 交的产出 11-03 才评（只是示例）。推演：2 个工作日。
- 依据：〔原型〕`Home.tsx:173`；`mock.ts:145`、`159`。〔推演〕阈值。
- 对需求的影响：新增规则"点评时效"（阈值由业务定），超时才进首页焦点并提醒；待点评按"离超时还有多久"排序，不按"先到先评"（`Growth.tsx:226`）。

**Q5 管培生交了以后，我怎么知道？**
- 答：原型的提示语说带教人会收到飞书提醒，但 PRD 一期接口只让机器人读"即将到期和已逾期的任务"，没有"新提交"或"待点评"。
- 依据：〔原型〕`Growth.tsx:129`。〔PRD〕第 153-155 行。
- 对需求的影响：机器人接口加"带教人待点评（含已等待时长）"的读接口，或者由工作台发事件。提醒卡片直接链到 `/growth/tasks/:id`，点开就落在点评表单。

**Q6 能不能在飞书卡片里直接点评？**
- 答：推演：一期不做，卡片只负责跳转；二期再看能不能做"三档 + 一句话"的轻点评。写接口里没有点评（PRD 第 155 行）。另外，机器人共识明确"专业成果评阅"不是机器人的职能，点评必须由人做，但入口可以放在飞书里。
- 依据：〔PRD〕第 150、155 行。〔推演〕旁证：业务共识第 13 行。
- 对需求的影响：一期提醒卡片只带深链。二期如果做卡片点评，写接口要加 `review`，并限制只能由本人（带教人）提交。

**Q7 管培生交上来的飞书文档我打不开怎么办？**
- 答：推演：这会是最常见的卡点。工作台只存链接，权限由飞书判断，原型只校验了链接格式。
- 依据：〔PRD〕第 72、90 行。〔原型〕`api.ts:157-158`。〔推演〕常见程度。
- 对需求的影响：提交时提示"请确认已分享给带教人 XX"；二期可以考虑用飞书接口检查权限，打不开就不让提交，或者自动提示管培生去开权限。

**Q8 我习惯在飞书文档里直接写批注，工作台还要再写一遍评语吗？**
- 答：推演：要求再写一遍会被绕开。工作台的评语定位成"三档 + 一两句总评"，细节留在文档批注里。
- 依据：〔原型〕`Growth.tsx:174`（占位提示要求"写具体"）。〔推演〕现有习惯。
- 对需求的影响：评语只要求写总评，不设字数下限；占位提示改成"一两句总评，细节可以写在文档批注里"。

**Q9 需修改后再交，我能一眼看出改了什么吗？**
- 答：原型的时间线把多次提交和点评按时间排在一起，但没有把"上次评语"和"这次说明"并排；点评时默认针对最新一次提交。
- 依据：〔原型〕`Growth.tsx:138-141`、`179-185`；`api.ts:166-170`。〔PRD〕第 133 行（提交带版本）。
- 对需求的影响：再交时，点评区顶部固定显示"上次你的评语 / 这次管培生的修改说明"；管培生再交时必须写修改说明。

**Q10 下一站谁来、哪天来，我怎么知道？**
- 答：原型不知道。看板只列当前在带的人。
- 依据：〔原型〕`api.ts:185-186`；`Growth.tsx:13`（带教人的页签里没有轮岗日历）。〔PRD〕第 39、66 行（轮岗日历由个人路径汇总）。
- 对需求的影响：首页和看板加"即将到站"分组；开站前 N 天由机器人推一条"下周 XX 到你这站"（N 由业务定，推荐 5 个工作日）。

**Q11 我能看到他上一站的点评和交接要点吗？**
- 答：按 PRD 的字面意思（产出、点评、考核"只给本人、带教人和管理员"），"带教人"指谁不清楚。原型的可见性只认任务上的带教人，按站分配以后，下一站带教看不到上一站的点评，交接出去的带教连这个人的档案都看不到了。
- 依据：〔PRD〕第 58、85 行。〔原型〕`api.ts:147`、`types.ts:92-94`、`Team.tsx:49`。
- 对需求的影响：重新定义可见性（第 6 节 Q2），并且由服务端执行（PRD 第 29 行）。

**Q12 本站最后一份小结在站末当天截止，交接后谁评？**
- 答：原型改带教时会把所有没通过的任务转给新带教，新带教不了解这一站。推演：应该由原站带教评。
- 依据：〔原型〕`mock.ts:113` 和 `69`（截止时间正好是站结束时间）；`api.ts:43`。
- 对需求的影响：规则"任务的带教人 = 任务所属站的带教人，生成时固定，换站不转"。站末尾巴任务（含需修改后再交）仍归原站带教，并给他设一个兜底时限（比如站后 3 个工作日），超时由管理员接手。

**Q13 轮岗阶段的阶段评估谁来填？**
- 答：轮岗阶段 84 天、6 位带教。PRD 说"每阶段结束时带教人填写"，到轮岗这里落不了地。
- 依据：〔PRD〕第 79 行。〔原型〕`mock.ts:28`。
- 对需求的影响：增加"站评"（每站结束由本站带教填：三档 + 评语 + 交接要点）。轮岗阶段评估由管理员根据 6 份站评汇总确认（第 6 节 Q3）。

**Q14 跟岗、陪访、1:1、试讲观察，在工作台里算什么？**
- 答：PRD 里都没有。原型的首页"本周带教安排"是写死的示例，并标了"二期接飞书日历"。
- 依据：〔原型〕`mock.ts:188-193`；`Home.tsx:196-199`。〔PRD〕第 111 行（只有团队活动读飞书日历）。
- 对需求的影响：定义"带教日程"：工作台**只读**飞书日历里和带教有关的日程，不存日程本体。怎么判断"和带教有关"见 Q16。

**Q15 排 1:1 和本职会议冲突怎么办？**
- 答：推演：带教人不会为了工作台换掉自己的日历工具。工作台能帮的是：在带教日历上同时显示"带教日程"和"本职占用的时段（只显示忙或闲）"，再一键跳到飞书去建日程。
- 依据：〔推演〕。
- 对需求的影响：二期。要用飞书日历的忙闲查询，涉及授权。工作台不做排期引擎。

**Q16 读我的飞书日历，会不会把我的私人会议暴露出来？**
- 答：推演：会有这个担心。只读两类：①参会人里有我所带管培生的日程；②团队活动（PRD 第 111 行）。其他时段只拿"忙或闲"，不拿标题。
- 依据：〔PRD〕第 28-29 行（可见性在服务端执行）。〔推演〕读取范围。
- 对需求的影响：写进数据边界：带教日程只给带教人本人和对应的管培生看，不给其他同事看。

**Q17 客户线负责人会不会同时带客服、销售两站？**
- 答：示例里周颖是"客户线负责人"，技能写客服管理和销售，看起来像一个人管两站。真是这样的话，他同时在带的人数可能超过 3 人，而且同一个管培生可能连着两站都由他带（比如林夏客服之后正好是销售，`mock.ts:83`）。
- 依据：〔原型〕`mock.ts:19`、`37-38`、`83`。〔推演〕人数推算。
- 对需求的影响：数据上允许同一位带教挂多站；连续两站同一人时，可以省掉交接要点（第 6 节 Q1）。

**Q18 跟岗其实是一线员工在带，不是我，那怎么办？**
- 答：推演：线负责人很可能把日常跟岗交给一线员工，自己只负责点评和站评。
- 依据：〔推演〕。
- 对需求的影响：一期不建"跟岗师傅"角色，在带教日程里写名字就行。如果以后要让跟岗师傅也写观察记录，再按"同事 + 受限可见"单独定。

**Q19 我第一次带教，不知道"达标"是什么标准。**
- 答：原型只有任务要求列表和一句占位提示，没有样例。
- 依据：〔PRD〕第 70 行（要求即标准）、第 74 行（三档）、第 86 行（优秀产出进作品集）。〔原型〕`Growth.tsx:156`、`174`。
- 对需求的影响：任务模板加"三档说明"（各一句话），作品集里的优秀产出挂到对应任务做样例（二期，和作品集一起上）。首页给第一次带教的人一份"本站带教清单"：开站要做什么、每周做什么、站末要写什么。

**Q20 带过三期的老手要什么？**
- 答：推演：①交接周的"别漏"清单；②一屏看完所有人的待办；③跨期对比和复用自己写过的评语。
- 依据：〔原型〕`mock.ts:19`。〔PRD〕第 128、157 行（期次、历史导入）。〔推演〕需求本身。
- 对需求的影响：①②放一期（看板分组、本周带教清单）；③放三期以后。

**Q21 有人逾期，我点"飞书提醒"会发生什么？**
- 答：现在什么也不会发生。PRD 也没有"带教人催办"的接口；而且机器人本来就会提醒到期和逾期，两边一起催会重复打扰。
- 依据：〔原型〕`Home.tsx:181`。〔PRD〕第 154 行。
- 对需求的影响：定义"催办"：由带教人发起，通过机器人发给管培生，附带教人的一句话，留下记录；同一任务 24 小时内只能催一次（推演）。另外加一个"问原因"选项，有些逾期是带教人自己临时安排业务造成的。

**Q22 怎么量"带教做得好不好"？**
- 答：量结果，不量代理。结果是：①超过点评时效阈值之前评完的比例；②需修改后再交并通过的比例（看点评有没有让产出变好）；③站评按时写完的比例。不要用点评条数、评语字数、登录次数。"交接要点被下一站打开过"只能当辅助，它是代理指标，打开了不等于用上了。
- 依据：〔PRD〕第 178 行（主指标只有管培生这一侧）。〔推演〕旁证：业务共识第 11、154 行。
- 对需求的影响：管理员看的指标里增加"带教侧"一组，但不做带教人排行（推演：带教是兼职，排行会伤积极性）。

**Q23 临时让管培生去顶业务缺口，截止要顺延吗？**
- 答：PRD 没有延期。按时提交率是主指标，这样会把带教人的临时安排算成管培生逾期。
- 依据：〔PRD〕第 73、178 行。〔推演〕场景。
- 对需求的影响：带教人可以改自己这一站任务的截止时间，必须写原因，留痕，管理员能看到；主指标按调整后的截止时间算，同时单独统计"调整过截止的任务数"。

**Q24 轻测是谁出题？**
- 答：PRD 说机器人出题；原型写"带教人出题"，还放了一个"轻测出题截止"日程。旁证：机器人共识是机器人整理题目、集中审核，每周 2–3 道选择题。
- 依据：〔PRD〕第 78 行。〔原型〕`mock.ts:114`、`122`、`191`。〔推演〕旁证：业务共识第 97-108 行。
- 对需求的影响：以 PRD 为准，改掉原型里的说法。站带教要不要参与审题（各站专业题），二期和考核一起定。

**Q25 带教人首页顶上"本期带教 N 人"，到了交接周怎么算？**
- 答：原型取的是当前在带的人数。交接周同时有要走的和要来的，一个数字说不清。
- 依据：〔原型〕`Home.tsx:166`。
- 对需求的影响：首页标题改成按状态说："在带 2 人 · 下周四到站 2 人 · 上一站还有 1 份未评"。

**Q26 我能对本站的任务提建议吗（比如这周客服系统切换，改成实地跟岗）？**
- 答：PRD 说带教人可以提建议，但原型没有入口。
- 依据：〔PRD〕第 16 行。〔原型〕`Growth.tsx:153-157`（任务详情只有要求展示）。
- 对需求的影响：任务详情和路径总览加"对这个任务提建议"，进入管理员审核队列。低优先级，放二期。

**Q27 我请假或出差两周怎么办？**
- 答：PRD 没有代理带教。原型的后台只能直接换人，而且换人会把未完成的任务一起转走（`api.ts:43`）。
- 依据：〔原型〕`api.ts:41-44`、`Admin.tsx:70`。〔推演〕场景。
- 对需求的影响：二期加"代理带教"：设一个时间段，期间代理人能点评、能看本站相关内容，原带教的归属不变。

**Q28 我想把这站表现好的人要到我们线定岗，站评里能体现吗？**
- 答：推演：线负责人会有这个动机。站评要不要加"是否推荐定岗到本线"，会影响定岗的公平性和可见性。
- 依据：〔PRD〕第 64 行（定岗阶段）。〔推演〕。
- 对需求的影响：二期和考核一起决定。即使加，这个字段也只给管理员看，管培生本人和其他带教都看不到。

## 4. 需求缺口清单

严重度：**高** = 不补的话带教这条线跑不通，或者数据关系是错的；**中** = 能用，但会被绕开，或者数据失真；**低** = 体验和效率问题。

| 编号 | 缺口 | 严重度 | 建议期次 | 依据 |
|---|---|---|---|---|

## 5. 对信息架构和视图的建议

### 5.1 带教人的首页：从"待点评数"改成"三种状态 + 今天"

现在的首页（`Home.tsx:155-209`）结构是：一句话（N 份待点评）→ 两个焦点（等得最久、逾期）→ 看板、待点评、本周安排、我的资产、动态。问题是只认"当前在带"，而且没有时间维度。建议：

1. **标题按状态说**：「周颖，在带 2 人 · 下周四到站 2 人 · 上一站还有 1 份没评」。
2. **焦点条换成三类，按紧急程度排**：
   - 快超时或已超时的待点评（显示还剩多少小时，超时变红）；
   - **下一个换站节点**（如「11-11 林夏、许诺离站 · 交接要点待写」或「11-12 赵一然到站 · 上一站要点已就绪」）；
   - 需要跟进的逾期（带"催办"和"问原因"两个动作）。
3. **"今天"一栏**（替代"本周带教安排"）：一条当天时间线，按时间放带教日程、我的人的截止时间、团队活动。一期只放截止时间和团队活动，二期接飞书带教日程，本职占用的时段画成灰色"忙"块。
4. **看板改成三组**：本站在带 / 即将到站 / 刚交接出去（还有没做完的事）。没做完的事都清掉以后，"刚交接出去"这组自动消失。
5. **第一次带教的人**多一张"本站带教清单"（开站、每周、站末），老手可以收起。
6. "我贡献的资产"和"团队动态"下移，不占首屏（PRD 第 51 行原来就把它们排在后面）。

### 5.2 带教日历（成长 → 轮岗日历，带教人默认"只看我这一站"）

PRD 的轮岗日历（第 39、66 行）由个人路径汇总生成。建议做成一个视图、两种切换：

- **轮岗视图（甘特，一期）**：一行一位管培生，横轴是周；每段按线着色（客户、老师、市场）；**落在我这一站的那几段高亮**，过去的变浅，未来的描边。段上标点：任务截止、提交、点评；站末标"交接要点"状态（已写 / 未写）。顶部标出换站日，让人一眼看出"所有人同一天换站"这种交接高峰。
- **周视图（二期）**：七列日程表，叠三层：①带教日程（从飞书读，跟岗、1:1、陪访、试讲）；②我的人的截止时间；③团队活动（分享会、路演、答辩，PRD 第 111 行）。本职日程只画"忙"块，不显示标题。点空白处 → 跳到飞书建日程，参会人自动带上这位管培生。
- 管理员用同一个视图，默认看全员；管培生只能看到自己那一行。

### 5.3 多人视图（带教看板）

现在的列：管培生、当前岗位、本周提交、最近评价、状态（`Home.tsx:215`）。建议改成：

| 列 | 说明 |
|---|---|
| 管培生 | 头像、姓名、所在分组（在带 / 将到 / 刚走） |
| 本站进度 | 第 N 天 / 14 天，本站任务完成 x / y |
| 待我做 | 待评几份（最久的等了多久）、待写交接要点、待 1:1 |
| 最近评价 | 本站最近一次三档 |
| 上一站要点 | 有 / 无，悬停显示前 3 条 |
| 下次见面 | 下次 1:1 或跟岗的时间（二期） |
| 状态 | 逾期、延期过、正常 |

### 5.4 个人档案和任务详情（带教人看到的部分）

- 档案顶部加一张**"交接卡"**：历次站评（三档 + 一句话）和最近一站的交接要点。按 Q2 拍板的可见性规则展示。
- 任务详情侧栏加"这个人上一站的评价摘要"；再交时在点评区顶部并排显示上次评语和修改说明（M-13）。

### 5.5 本体补充（给第二步技术方案用，草案）

| 类别 | 新增或修改 |
|---|---|

## 6. 待常浩拍板的问题

**Q1 带教关系按什么粒度挂？**
- 推荐：**按站挂（`personal_module.mentor` 唯一来源），允许同一人挂多站**（例如客户线负责人兼客服、销售两站）。`user` 表上的"带教人"改成派生值（当前所在站的带教）。入职、通识两段默认由管理员带；定岗带教单独指定。
- 理由：PRD 本来就是按模块挂的（第 65、131 行），只是 `user` 表和原型没跟上。按站挂是交接、可见性、日历的前提，不先定，后面的规则都没法写。

**Q2 跨站可见性：一位管培生的历史产出和点评，哪些带教人能看？**
- 推荐：**本人路径上所有站的带教人都能只读查看他的全部产出和点评**：下一站带教从开站前 5 个工作日起能看，交接出去的带教继续保留只读。点评只能由写的人修改。考核（站评三档、阶段评估）只给本站带教、管理员和本人。
- 理由：交接的价值就在于下一站能看到上一站，只给"交接要点"信息太薄。管培生全程都在同一个培养体系里，对路径上的带教公开，比对全体同事公开风险小得多。备选：只看交接要点，不看历史点评（更保守，但交接质量全靠上一站写得好不好）。

**Q3 要不要新增"站评 + 交接要点"，轮岗阶段评估怎么出？**
- 推荐：**要**。每站结束由本站带教在站后 2 个工作日内写：交接要点（最多 3 条，一期就上）+ 站评三档和评语（二期和考核一起上）。轮岗阶段评估由管理员根据 6 份站评汇总确认，不再要某一位带教单独填。
- 理由：PRD 第 79 行"阶段结束带教人填"在轮岗阶段找不到这个"带教人"。站评同时也是交接材料和定岗依据，一份东西用三处。

**Q4 点评的范围和时效怎么定？**
- 推荐：**站带教只评路径任务**，时效 2 个工作日（超时提醒带教人，超时 3 个工作日抄送管理员）。周报、日报只读不评，带教人在 1:1 准备里能看到。月度物料沿用现在的做法，由管理员确认。轻测由机器人判。
- 理由：周期任务如果都要站带教评，工作量会翻几倍，带教人是兼职，会直接放弃工作台。机器人项目已经定了周期任务由常浩确认（旁证：业务共识第 111-126 行）。2 个工作日是推演值，请按实际情况调。

**Q5 带教日历一期做到哪一步？**
- 推荐：**一期只做"轮岗日历"（甘特，由个人路径生成，带教人默认只看自己这一站）+ 首页"今天"一栏里的截止时间**，不接飞书日历。二期再读飞书日历：只读参会人包含所带管培生的日程和团队活动，本职时段只取忙闲，不取标题。
- 理由：轮岗日历不依赖任何外部授权，PRD 第 66 行已经说明能直接生成，补上就回答了"为什么没有日历"。读飞书日历牵涉授权和隐私（带教人的本职日程），放二期和团队活动（PRD 第 111 行）一起做，接口只接一次。
