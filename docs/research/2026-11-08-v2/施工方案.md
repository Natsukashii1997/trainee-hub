## 0. 一句话

先把工作台的骨架搭完整：有哪些对象、对象归谁、和谁关联、在哪个页面、能做哪些业务动作，每个动作之后**记下了什么事实**。至于这些事**什么时候自动发生**（提醒、超时、升级、自动待办），**谁能看**（权限范围、历史权限），**怎么统计**（指标口径），放到第二轮集中定。骨架期只用示例数据，演示环境和正式环境明确隔离。

## 1. 需求理解

**常浩原话（2026-11-08）：**
- 关于带教权限，起码初始版本不用纠结，也不用卡这么严。目前严格来说只有我一位带教，所以不管是带教还是管理员，权限都是无限大的，我要看到所有信息。
- 重点是先把工作台的底层逻辑、结构框架、UI 等等梳理清楚，先把这个壳搭起来。
- 运行规则，我更倾向于在完整机制已经足够清晰的基础上，再磨第二轮，然后让它真正有门径、有限制地流转起来。
- 先把完整的底层架构迅速优化、确认，然后对 UI 等框架内容做一轮优化，再去磨细节。

**我的理解：**

| 原话 | 背后的真实诉求 | 方案里怎么落 |
|---|---|---|
| 权限不用卡，我看所有信息 | 现在只有一位带教，权限规则没有真实场景可以验证，现在推演只会拖慢进度 | 骨架期带教 = 管理者，能看、能改全部内容。这种宽松权限是**演示环境的明确特例**，不散落在业务代码里（第 6 节） |
| 先把壳搭起来 | 先看到、点到完整的产品形态，再判断规则怎么定 | 四个工作域和管理区全部呈现；按 A/B/C 分级，只有核心闭环页接真实接口，避免把尚未验证的模块提前做死（第 7 节） |
| 机制清晰后再磨第二轮 | 规则长在骨架上；但「发生了什么、怎么记」本身就是骨架的一部分 | 三层划分：现在定结构和最小业务契约，第二轮定精细运行规则（第 3 节） |
| 先架构，再 UI，再细节 | 每层确认后再进下一层，不来回返工 | 4 步施工，每步有独立的验收标准（第 8 节） |

## 2. 路径变化

| | 原路径（PRD v2.0 第 17 节） | 新路径 |
|---|---|---|
| 切分方式 | 按业务能力切：阶段 1 最小闭环（含规则）→ 阶段 2 轮岗协同 → 阶段 3 知识 → 阶段 4 运营 | 按层切：骨架与最小业务契约 → 核心后端 → UI 框架 → 精细规则与试点 |
| 范围 | 阶段 1 只做闭环相关页面，规则做足 | 全部页面呈现（A 级接真实接口，B 级是可交互原型，C 级只保留位置）；精细规则不做 |
| 权限 | 两个角色 + 管理权限开关 + 可见性表 | 演示环境下带教看、改全部；保留统一授权入口和管理权限字段，不做权限配置界面；可见性表进第二轮 |
| 真实试点 | 阶段 1 结束就试点 | 第二轮规则、飞书登录和服务端对象级权限都做完后才开始试点 |

不变的部分：产品定位、三条线、两个角色、四个工作域、项目与培养任务分开建模、成果只交一次、两级反馈、能力证据用 4+1 主线、V3 柔光视觉、机器人不作为前提。

## 3. 三层划分

**判定标准：现在可以不规定「什么时候自动发生、谁能看、怎么统计」，但必须规定「有什么、发生了什么、怎么记」。**

| 层 | 管什么 | 什么时候做 |
|---|---|---|
| 一、结构骨架 | 有哪些对象、对象归谁、和谁关联；页面、导航、基本操作入口 | 现在完整设计 |
| 二、最小业务契约 | 每个业务动作的含义；状态边界（哪些状态是不同的事实）；责任归属（现在由谁负责）；数据关联与写入约束 | 现在必须明确，但不做复杂的自动化 |
| 三、精细运行规则 | 权限范围、时间计算、超时升级、提醒频率、自动待办、统计口径 | 第二轮集中设计和实现 |

**示例：**

| 问题 | 所属层 | 现在就定吗 |
|---|---|---|
| 有项目、节点、成果三个对象 | 结构骨架 | 是 |
| 一份成果能关联多个培养任务 | 结构骨架 | 是 |
| 培养任务的「已通过」必须来自一条有效的认定记录 | 最小业务契约 | 是 |
| 「已提交、待评审」和「已通过」是不同状态 | 最小业务契约 | 是 |
| 带教已响应受阻和问题已解决是两件事 | 最小业务契约 | 是 |
| 带教关系和评审负责人怎么关联 | 最小业务契约 | 是 |
| 谁有权认定培养任务达标 | 精细运行规则 | 第二轮 |
| 提交后几个工作日内必须评审 | 精细运行规则 | 第二轮 |
| 受阻超过多久升级提醒 | 精细运行规则 | 第二轮 |
| 离任带教能查看哪些历史记录 | 精细运行规则 | 第二轮 |

## 4. 最小业务契约：骨架期的业务命令

骨架期所有写入都通过下面这些**业务命令**完成。每条命令在同一个事务里更新相关对象，并写一条事件日志（只追加）。业务界面上**没有**「任意改状态」的入口；本机调试需要时，用开发工具里单独的状态调试功能，与正式业务接口分开。

| 命令 | 谁发起（骨架期） | 记下的事实 | 状态变化 |
|---|---|---|---|
| 创建项目 | 管培生或带教 | 项目（目标、主责与参与管培生、验收条件） | → 草拟 |
| 确认立项 | 带教 | 确认人、确认时间 | 草拟 → 推进中 |
| 新建关键节点 | 项目成员或带教 | 节点（目标、验收标准、原截止） | → 未开始 |
| 提交成果 | 管培生 | 新的成果版本（不可修改）；评审负责人快照 | 节点或任务 → 待评审 |
| 评审 | 评审负责人 | 评审记录（三档、短评；关键节点另有关键问题、带教判断）；下一步行动（可多条）；成果对培养任务的认定记录（可选） | 通过 → 已通过；需修改 → 需修改。已通过只能由一条评审记录产生 |
| 修改再交 | 管培生 | 新版本，关联上一版的评审；关闭对应的「修改再交」类下一步行动 | 需修改 → 待评审 |
| 标记受阻 | 项目成员或带教 | 受阻记录（原因、需要谁决定、当前处理责任人） | 节点带受阻标记，原状态不变 |
| 响应受阻 | 带教 | 响应内容、响应人、响应时间 | 不解除受阻 |
| 解除受阻 | 项目成员或带教 | 解除人、时间、说明 | 去掉受阻标记 |
| 项目结项 | 主责管培生填写，带教确认 | 项目结论：交付结论 + 业务验证四个字段（第 5 节） | 推进中 → 已结束（完成 / 中止） |
| 提炼或确认能力证据 | 带教 | 能力证据（来源对象、能力项、判断、确认人、时间） | → 已确认 |
| 指定或更换带教 | 带教（管理者） | 带教关系记录（范围、起止） | 旧关系写结束日，新关系生效 |

**状态边界（现在定死，第二轮不改含义）：**
- 已提交、待评审 ≠ 已通过；培养任务的「已通过」只能来自一条认定记录。
- 交付完成 ≠ 业务效果已验证。
- 带教已响应受阻 ≠ 受阻已解除。
- 逾期是标记，不是状态；怎么算逾期放第二轮。

## 5. 数据结构调整

**沿用上一版的三处：**
1. `submission_credit`：一行 = 一个成果版本 + 一个培养任务实例（任务实例属于某一位管培生），另有认定状态、认定人、认定时间。多人项目里每人的认定各记一行。
2. 删除 `project` 表里的「项目带教」字段；项目带教统一记在带教关系里（范围 = 项目），这是唯一来源。
3. 项目结论区分交付结果和业务验证（见下方第 7 条）。

**本次新增的四处：**

4. **评审责任快照：** 成果版本上记「评审负责人」和「评审状态」（待评审 / 已评审）。提交时按带教关系定下负责人并存下来，之后**不再每次查询时重新推导**；更换负责人时写一条明确的改派事件。待评审的成果本身就是评审待办的事实来源，不另存一份。
5. **下一步行动：** 独立的小对象，不再只是评审里的一段文字。字段：来源评审、类型（修改再交 / 推进后续节点 / 建议）、内容、负责人、状态（未完成 / 已完成 / 不再需要）、完成依据（例如再交的版本）。哪类行动生成提醒、何时提醒放第二轮。
6. **受阻处理记录：** 独立对象，挂在节点上。字段：原因、需要谁决定、当前处理责任人、响应（内容、人、时间，可多次）、解除（人、时间、说明）。
7. **项目结论拆字段：** 交付结论（达成 / 部分达成 / 未达成验收条件）；验证状态（未验证 / 已验证 / 不适用）；验证结论（达成 / 部分达成 / 未达成 / 无法判断）；验证来源（业务负责人反馈、试点数据、成果文档等）；验证证据（链接、确认人、时间）。

**另外：** `user` 表保留「管理权限」字段（现在只有常浩为是），不做权限配置界面。

## 6. 骨架期的简化约定与四个统一入口

| 方面 | 骨架期 | 第二轮再定 |
|---|---|---|
| 环境 | 本机演示模式：可以切换示例身份，只用合成数据，只监听 127.0.0.1。演示模式由明确的环境开关打开，正式环境禁止开启 | 部署环境配置 |
| 权限 | 所有读写都经过统一授权入口。演示模式下：带教放行全部；管培生的页面只展示自己的数据和参与的项目。非演示模式下，没有完成身份认证和资源授权时，默认拒绝访问业务数据 | 可见性范围、历史权限、交接期权限、服务端对象级过滤；**真实数据进来前必须完成并验收** |
| 登录 | 演示身份切换 | 飞书登录（第 4 步，试点前） |
| 状态 | 只能通过第 4 节的业务命令改变 | 完整的状态流转约束、谁能执行哪条命令 |
| 时间 | 截止是普通日期；原截止和调整记录照存 | 工作日推算、评审时效、逾期判定、截止双报告 |
| 待办 | 待办页直接查询事实对象：待我评审的成果、我未完成的下一步行动、未响应的受阻、待确认立项的项目 | 自动待办规则 T01–T17、定时扫描、提醒、升级；只为提醒和升级的状态单独建表 |
| 指标与看板 | 位置齐全，只做标注清楚的基础计数 | 指标口径、分母、达标线 |
| 机器人、通知、AI | 不接；「AI 与接入」页保留（P-13） | 后续阶段 |

**四个统一入口（第二轮补规则时不返工结构的保证）：**
1. **业务命令写入：** 按业务动作组织写入（第 4 节），同一事务里更新对象并写事件日志。不按表生成通用增删改接口。
2. **统一授权入口：** 每条命令、每个查询都先过授权判断；第二轮在这里加对象级规则，并在查询层加数据过滤。
3. **待办来自事实对象：** 评审义务来自「待评审的成果版本」，修改义务来自「未完成的下一步行动」，受阻义务来自「未响应的受阻记录」。第二轮的自动待办与提醒都从这些对象和事件长出来，同一份业务责任不存两次。
4. **演示环境开关：** 宽松权限和身份切换只存在于这个开关之下。

## 7. 页面分级（A / B / C）

| 级别 | 做到什么程度 | 页面 |
|---|---|---|
| A 核心闭环 | 真实接口、真实持久化，用示例数据能跑完整流程 | 工作台首页（两种角色）；项目列表；项目详情（节点、成果版本、评审、下一步行动、受阻）；培养任务（我的路径、任务详情、关联成果与认定）；成长档案（基础：项目经历、能力证据及来源）；待办页；管理区必要入口（成员与带教关系、能力项） |
| B 架构确认 | 可交互原型：入口、布局、数据展示和操作流程都确定，暂不建表、不接接口 | 日程与本周；轮岗排期；交接；阶段复盘；带教看板与决策看板；知识资料；业务案例；AI 资产与贡献审核；路径模板、期次、工作日日历；「AI 与接入」 |
| C 远期能力 | 只确定在导航和架构里的位置，页面只放占位说明 | 积分与激励；跨期分析；飞书知识库同步；带教机器人接口；通知中心；汇报与团队活动 |

B 级尽量复用现有原型的页面（33 个路由），按新的四个工作域重新归位。

- **怎样算完：** 两种角色都能看懂整个产品并走通核心路径；按状态逐一检查页面（空数据、待提交、待评审、需修改、已通过、受阻、结项），截图只是辅助证据。

### 第 4 步　精细规则与真实试点

- 逐项设计并实现规则池：权限与可见性、时限与逾期、自动待办与提醒、评审改派、交接、指标口径。GPT 第一轮列的 8 个场景作为规则验收用例。
- 飞书登录和服务端对象级权限验收通过后，才录入 T1、T2 的真实数据开始试点。
- **怎样算完：** 规则用例全部通过；真实项目运行后能产出可追溯的成果和带教证据；记录用户额外的操作负担。

**粗估节奏：** 第 1 步约 1 轮会话；第 2 步约 1–2 轮；第 3 步约 2–3 轮（含挑版）。第 4 步看规则讨论的深度，不预估。

## 9. 骨架验收

### 9.1 骨架验收矩阵（第 1 步细化）

| 业务对象 | 核心命令 | 命令之后的事实 | 对应页面 | 页面级别 |
|---|---|---|---|---|
| 项目 | 创建、确认立项、结项 | 项目状态、立项确认记录、交付结论与业务验证 | 项目列表、项目详情 | A |
| 关键节点 | 新建、标记受阻、响应受阻、解除受阻 | 节点状态、受阻处理记录 | 项目详情 | A |
| 成果 | 提交、修改再交 | 不可修改的成果版本、评审负责人快照、与上一版评审的关联 | 项目详情、任务详情 | A |
| 评审 | 评审（通过 / 需修改） | 评审记录、下一步行动、认定记录 | 项目详情、待办页 | A |
| 下一步行动 | 随评审产生；再交或手动完成 | 行动状态与完成依据 | 项目详情、待办页、首页 | A |
| 培养任务 | 关联成果、认定 | 认定记录、任务状态 | 我的路径、任务详情 | A |
| 能力证据 | 提炼、确认 | 带来源和确认人的能力记录 | 成长档案 | A |
| 带教关系 | 指定、更换 | 关系记录（范围、起止） | 管理区 | A（基础） |
| 交接 | 换前、接手、结清 | 交接信息 | 交接页 | B |
| 阶段复盘 | 自评、带教结论 | 复盘记录 | 阶段复盘页 | B |
| 知识与 AI 资产 | 查询、贡献、复用 | 可复用的知识 | 知识与工具 | B |

用矩阵检查三件事：有没有对象找不到使用场景；有没有页面按钮找不到对应的业务命令；有没有命令执行后，关联页面的数据没有跟着变。

### 9.2 八项骨架验收（骨架完成后、第二轮开始前验证）

1. **项目与成果闭环：** 立项 → 新建节点 → 提交 V1 → 评审需修改 → 提交 V2 → 评审通过 → 结项。
2. **成果复用：** 一个成果版本关联培养任务，不需要重新提交第二份成果。
3. **带教责任：** 带教关系能保存，并正确关联到项目、培养任务和评审负责人。
4. **受阻状态：** 节点受阻、带教响应、阻碍解除是三件可区分的事实。
5. **业务结果：** 结项能区分交付完成、验证状态和实际效果。
6. **能力证据：** 从已评审的成果提炼证据，在成长档案里能追溯到来源。
7. **跨页面一致：** 一个命令完成后，工作台、项目详情和成长档案的数据没有矛盾。
8. **演示数据隔离：** 演示身份和合成数据不会误连真实用户环境；关掉演示开关后，未认证的请求拿不到业务数据。

这八项不要求真实的权限体系或完整的自动化，只要求业务对象和基础交互没有结构性缺陷。
