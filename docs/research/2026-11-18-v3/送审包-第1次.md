思维评审｜TraineeOS｜PRD v3.0 带教杠杆方向（第一阶段）

【本次要判断什么】
TraineeOS（管培生培养工作台）的 PRD 要从 v2.1 改到 v3.0：把定位收紧为「带教杠杆系统」，并据此重排功能和施工顺序。这个方向和第一阶段的范围是否成立。拆成四个子问题：
1. 底层需求判断对不对：瓶颈真的是「一位带教的判断带不动更多人」吗？有没有更值得解决的问题被漏掉？
2. 「两个回路、四个杠杆」是不是对的解法，先后顺序对不对？其中「反馈有相当比例在重复」这个前提没有验证，能不能支撑把反馈模式库放进核心？
3. 能力模型从「五条能力项 + 三级判断」换成「可托付活动 + 五级信任」，在 2–10 人的规模上值不值得，还是过度设计？
4. 路线：第一阶段的范围、以及「路径与评审先切换、答疑后切换」的分模块切换，是不是最快拿到真实使用的走法？有没有更小的第一步？

【本次不判断什么】
实现细节、数据库字段、命令编号、界面视觉、已建成后端的代码质量。

【背景与目标】
- 这是一个自建的网页工作台（React + Node + PostgreSQL），用来带公司里的管培生：培养路径、真实业务项目、成果评审、带教反馈、能力证据。
- 现状：两名管培生、一位带教（常浩，同时是产品负责人和唯一的管理者）。两人目前在常浩另一个个人工具里带，本工作台还没有真人使用。
- 已有 PRD v2.1（2026-11-14）：定位是「业务实践驱动的管培生成长与带教协同系统」。已建成后端 19 条业务命令（项目、里程碑、成果提交、评审、下一步行动、受阻、结项、能力证据、带教关系）、事件日志、统一授权；页面大多还是原型。

【目标用户与核心假设】
- 带教：用同样的时间带更多人；在评估点有证据地判断去留和定岗。
- 管培生：知道该做什么、做到什么样算好；更快拿到反馈；看得见离「能独立」还差什么。
- 核心假设（未验证）：成长 ≈ 真实任务的挑战 × 反馈的质量和速度 × 带着反馈再做一次；系统能直接作用的是后两项。

【常浩的原始诉求】（原话）
- 「管培生的数量会加，需要可以操作，带教目前就按我一人算。」
- 「我要做出一个有价值的好用的酷炫的牛逼的管培生工作台。」
- 「当前功能是否满足，逻辑是否清晰，还有哪些功能想法可以考虑？不要默认我提出的问题定义就是正确的。你先分析我真正想解决的底层需求，判断我有没有把症状误认为原因、把手段误认为目标。如果存在更值得解决的问题，直接指出来。以及其他领域里有没有类似的方案，用跨领域的方式全面思考，找到最优解。」
- 「要依据你最新的思考和判断，最新的 prd 重新梳理，当前的所有内容都可以推翻。」

【已知事实】
- v2.1 里期次、个人路径、培养节点只能由初始化脚本生成，界面上不能加人（来源：PRD v2.1 第 4.1 节）。
- v2.1 里评审是「结论 + 一段文字」；评审、答疑审核、立项确认、受阻响应全部由带教一人处理，没有前置筛查（来源：PRD v2.1 第 7、11 节）。
- v2.1 的规则池里已有一句「多名管培生重复遇到同类问题，需要给关键问题加问题标签」，排在第二轮（来源：PRD v2.1 下篇 R7）。
- v2.1 规定工作台自己不调用 AI；AI 产出由一个外部的企业带教 Agent 经接口写入，全部是草稿，带教审核后才生效（来源：PRD v2.1 第 15 节）。
- 2026-11-06 到 11-14 的 9 天里 PRD 出了 4 版，真实使用为零（来源：仓库提交记录）。
- 以下来自常浩的本地记录，原文不外发，此项在本地核实：带教反馈大量发生在口头点评和答辩里，不在表单里；有同类反馈隔了几个月再次出现的例子（例子数量少，不构成统计）；这个培养项目带有去留评估；成员不是同一批入职，走的线也不同。
- 未核实：带教每周实际花在带教上的时间；反馈里重复的比例；管培生会增加到多少人。

【约束与不可改变的边界】
- 带教现阶段只有一人；管培生会增加（数量未定）。
- 只做电脑版；视觉规范已定，不在本次范围。
- 应用里的 AI 产出必须在设置页写清谁做的、怎么接入、读什么、写到哪，并带留痕（常浩的全局规则）。
- 带教既是使用者又是产品负责人，他的确认本身消耗同一份注意力。

【既定决策】
无。常浩明确说当前内容都可以推翻。

【方案来源】
v2.1 之前的方案由常浩与 ChatGPT、Claude 多轮讨论形成；v3.0 草案由 Claude 在 2026-11-18 独立起草，没有经过独立评审。常浩读了草案摘要后回复「都按推荐」，其中一条推荐就是定稿前送这一轮评审，所以下面的方向是「常浩倾向、仍可被推翻」。

【已考虑的替代方案】
- 沿用 v2.1，先把页面接上接口、补齐旧工具的全部功能再切换：被放弃，理由是没有任何减负机制，而且离真人使用更远。
- 不自建，用多维表格加机器人：此前试过一个版本，约两周后停用（常浩的本地记录，此项在本地核实）。
- 其他替代方案尚无，欢迎提出。

【未确定的假设或分歧】
- 「反馈有相当比例在重复」是复用回路的前提，只有零散例子。
- 容量估算是假设：每人每周 3 份成果 × 15 分钟 + 30 分钟一对一，10 人约每周 12.5 小时。
- 可托付活动的清单（9 条）是 Claude 起草的，常浩还没改。
- 这是第五版 PRD，再次改方向本身有成本。

【为什么值得独立论证】
方向性改动，影响后续全部实现；关键前提没有验证；方案由一个模型独立形成；错了要返工 PRD、任务拆分和后续开发。

【本次希望得到的结果】
先请你只根据上面的事实、约束和四个子问题，独立给出你的判断；然后再对照下面的方案，指出哪里成立、哪里需要深化、哪里不值得继续讨论。能一次收口就直接给退出建议。

【Claude 当前的判断与依据】（PRD v3.0 草案的要点）

一、底层需求（推断）
- 真正稀缺的是带教的判断，不是功能。三处把手段当成了目标：把「过程可见」当成「人会成长」；把「功能全」当成「有价值」；把「酷」当成模块数量。
- 「能加人」只说了一半：加人界面好做，随人数增长的是评审量。
- 更值得解决的问题：每多带一个人，带教每周多花的时间能不能越来越少；每个去留判断能不能拿得出证据。

二、定位与指标
- 定位：把一位带教的判断变成可复用的标准，把每次交付变成更快的反馈回路，让每个去留判断有证据。
- 北极星：人均带教用时（系统记带教处理每项的时长）。辅助：判断等待时长、重复反馈率、首次通过率、到「独立完成」的天数、预审采纳率。不设排行，不用活跃度。

三、两个回路
- 反馈回路：培养节点或项目里程碑（标明练的是哪几项活动）→ 提交成果 → 自检（该活动的自检项，加上本人上次被指出的问题）→ 预审（外部 Agent 或被指派的同伴，只给意见、不改状态，固定三问：结论是什么、证据够不够、最大的漏洞是什么）→ 带教判断（结论 + 逐条反馈）→ 通过则形成证据，需修改则生成下一步行动。只有带教的判断改变状态。
- 复用回路：每条反馈可挂一个「反馈模式」→ 同一模式累计出现 3 次时提议晋升 → 升为自检项或写成标准卡 → 下一个人提交前就看到。系统不自动晋升，由带教决定。

四、功能
1. 加人与路径：界面上填入职日、选模板版本和线，按工作日自动排期；按人滚动入职，「期次」降为可选的批次标签。
2. 判断队列：带教首页只有一个队列，装下所有等他判断的事（待评审、受阻、立项、答疑审核、反馈草稿、模式晋升提议、信任级别建议、评估到期），按「卡住别人的事优先、等得久的优先」排序，每项预先整理好上下文，就地处理。
3. 评审漏斗：自检 → 预审 → 带教判断（见上）。
4. 反馈与模式库：反馈成为独立对象，来源有评审、会议纪要（Agent 提炼成草稿，带教确认）、带教随手记的观察（目标 30 秒记一条）、答疑。
5. 可托付活动与信任地图：把能力落到具体活动上（如岗位观察、问题定义、调研取证、方案设计、结论先行的汇报、项目推进、AI 协同、沉淀复用、给他人预审），五级信任：未观察、了解、指导下完成、独立完成、可带人。等级只由带教确认，不自动计算。
6. 评估点与决定：到评估点自动拼出材料包（信任地图及变化、代表性成果、重复中与已改掉的反馈模式、项目与业务验证、评审分数、自评），带教给出决定（继续、限期复核、停止、定岗）和理由，导出一页给上级。
7. 项目与里程碑、答疑记录：沿用 v2.1。
8. 标准卡与问答只在用得上的那一步出现，不建供人浏览的知识库。
9. 管培生首页只回答三件事：现在最该做的一件事；提交前别再犯的（最多 3 条重复中的模式）；离独立还差什么。

五、AI
工作台仍不直接调用模型。外部 Agent 写入五类草稿：答疑答案、成果预审、会议纪要提炼的反馈、模式归并建议、评估结论草稿。全部要带教确认或可忽略。

六、冻结
交接流程、多带教视角、多位评委、周期任务、积分、知识库同步、独立的日程日历。数据结构保留，界面不出现。

七、路线（四个阶段，逐个验收）
- 一 · 能加人、能判断、真人用起来：加人与排期、调整安排、评审方式、判断队列与管培生首页、主要页面接上接口、评审时反馈可挂模式（先做到能选、能新建、能计数）、登录与部署、导入两个人现有的路径和评审记录。答疑暂时留在旧工具里。
- 二 · 判断可复用：自检项、模式晋升与回流、标准卡、答疑与 Agent 接口、Agent 预审、会议纪要回流。
- 三 · 去留有证据：证据绑定活动、信任地图、评估点与导出。
- 四 · 人多了更省：同伴预审、达到「可带人」的人做预审、业务部门的带教经 Agent 留观察。管培生达到 3 人以上再开。

八、跨领域依据
住院医师培养（可托付活动、多次短观察、定期汇总决定；教训是表单一重就走形式）；软件工程（提交模板、自动检查先拦常规问题、同一条评审意见说到第三次就写成规则）；咨询公司的项目制评价；丰田的「标准是当前最好做法，暴露问题就更新」；体育教练的录像回看与一次只练一个弱点；训练营的同伴互评；医院分诊与工单队列；游戏的技能树（只取呈现方式，不做积分排行）。

九、Claude 自己认为的风险
重复反馈的前提未验证；这是第五版 PRD；自检可能流于勾选；预审可能添乱或把带教带偏；可托付活动的设计成本和等级通胀；一位带教带 10 人以上即使有漏斗也可能接不住。

请以独立思考者的身份做思维评审，不是代码审查：
1. 先判断问题本身是否提对了：先审目标用户、核心假设，以及它们是否符合常浩的原始诉求，再看具体设计。如果待决问题的定义、目标或边界有问题，直接重构它。
2. 不局限于我给出的方案。可以提出我没考虑的路径，挑战关键假设，指出隐藏的系统性影响，判断是否存在不必要的复杂化。
3. 方案已经成熟的部分，请明确认可，不需要为了提意见而提意见。评审价值看是否帮助形成有依据、可执行的正确方向，不看问题条数。
4. 只围绕本次待决问题，不扩展到整个项目；不按 P0–P3 列缺陷。
5. 我提供的事实中你无法核实的，请在依赖它的判断旁标出「依赖未核实事实：……」。
6. 本次处于第一阶段：请先只看【已知事实】【约束】和四个子问题，独立给出你的判断，再对照【Claude 当前的判断与依据】。尽量一次找出会实质影响结论的问题（重大遗漏、错误前提、不成立的因果、被忽略的路径、未比较的取舍、决定性风险），给出关键问题地图，每条标「成立 / 需深化 / 不值得继续讨论」。
7. 如果首轮已经可以收口，直接给出退出建议，不必走完三个阶段。

回信结构：
## 问题重述（如需重构问题定义，在此说明）
## 判断（逐个待决问题：认知状态 + 依据）
## 新发现（只写会改变核心判断的）
## 执行建议（不阻断，由 Claude 自行取舍）
## 交接（选定路径、执行中要验证的假设、需要常浩决定的事项）

评审出口：成熟退出 / 继续深化 / 证据不足暂停 / 决策升级 / 转其他路径（五选一）
结论：<按下表填写>
- 成熟退出、转其他路径 → 结论：通过
- 继续深化、证据不足暂停 → 结论：需修改
- 决策升级 → 结论：交常浩裁决
