## 修订记录

v2.0 相对 v1.1 的主要变化：

1. **定位**从「培养路径、资料、AI 资产与贡献的聚合工作台」改为「业务实践驱动的管培生成长与带教协同系统」：工作本身是培养的载体，培养嵌在真实业务里，不在工作之外另加一套打卡流程（第 1 节）。
2. **角色**从四种（管培生、带教人、管理员、同事）减为两种：**管培生、带教**。管理功能是带教身上的「管理权限」开关；去掉同事角色。站带教、主带教合并为一种**带教关系**，可按全程、某站或某项目指定（第 2 节）。
3. 新增**项目**和**关键节点**：项目可跨站持续存在，只管五件事（为什么做、到哪一步、卡在哪、谁来判断、证明了什么），不做项目管理器（第 4 节）。
4. 培养任务可以**关联项目**；一份成果只交一次，可同时满足项目节点和培养任务（第 3、6 节）。
5. 点评改为**两级反馈**：日常任务保留三档加短评；关键节点加「关键问题、带教判断、下一步行动」，下一步行动直接生成待办（第 6 节）。
6. 新增**能力证据**和**阶段复盘**：能力项起步采用已有的季度答辩「4+1 主线」，证据按「事实 → 判断 → 行动 → 结果 → 修改」记录，由带教确认，不自动打分；阶段复盘取代 v1.1 的阶段评估和站评（第 7 节）。
7. **交接**只在带教换人时发生，拆成换前交接、接手确认、换后结清三步，修掉 v1.1「新带教提前 5 天准备、交接要点却在站后 2 天才写」的时序错位；培养责任移交和项目带教移交分开处理（第 8 节）。
8. **信息架构**从六个平行板块改为四个工作域：工作台、项目实践、培养成长、知识与工具；团队内容放回人员和项目页，激励不设入口；管理区按权限显示（第 9 节）。
9. **待办规则**按开发阶段分批启用：阶段 1 只启用 7 条核心规则，其余列为候选随功能上线；明确「事件即时处理 + 定时扫描时间条件」（第 10 节）。
10. **知识与 AI 合并**为「知识与工具」，新增业务案例；资产详情加适用条件、已验证效果、已知限制、维护状态，可关联项目（第 11 节）。
11. **指标**不再设单一主指标：分业务推进、带教协同、培养成长三层；管理者首屏以决策看板为主；v1.1 的路径任务按期达标率降为执行指标，并修正口径：待评的留在总数里，原计划和调整后分开报告（第 12 节）。
12. **分期**改为五个开发阶段（阶段 0–4）；带教机器人不再是首期的必需依赖，核心闭环不靠机器人也能跑通（第 17 节）。

重构评审里没有采纳或收着做的：项目不做六阶段生命周期，只记五件事；能力方向不用评审新编的六项，改用已有的「4+1 主线」；「请求带教判断」的求助流程先不做，等真人验证（第 18 节）；AI 资产库不砍，降为「知识与工具」下的二级，排在项目闭环之后。

## 1. 定位

**一句话：** 业务实践驱动的管培生成长与带教协同系统。以真实业务项目为实践载体，以结构化带教为成长机制，以能力证据为评价依据，以经验沉淀为组织复利，推动管培生从理解业务、解决问题，到独立承担业务与项目。

**设计命题：** 不从「管培生需要管理什么」出发，而从「管培生如何在真实业务中成长并创造价值」出发。

### 1.1 三条线

| 线 | 回答什么 | 主干 | 最终形成什么 |
|---|---|---|---|
| 业务项目推进 | 做成了什么 | 项目 → 关键节点 → 成果 → 评审 → 结论 | 可验收的业务成果 |
| 培养与能力成长 | 人获得了什么成长 | 培养路径 → 培养任务 → 带教反馈 → 能力证据 → 阶段复盘 | 有证据的成长判断 |
| 经验沉淀（横向） | 经验如何帮下一个人 | 已验证的成果 → 案例或资产 → 审核 → 复用 → 反馈改进 | 案例、方法、模板与 AI 资产 |

前两条线通过成果、评审和能力证据相互关联，不互相替代；第三条线从前两条线的产出里取材。

这一结构与飞书知识库《00｜知识库使用说明》里已定的个人能力形成闭环一致：角色与能力要求 → 阶段训练 → 真实业务实践 → 反馈与结果验证 → 实质修订 → 能力证据 → 阶段评价 → 下一步训练；「完成任务不等于形成能力」。

### 1.2 价值亮点

1. **业务推进与培养成长双线联动：** 一个真实项目同时是工作成果、培养实践和能力证据的来源，不形成两套各自独立的记录。
2. **带教判断驱动的持续改进：** 不只追踪「做完没有」，还追踪「为什么没做成、带教怎么介入、改进有没有发生、下一步谁推动」。
3. **真实项目经验跨期复用：** 已结束的项目沉淀为案例、方法和资产，降低下一批管培生的学习成本。

三者形成飞轮：真实实践提高培养质量 → 带教提高业务产出质量 → 优质成果沉淀为组织经验 → 组织经验支持下一轮实践。

### 1.3 分工与边界

| 系统 | 负责 |
|---|---|
| 工作台 | 保存可信的业务与培养状态：项目、节点、培养路径、成果、评审、能力证据、交接；是这些数据的唯一数据源 |
| 飞书文档与知识库 | 文档正文、原始成果、正式知识；访问权限由飞书判断 |
| 飞书带教机器人 | 在工作发生的地方提供提醒、问答、周报与轻测、快速提交入口；通过工作台接口读写，是可替换的外部通道（第 14 节） |
| 企业带教 Agent（以后可选） | 基于授权知识和项目背景做解释与引导；先定义价值场景和数据权限，不作为任何阶段的阻塞依赖 |

**不做：**

- 不做项目管理器（Jira、Trello 或另一个飞书项目）：不做细任务分解、甘特、工时、评论区；日常协作和沟通留在飞书。
- 不存文件，产出只交飞书文档链接；不支持草稿。
- 不做手机版，只做电脑版（≥1280px）；人不在电脑前时的提醒交给机器人。
- 不写飞书日历；推算出的截止、换站、节点不进飞书日历。
- 不做聊天界面；不把规则功能包装成 AI；工作台自己不调用 AI（第 15 节）。
- 不把完成次数、AI 使用次数、活跃度当成能力结论。
- 不做账号密码登录。
- 积分、排行、兑换在价值被验证前不做。

### 1.4 一次事实输入，多处派生

用户只在一处录入一件事实；项目进度、待办、成长时间线、能力证据候选、案例候选都从同一事实派生，不要求在飞书、工作台、档案里各填一遍。「用户为维护系统额外付出了多少工作」是每个阶段的验收观察项（第 17 节）。

### 1.5 规模

- 现阶段：两名管培生、一位带教（常浩）。阶段 1 就在这个规模上验证。
- 规划：约 12 人一期，多位带教。数据结构预留「团队 / 部门」维度，全公司版不在范围内。

## 2. 角色与权限

### 2.1 两个角色

| 角色 | 能做什么 |
|---|---|
| 管培生 | 看自己的路径、项目和任务，提交成果，回应反馈，自荐能力证据，写阶段自评，使用和贡献知识与工具 |
| 带教 | 指导自己带的管培生：确认立项、评审成果、写下一步行动、提炼和确认能力证据、写交接、写阶段复盘结论；也可贡献知识与工具 |

- **管理权限**是带教身上的一个开关，不是第三种角色。开了管理权限的带教（下文称**管理者**）可以维护路径模板、期次、工作日日历、能力项与标签、成员与带教关系，审核贡献，看全部数据和决策看板，签发机器人密钥。现阶段只开给常浩。
- 去掉 v1.1 的「同事」角色。以后扩展到全公司时再加。

### 2.2 登录与开通

- 只用飞书登录（飞书内免登），只有公司飞书成员能进。
- 飞书 open_id 在某个期次预置名单里的人，首次登录直接成为该期次的管培生。
- 带教由管理者在后台开通。
- 其他人登录后看到「未开通」页，同时生成待办给管理者（T07）。

### 2.3 带教关系

带教关系只有一种，记为「某位带教在某段时间带某位管培生，范围是全程、某一站或某个项目」。

- **默认带教：** 范围为全程的那位。每位管培生在培养期内必须有一位默认带教，没有时由管理者兜底。
- **评审人推导：** 项目节点 → 项目上指定的带教，没指定就用管培生的默认带教；培养任务 → 所属站上指定的带教，没指定就用默认带教；都没有 → 管理者。评审人不单独存，查询时推出。
- **项目带教**和**培养带教**可以是同一个人，也可以不同；一个人可以同时带多位管培生、多个项目。
- 带教权限由关系的起止日推出，不靠手工改角色。
- 项目的业务验收人（业务部门负责人）只记名字，不进系统、不开账号。

### 2.4 可见性（全部在服务端执行，无权看的条目接口直接不返回）

| 内容 | 管培生本人 | 其他管培生 | 带教 | 管理者 |
|---|---|---|---|---|
| 站级进度（在哪站、换站） | 是 | 是 | 是 | 是 |
| 项目基本信息（名称、目标、状态、成员） | 是 | 是 | 是 | 是 |
| 项目的成果、评审、阻碍 | 项目成员可看 | 否 | 项目带教、成员的带教 | 是 |
| 培养任务状态、逾期 | 是 | 否 | 自己带过的人 | 是 |
| 成果、评审 | 是 | 否 | 自己带过的人 | 是 |
| 能力证据、阶段复盘 | 是 | 否 | 自己带过的人 | 是 |
| 交接记录 | 待定（第 18 节） | 否 | 交接双方 | 是 |
| 知识与工具（上架内容） | 是 | 是 | 是 | 是 |

- 「自己带过的人」= 与该管培生有过任一带教关系；关系结束后保留只读。
- 新带教从换前交接开始（变更日前 5 个工作日）起，可只读这位管培生此前的全部记录。

## 3. 核心业务模型

### 3.1 对象关系

```
培养关系   期次 ─ 个人路径 ─ 站 ─ 培养任务
                   │          │
                带教关系（全程 / 某站 / 某项目）
                              │
业务关系   项目 ─ 关键节点 ─ 成果（版本） ─ 评审（三档 + 关键问题 / 判断 / 下一步行动）
                                   │
                    同一份成果可同时满足关联的培养任务

证据与沉淀  成果 / 评审 / 带教观察 → 能力证据 → 阶段复盘
           已结束的项目 → 项目结论 → 业务案例 / AI 资产

底座       人员与角色 · 带教关系 · 工作日日历 · 事件日志（只追加） · 待办 · 权限 · 机器人接口
```

### 3.2 三类工作对象的区别

| 对象 | 是什么 | 例子 | 谁定义 | 生命周期 |
|---|---|---|---|---|
| 项目 | 有业务目标和责任人的持续性工作 | 某业务流程优化 | 管培生或带教发起，带教确认立项 | 可跨站，不随站结束关闭 |
| 关键节点 | 项目里需要交出关键成果或作出决定的检查点 | 完成问题定义并通过评审 | 项目成员与带教 | 属于项目 |
| 培养任务 | 对管培生提出的学习或能力要求 | 掌握流程分析方法，并在一个项目中应用 | 路径模板（路径任务）或周期规则（周期任务） | 属于站或周期规则 |

三者可以关联，但不能合并成同一个对象；否则会出现培养任务结清但项目没完成、跨站项目找不到责任人、同一成果重复提交等问题。

### 3.3 成果只交一次

- 成果的主挂靠对象是一个关键节点或一个培养任务。
- 培养任务可设「在项目中完成」：评审人通过某个节点的成果时，可勾选「同时满足培养任务 X」，管培生不必再交一次。
- 任务和节点的状态各自独立，不合并成一个笼统的「完成」：提交、评审结论、节点通过、项目结束分开记。

## 4. 项目与关键节点

### 4.1 项目

- **字段：** 名称；目标（为什么做、要解决什么问题）；主责管培生；参与管培生（可空）；项目带教（可空，空则用主责管培生的默认带教）；业务验收人（只记名字）；验收条件；关联站（可多个，记录项目发生在哪些站）；项目文档（飞书链接）；状态；结论。
- **状态：** 草拟 → 推进中 → 已结束（完成 / 中止）。
- **立项确认：** 管培生或带教都可以新建项目，状态为「草拟」；项目带教确认目标和验收条件后转「推进中」（T06）。带教新建时可直接确认。
- **结论：** 项目结束时由主责管培生填写，带教确认：结果是否达成验收条件、证据（链接到成果）、可复用的经验、后续建议。结论是案例候选的来源（第 11 节）。
- **跨站：** 项目不随站结束关闭；管培生换站或换带教时，在交接里决定项目带教是否随之移交（第 8 节）。
- **中止培养：** 主责管培生中止培养时，推进中的项目必须由管理者重新指定主责人或标为中止。
- **不做：** 细任务分解、甘特、工时、评论区、项目内聊天。

### 4.2 关键节点

- **字段：** 名称；节点目标；验收标准；原截止；当前截止；状态；当前阻碍（可空）；关联的培养任务（可空）。
- **状态：** 未开始 → 进行中 → 待验收 → 需修改 / 已通过；可取消（写原因）。超过截止未通过自动标「逾期」，逾期是标记，不是状态。
- **截止：** 由项目成员或带教填写，不按模板推算；落在非工作日时提示。调整截止必须写原因并留痕（原截止、新截止、原因、操作人），原截止永久保留。
- **受阻：** 节点可标「受阻」，写一句原因和需要谁决定；受阻时生成待办给项目带教（T05），并在带教首页和决策看板上显示。工作台不提供对话或求助流程（见第 18 节「请求带教判断」）。
- **评审：** 节点成果按关键节点深反馈评审（第 6 节）。

### 4.3 项目模板（阶段 3 以后）

- 前身项目的 45 条标准项目模板可以改写成「项目模板」，复用路径模板的版本冻结机制；新建项目时可选模板生成节点。
- 阶段 1、2 不做，项目和节点手动建。

## 5. 培养路径与培养任务

本节沿用 v1.1 第 4.1、4.2 节的大部分规则，改动处单独说明。

### 5.1 路径结构（沿用）

- 三层：**阶段 → 模块（轮岗岗位）→ 任务模板**。阶段示例：入职、通识、轮岗、定岗。
- **路径模板**由管理者维护，带版本号：已被期次绑定的版本只读，改动另存新版本。
- **期次**：名称、绑定的模板版本、开学日、结束日、状态（筹备 → 进行中 → 已结束）、预置名单（飞书 open_id）。
- **个人路径**从模板派生，带起止日期、轮岗顺序和站；入职、通识、定岗也各算一站。
- **改动：** 站上不再有「站带教」字段，带教关系统一记在带教关系里（2.3）。
- **期次启动：** 阶段 1 只做最简版（选模板版本、录入名单、设开学日、指定默认带教、发布）；完整向导（轮岗矩阵、按站指定带教、甘特预览）在阶段 2。
- **调整个人路径**（顺延、换顺序、换带教）是一个事件：未开始的站和任务按新日期重排，已开始的站只能顺延；每次调整留痕。轮岗排期由所有人的个人路径汇总生成，不单独维护。

### 5.2 时间规则（沿用）

- **工作日日历**由管理者维护法定假期与调休；所有期限按工作日推算，统一由服务端计算，并记录日历版本和截止调整历史。
- **截止规则：** 任务模板写「锚点（站开始或站结束）+ 偏移 N 个工作日 + 时刻」和「建议用时（天）」；开放日 = 截止 − 建议用时。
- **评审时效：** 提交后 2 个工作日；超时提醒评审人，再过 3 个工作日提醒管理者。
- **修改截止：** 评审为「需改进」时默认 3 个工作日，带教可改。
- **调整截止：** 带教或管理者可改，必须写原因，留痕；原截止永久保留，指标按原计划和调整后分开报告（第 12 节）。

### 5.3 培养任务

- **两种类型（沿用）：** 路径任务（属于某站）和周期任务（由周期任务规则展开）。
- **改动：** 路径任务可设「在项目中完成」，并关联项目（3.3）。
- **状态（沿用）：** 未开始 →（到开放日自动，或本人点开始）进行中 → 已提交 → 需修改 / 已通过；逾期是标记。
- **周期任务四种完成方式（沿用，阶段 2 启用）：**

| 完成方式 | 例子 | 怎么算完成 | 带教评不评 |
|---|---|---|---|
| 提交链接 | 日报（是否保留待定） | 同路径任务 | 待定 |
| 机器人收周报 | 周报 | 只在机器人里交，工作台只显示交没交 | 只看不评 |
| 机器人写成绩 | 轻测 | 机器人出题、成绩写回；未作答记「未答」，不判逾期 | 不评 |
| 本人声明 + 带教确认 | 月度物料 | 本人声明，带教确认通过或退回 | 带教确认 |

- 尽量不让管培生每天重复填日报：成果提交和节点推进本身就是进度。

## 6. 成果、评审与两级反馈

### 6.1 成果

- 以飞书文档链接提交，工作台不存文件，不支持草稿。
- 字段：主挂靠对象（节点或培养任务）、飞书链接、版本、提交时间、提交渠道（网页 / 机器人）、修改说明（再交必填）。
- 再交时，详情页并排显示上次评审的关键问题、下一步行动和这次的修改说明。

### 6.2 两级反馈

| | 日常轻反馈 | 关键节点深反馈 |
|---|---|---|
| 用在哪 | 培养任务 | 项目关键节点；带教也可对重要的培养任务选用 |
| 结论 | 三档：优秀 / 达标 / 需改进 | 三档：优秀 / 达标 / 需改进 |
| 文字 | 一两句短评，不设字数下限 | **关键问题**（这份成果说明了什么、还缺什么）、**带教判断**（为什么这样判断）、**下一步行动**（需改进时必填，写清要补什么、怎么验证） |
| 产生什么 | 需改进时生成修改待办 | 下一步行动生成待办给管培生（T02）；可一键「提炼为能力证据」 |
| 可选 | 同时满足关联的培养任务 | 同时满足关联的培养任务；升级给业务验收人判断（只记录，不在系统内流转） |

- 不打分数；细节可留在飞书文档批注里。
- 系统不要求带教填复杂表单：深反馈三栏都是短文本，只在关键节点出现。
- 评审人推导见 2.3；评审人更换时，未完成的评审按规则迁移，已写的评审保留原评审人。

## 7. 能力证据、阶段复盘与成长档案

### 7.1 能力项

- 由管理者维护的列表，**起步采用季度答辩的「4+1 主线」**：
  1. 公司、行业与导师侧认知
  2. 用户与服务链路认知
  3. 实际项目推进与交付
  4. 营销线（是否作为通用能力项待定，见第 18 节）
  5. AI 使用与人机协同（贯穿前四条）
- 这是起始框架，不是公司已确认的能力标准；可增删，带版本。

### 7.2 能力证据

- **字段：** 管培生、能力项、来源（成果版本 / 评审 / 带教观察）、证据内容、判断、确认人、状态（待确认 / 已确认 / 退回）。
- **证据内容**按季度答辩的证据链写，按需填，不强制每栏都写：情境与事实 → 判断与依据 → 行动 → 结果与验证 → 反馈后的修改。
- **判断三级：** 尚未观察到充分证据 / 有指导下完成 / 可独立完成。
- **来源两条：** 带教在评审时「提炼为能力证据」（直接已确认）；管培生从已通过的成果自荐（待带教确认，阶段 2 启用）。
- **不做：** AI 自动打分；从任务状态、完成次数、活跃度自动推出能力判断。

### 7.3 阶段复盘（取代 v1.1 的阶段评估和站评）

- 每个阶段结束时做一次（T12）：
  - **管培生自评**：用季度答辩 5 问——原来怎么理解 → 哪些经历、事实或冲突改变了理解 → 现在怎么判断 → 为什么现在的判断更完整 → 这个判断能否指导下一步。做对和做错都要复盘。
  - **带教结论**：三档 + 评语 + 下一阶段重点要验证的能力。
- 复盘页自动汇总这个阶段的项目、通过的节点与成果、受过的关键反馈、各能力项的证据覆盖（哪些能力项还没有已确认证据）；带教只需作综合判断和补充说明，不用重新翻阅大量文档。
- 带教填写即生效；填写人不是管理者时，管理者可查看并退回。
- 定岗答辩材料包（阶段 4）从这里一键汇总。

### 7.4 成长档案（成果与能力的解释页）

- 每位管培生一页：当前阶段与站、项目经历（每个项目的目标、自己的角色、结论）、通过的成果、能力证据（按能力项）、阶段复盘、交接卡、成长时间线（事件日志按人的投影）。
- 档案顶部给带教看**交接卡**：历次交接摘要。
- 可见性见 2.4。

## 8. 交接

只在某位管培生（全程或某一站、某个项目）的带教换人时发生；前后是同一位带教时不交接。

| 步骤 | 谁 | 期限 | 内容 |
|---|---|---|---|
| 换前交接（T08） | 原带教 | 变更日前 3 个工作日（变更日前 5 个工作日出现） | 进行中的项目及下一步、已知问题、培养建议（下一步要验证的能力）、待转交事项；每个进行中项目选「项目带教随之移交 / 保留原带教」 |
| 接手确认（T09） | 新带教 | 变更日 | 读完点「已接手」；变更日仍未确认则提醒管理者 |
| 换后结清（T10） | 原带教 | 变更后 2 个工作日，超时转管理者 | 遗留的待评成果给出结论或转交新带教；遗留任务指定责任人 |

- 培养责任移交和项目带教移交分开处理：项目可以在管培生换站后继续由原带教指导，也可以随之移交。
- 新带教从换前交接出现时起，可只读这位管培生此前的全部记录（2.4）。
- 交接记录进成长档案的交接卡。

## 9. 信息架构与核心场景

### 9.1 四个工作域

原则：以业务对象和用户目标组织主导航；以待办、日程、搜索组织跨场景入口；激励和展示作为附属能力。

| 工作域 | 二级功能 | 定位 | 阶段 |
|---|---|---|---|
| **工作台** | 我的重点、待我推进、待我判断、近期进展（按角色组合，见 9.3） | 当前行动与协同入口 | 1 |
| **项目实践** | 我的项目（管培生）/ 我带的项目（带教）/ 全部项目（管理者）、项目详情、新建项目 | 真实业务推进的核心 | 1 |
| **培养成长** | 我的路径（阶段、站、培养任务）、任务详情、成长档案、阶段复盘 | 培养与能力证据 | 1（阶段复盘 2） |
| | 我带的人（带教看板）、交接 | 带教视角 | 2 |
| **知识与工具** | 知识资料、业务案例、AI 资产（Skill、Prompt、工作流、用例）、模板与 SOP（筛选视图，不另建对象）、贡献与审核、FAQ | 经验复用与 AI 赋能 | 3 |

- **顶栏：** 待办（阶段 1）、日程（阶段 1 起，视角逐步增加）、全局搜索（阶段 3）、通知（阶段 3）。头像进入自己的成长档案。
- **管理区（只对管理者显示）：** 待处理；成员与带教关系；期次与路径（期次、轮岗排期、路径模板、周期任务规则、工作日日历）；能力项与标签；审核；AI 与接入；汇报（阶段 4）。
- 不设单独的「团队」「激励」入口。成员列表放在管理区和项目成员里；公告、活动、周报汇总、积分排行推后（第 17 节）。
- **聚合优先，不加页面：** 项目详情一页内就能看到目标、当前节点、关联培养任务、最近反馈、阻碍和可用的知识与工具，不需要跳五个板块。新结构不以页面数衡量进度。

### 9.2 日程

日程项是从现有对象查询推出的视图，不建表。三种形状：时段（阶段、站、任务开放期）、截止（任务截止、节点截止、修改截止、评审期限、交接期限）、时刻（换站、带教变更、阶段复盘节点）。

| 视角 | 给谁 | 回答什么 | 阶段 |
|---|---|---|---|
| 我的本周 | 管培生 | 这周哪天交什么（节点和任务）、在哪站第几周、下一站哪天开始 | 1 |
| 我带的人 | 带教 | 谁哪天交、我哪天要评完、谁要换到或离开我这里 | 2 |
| 轮岗排期 | 管理者（其他人只读） | 按人、按岗位、按带教三视角；标出换站、带教变更、阶段复盘节点、假期 | 2 |
| 团队活动 | 全员 | 分享会、路演（只读共享飞书日历） | 4 |

每条日程点开跳回它所属的对象。

### 9.3 工作台（首页，两种角色）

- **管培生：** 本阶段核心目标（当前站 + 主推项目的当前节点）→ **最重要的下一步**（最近一次评审给出的下一步行动，或最急的两条待办）→ 需要协调的事（受阻节点、等待验收的成果）→ 最新带教反馈（关联到成果）→ 我的本周 → 进度（时间进度、完成进度、能力证据覆盖）。
- **带教：** **待我判断**（待验收节点、待评审任务，按离超时排序；立项待确认；受阻节点）→ 我带的人（每人一行：在哪站、当前项目与节点、最近一次反馈、风险标记：逾期 / 受阻 / 连续需改进）→ 交接（如有）。
- **管理者额外看到决策看板**（替代 KPI 大屏），每条信号对应一个管理动作：

| 信号 | 对应的管理动作 | 阶段 |
|---|---|---|
| 某项目连续两次未通过同一节点 | 判断是能力不足、目标不清还是资源问题 | 1 |
| 某带教评审持续积压 | 调整带教负载或介入 | 1 |
| 某管培生某能力项长期没有证据，或阶段将结束仍缺证据 | 安排下一个有针对性的项目 | 2 |
| 某站长期难形成通过的成果 | 修正培养任务或轮岗安排 | 2 |
| 多名管培生重复遇到同类问题 | 更新培养材料或沉淀 SOP（需要给评审「关键问题」加问题标签） | 3 |

### 9.4 核心场景

| 场景 | 发生什么 | 产品价值 | 阶段 |
|---|---|---|---|
| S1 管培生每天打开 | 先看到正在推进的目标、当前阻碍和下一步行动，而不只是待完成事项 | 从展示信息转为推动行动 | 1 |
| S2 带教在关键节点评审 | 看到项目目标、上次反馈、本次修改说明和验收标准，给出结论和下一步行动 | 把带教时间花在真正需要判断的地方 | 1 |
| S3 阶段结束复盘 | 复盘页汇总项目、成果、反馈、证据覆盖；管培生自评，带教作综合判断 | 减少印象式评价，培养决策可解释、可追溯 | 2 |
| S4 带教换人 | 换前交接传递进行中的项目和培养建议，换后结清遗留 | 交接传递业务上下文，而不只是换人审任务 | 2 |
| S5 下一批复用 | 新管培生进入同一岗位时，能看到上一批的项目案例、遇到的问题、用过的方法和工具 | 跨期积累的组织资产 | 3 |
| S6 遇到问题请求带教判断 | 管培生带上下文发起求助，带教回复后形成下一步行动 | 降低沟通信息损失 | 待验证（第 18 节） |

## 10. 待办与提醒

### 10.1 机制

- **待办 = 触发 × 规则：** 一条触发按一条规则生成一条待办，由另一事件关闭或撤销。
- **两种触发：** 事件即时触发（提交、评审、标受阻等）；**定时扫描**时间条件（今明到期、逾期、交接期限、开站预告）。没有任何人操作时，时间条件也必须能生成待办。
- **一致性：** 业务状态更新、事件日志写入和待办生成在同一事务内完成；对外推送（机器人）走事务型 outbox 异步投递。
- **唯一性（沿用）：** 同一规则、同一对象、同一负责人只有一条未关闭的待办；同一扫描重复执行也只生成一次。
- **兜底（沿用）：** 负责人为空时落到管理者；中止培养的人，其个人培养待办全部撤销（项目按 4.1 处理）。
- **汇总不生成待办：** 决策看板上的信号是查询。

### 10.2 规则（按阶段启用）

| 规则 | 触发 | 负责人 | 期限 | 关闭 | 阶段 | v1.1 对应 |
|---|---|---|---|---|---|---|
| T01 成果待评审 | 提交节点成果，或提交需评审的培养任务 | 评审人（2.3） | 2 个工作日；再过 3 个工作日提醒管理者 | 评审写入 | 1 | R02 |
| T02 按下一步行动修改 | 评审为需改进 | 管培生 | 修改截止 | 再次提交 | 1 | R03 |
| T03 今明到期 | 节点或任务截止在今天或明天且未完成 | 管培生 | 即截止 | 完成；截止调后撤销 | 1 | R04 |
| T04 逾期跟进 | 过截止未完成（需修改看修改截止） | 管培生补交；评审人一条跟进 | 立即 | 提交；截止调到未来后撤销 | 1 | R05 |
| T05 节点受阻 | 节点标受阻 | 项目带教 | 2 个工作日 | 解除受阻 | 1 | 新增 |
| T06 立项确认 | 新项目进入草拟 | 项目带教 | 2 个工作日 | 确认或退回 | 1 | 新增 |
| T07 新成员待开通 | 不在预置名单的人首次登录 | 管理者 | 待定 | 开通或拒绝 | 1 | R01 |
| T08 换前交接 | 带教变更日前 5 个工作日 | 原带教 | 变更日前 3 个工作日 | 交接写入 | 2 | R08 改 |
| T09 接手确认 | 换前交接写入 | 新带教 | 变更日 | 点「已接手」；逾期提醒管理者 | 2 | R06 改 |
| T10 换后结清 | 带教变更后仍有遗留 | 原带教 | 变更后 2 个工作日，超时转管理者 | 遗留都有结论或已转交 | 2 | R09 改 |
| T11 换站预告 | 开站前 5 个工作日 | 管培生 | 开站日 | 开站日自动关闭 | 2 | R07 |
| T12 阶段复盘 | 阶段结束 | 管培生（自评）、带教（结论） | 待定 | 两部分都填写 | 2 | R13 改，R14 取消 |
| T13 能力证据待确认 | 管培生自荐证据 | 带教 | 待定 | 确认或退回 | 2 | 新增 |
| T14 接口或同步异常 | 机器人接口或同步出错 | 管理者 | 立即 | 恢复正常 | 2 | R12 |
| T15 贡献审核 | 提交资产、案例 | 管理者 | 待定 | 通过或退回 | 3 | R10 |
| T16 贡献退回修改 | 贡献被退回 | 作者 | 待定 | 重新提交 | 3 | R11 |
| T17 资料待标注 | 同步到新资料 | 管理者 | 待定 | 补标签、挂到项目或任务 | 3 | R15 |

- 候选（阶段 4 或随功能上线时再定）：活动挂回放（R16）、对外展示本人同意（R17）、多维表格只读归档确认（R18）、兑换发放（R19）。
- **催办**（随机器人接口启用）：工作台写催办事件，机器人推送到飞书并写回送达回执；同一对象 24 小时内只催一次。
- **通知中心与推送规则**（阶段 3）：什么事件通知谁、走站内还是机器人；同一事件不重复推；晚间提交产生的评审提醒合并到次日 08:30 推一次。

### 10.3 边界情况

| 情况 | 处理 |
|---|---|
| 管培生中止培养 | 撤销个人培养待办；推进中的项目由管理者重新指定主责人或标中止 |
| 带教变更 | 走交接（第 8 节）；未完成评审按规则迁移给新评审人，已写评审保留原评审人 |
| 假期日历调整 | 未完成事项按规则重算，保留旧截止与调整记录 |
| 跨站项目未完成 | 项目继续存在，在交接里决定项目带教 |

## 11. 知识与工具

- **知识资料（沿用 v1.1 第 5 节）：** 资料本体留在飞书「管培生知识库」空间；工作台同步目录，以资料卡片展示（标题、链接、摘要、标签、关联阶段 / 任务 / 项目）；摘要在同步时截取文档开头一段，管理者可改写，不调用 AI。
- **四维标签（沿用）：** 阶段 / 模块（引用路径结构）、主题、类型（SOP、模板、案例、培训材料、制度规范、工具指南）、岗位；后三维是固定列表，由管理者维护。
- **业务案例（新增）：** 来自已结束项目的结论。字段：背景与问题、采用的方法、关键判断、验证结果、可复用做法、已知限制、来源项目、关联资产。由带教或管培生提交，管理者审核（T15）后上架；入库前去除个人评价和敏感信息。
- **AI 资产（沿用并扩展）：** 四类：Skill、Prompt、工作流 / SOP、用例。原字段之外增加：**适用条件、典型使用案例、已验证效果、已知限制、维护状态**，可关联项目和节点。Skill 文件存在工作台，沿用 SKILL.md 格式。
- **模板与 SOP：** 是资料类型「模板 / SOP」和资产类型「工作流 / SOP」的合并筛选视图，不另建对象。
- **FAQ：** 机器人审核入库的问答在这里展示，每条显示「由 X 生成 · 某某审核」（第 15 节）。
- **复用逻辑：** 从「资源分发」改为「按问题复用」：实际业务问题 → 关联的知识、案例、模板与 AI 工具（附适用条件和历史案例）→ 实际使用与结果反馈（在哪用、结果如何、有何限制）→ 更新资产或沉淀新案例。第一版用项目类型、阶段、问题标签加人工精选实现，不引入模型调用或复杂推荐算法。
- 「这一步可以用 · 推荐 AI 资产」出现在项目详情和任务详情：取节点或任务挂的推荐资产，没有时取同类项目用过的、再没有时取使用人数最多的上架资产。
- 外部发现：Tidings（`https://tidings.natsukashii.cn`）只做跳转入口。

## 14. 带教机器人接口

- 机器人负责飞书里的推送和对话，工作台负责可信状态（1.3）。机器人是可替换的外部通道，**不是核心闭环的单点依赖**；阶段 1 不接机器人。
- 机器人由谁承担待定（第 18 节）；机器人的改造在机器人自己的项目里做，不在本仓库。
- **最小接口（草案，随机器人接入时定稿）：**

| 接口 | 用途 | 关键保护 |
|---|---|---|
| `GET /bot/v1/me/context` | 某位成员当前的工作上下文（站、项目与节点、今天的日程） | 成员身份与字段权限 |
| `GET /bot/v1/actions` | 待处理事项与待推送提醒 | 按责任关系过滤 |
| `POST /bot/v1/submissions` | 提交成果链接 | 幂等键、对象权限、版本校验 |
| `POST /bot/v1/decisions` | 写入授权范围内的评审或处理决定 | 评审权限、状态冲突校验 |
| `POST /bot/v1/receipts` | 写回消息送达回执 | 来源鉴权与去重 |

- 另有写入：周报、轻测成绩（含未答）、入库的 FAQ（必须带产出留痕，缺执行方拒收，见 15.5）。
- **授权：** 不只靠一把全权限密钥；按调用方、成员身份、对象权限和功能范围在服务端执行。密钥在管理区「AI 与接入」签发、吊销（15.2）。
- **可靠性：** 重复写入用请求幂等键；业务状态已经变化时返回明确冲突，不默默覆盖；执行结果不明时先查原请求结果，不盲目重放。
- **过渡切换（沿用）：** 从多维表格 `project_base` 一次性导入历史数据（项目、任务、成员；项目映射为 `project`，任务映射为节点或培养任务，映射规则导入前定）→ 机器人逐个功能切到工作台接口 → 到期后多维表格只读归档。全程不做双向同步。

## 15. AI 接入

依据全局规则 P-13（常浩 2026-11-07 定）：应用里凡是 AI 产出的东西，都要能在设置里看清谁做的、怎么接进来的、读了什么数据、写到了哪里；换一家时改设置就行，不改代码。本节与 `AGENTS.md`「AI 接入」一节内容一致，改一处要同步另一处。

用词：**执行方** = 真正产出内容的 AI（Claude、Codex、Hermes 等）；**接入方式**只有五种：本机 CLI、官方 API、网页桥、Hermes 派单、MCP 开放；**数据对象** = 应用只展示或采集、不是 AI 替应用产出的东西。

### 15.1 现状：工作台本身不调用 AI

- 各阶段规划的功能里，**工作台自己不调用任何 AI**。名字带「AI」的功能都是人工内容或规则（见 15.3）。
- 会写进工作台的 AI 产出只有一处：带教机器人在飞书里生成、带教审核后写入的 **FAQ 答案**（阶段 3）。AI 调用发生在机器人里，执行方也在机器人项目里切换；工作台只负责要求留痕、把留痕显示出来。
- 外部连进来的只有带教机器人接口（第 14 节）。它是普通 HTTP 接口，不是 MCP；归在「对外开放」一块。
- 以后接入的企业带教 Agent（1.3）属于新加 AI 功能，按 15.4 执行；应使用企业侧独立的权限和业务数据，不混入个人数字分身项目的运行体系。

### 15.2 设置页「AI 与接入」

- 位置：管理区，只有管理者能进；**合并原规划的「机器人接口密钥」页**，随机器人接口上线（阶段 2）。
- 四块：
  1. **默认执行方**：写明「本应用当前不调用 AI」，不放切换按钮（不能假装能切）。列出以后接入时支持的执行方（Claude、Codex），状态都是「未启用」。第一次加 AI 功能时，这一块改为可切换，并照 15.4 执行。
  2. **功能清单**：每个带「AI」字样或用到 AI 产出的功能一行：功能名｜实际是什么｜执行方｜接入方式｜读哪些数据｜产出写到哪里｜谁能看到｜阶段。内容见 15.3。
  3. **对外开放**：每个接入方一行：对谁开放、能读什么、能写什么、密钥状态（只显示「已配置 / 未配置」）、签发时间、最近调用时间、在哪关掉（「吊销」按钮，吊销后立即失效）。新签发的密钥只在签发当下显示一次。
  4. **数据对象**：AI 资产库、Tidings 入口，写明来源、是否由 AI 产出，不放进可切换项。
- 自检：不读代码，只看本页，能答出每个功能「谁做、怎么接、读什么、写到哪、现在能不能用」。

### 15.3 功能清单与数据对象（初始内容）

| 功能 | 阶段 | 实际是什么 | 执行方 | 接入方式 | 读哪些数据 | 产出写到哪里 | 谁能看到 |
|---|---|---|---|---|---|---|---|
| 这一步可以用 · 推荐 AI 资产（项目详情、任务详情） | 3 | 规则：取节点或任务挂的推荐资产；没有时取同类项目用过的；再没有时取使用人数最多的上架资产 | 无，不调用 AI | 无 | 推荐资产、项目类型、资产使用记录 | 只在页面上显示，不存 | 本人 |
| FAQ 答案 | 3 | 机器人在飞书里回答提问，带教审核后经接口入库 | 带教机器人里的 AI（机器人待定，见第 18 节；在机器人项目里切换，本页不可切） | 对外开放：机器人凭接口密钥写入 | 由机器人决定，工作台不向它提供生成用的数据 | `faq`，每条带产出留痕 | 全员 |
| 资料卡片摘要 | 3 | 同步时截取飞书文档开头一段，管理者可人工改写 | 无，不调用 AI | 无 | 飞书文档 | `resource_card` 摘要字段 | 全员 |
| 轻测 | 2 | 题目留在机器人里（是否由 AI 出题由机器人项目定），工作台只存成绩 | 无（工作台一侧） | 对外开放：机器人写成绩 | 无 | `quiz_result` | 本人、带过的带教、管理者（2.4） |

| 数据对象 | 来源 | 是否 AI 产出 |
|---|---|---|
| AI 资产库（Skill、Prompt、工作流/SOP、用例） | 人工贡献、管理者审核（第 11 节） | 否，讲 AI 的内容 |
| Tidings 入口 | 外部站点，只跳转，不取数据 | 否 |

### 15.4 第一次加 AI 功能时（规则，不在当前规划范围）

- 新的 AI 功能默认同时支持 Claude 和 Codex；做不到的，在功能清单里标「仅支持 X」并写一句原因。
- 工作台部署在公司服务器，接入方式按官方 API（API Key）考虑；本机 CLI 只适合开发期（推断，服务器环境待定，见第 18 节）。
- 切换在下一次调用生效；已经在跑的任务按原执行方跑完。必须重启才生效的，在设置页写明。
- 选定的执行方不可用时，明确报错并指向设置页，不自动换成另一家。
- 每条 AI 产出留痕：执行方、接入方式、模型（拿得到时）、时间，在界面上看得到。
- 同时改本节、`AGENTS.md`「AI 接入」一节和设置页。

### 15.5 留痕与对外开放的要求（随机器人接口起）

- 机器人写入 AI 产出（FAQ 答案）时，必须带执行方、接入方式、模型（拿得到时）、生成时间、审核人；**缺执行方的，接口拒收**。FAQ 页每条显示「由 X 生成 · 某某审核」。
- 接口密钥只存哈希；页面只显示「已配置 / 未配置」，不明文显示，不进仓库。
- 权限范围按第 14 节的读写清单逐项勾选；越权调用返回错误，并记进事件日志。

## 16. 技术方案

- 自己开发网站：前端 React + Vite，后端 Node（TypeScript），数据库 PostgreSQL，用 Docker Compose 打包。开发期在本机运行（只监听 127.0.0.1）；上线部署到公司服务器（环境待定）。
- 只做电脑版（≥1280px）。
- 页面时间统一按北京时间格式化显示；工作日推算只在服务端做。
- **对 v1.1 技术决策的复核：**

| 决策 | 结论 | 修正 |
|---|---|---|
| 事件日志只追加 | 保留 | 作为审计与投影来源，不替代业务对象的当前状态 |
| 待办由事件驱动 | 保留并修正 | 事件即时触发 + 定时扫描时间条件；事务一致，外发走 outbox |
| 工作日推算 | 保留 | 统一由服务端计算，记录日历版本和截止调整历史 |
| 日程不单独建表 | 保留 | 查询视图可缓存，但不维护第二套业务事实 |
| 权限服务端执行 | 保留 | 角色 + 具体资源关系（带教关系、项目成员）+ 时间范围 + 最小授权 |
| 机器人通过接口接入 | 保留 | 是可替换的外部通道，不是基本闭环的单点依赖 |
| 模板版本冻结 | 保留 | 新旧版本必须可追溯；调整不覆盖历史 |
| 所有能力一开始完整实现 | 不采用 | 只建必要的扩展点，不提前实现全部复杂规则 |

### 17.1 阶段 1 验收：用一次真实业务实践证明，不用页面数和测试数

用现有两名管培生和一位带教验证，以下八项全部通过：

1. 能创建真实业务项目，明确目标、责任人和关键节点的验收标准。
2. 能把培养任务关联到实际项目，同一份成果不需要重复提交。
3. 管培生提交成果后，带教能看到上下文（目标、上次反馈、修改说明）并给出有效反馈。
4. 反馈能转化为下一步行动，修订后的成果可以再次验收。
5. 项目状态、培养任务状态和成长档案之间没有相互矛盾。
6. 至少一次阶段复盘能依据真实产出形成能力判断。
7. 已有成果能被提炼成能力证据并关联来源。
8. 带教机器人没接入时，核心闭环也能独立运行。

**观察项：** 用户为维护系统额外付出的工作量。如果推进一个节点要在飞书写一次、工作台录一次、再向带教发一次消息，就说明违反了 1.4，需要改。

## 附录 A：视觉规范（V3 柔光）

2026-11-06 常浩从六个候选（V1 精工、V2 曜石、V3 柔光、V4 雾光、V5 素白、V6 色块）中选定 **V3 柔光**，取代 v1.0 的「01 器」。来源：[docs/research/2026-11-06-structure/design/v3-home.html](research/2026-11-06-structure/design/v3-home.html)、`v3-cal.html`；实现以 `web/src/styles/app.css` 的 token 为准，组件用法见 `web/src/components/README.md`，示例页 `/dev/kit`。新页面一律沿用。

### A.1 结构与层次

- 外壳：左侧玻璃侧栏（216px，sticky）+ 右侧主区，四周留 12px；顶栏在主区内：面包屑、演示视角、**日程**、**待办**（带计数）、通知、主按钮。
- 层次三层：**雾蓝底 → 半透明磨砂面（卡片）→ 卡内浅白块或凹槽**。面靠 1px 极淡描边、顶边内高光和柔软大半径阴影区分，不用粗边框。
- 内容用 Bento 式网格，模块大小有节奏：焦点和日程用大块，指标和列表用小块；一屏一个焦点。
- 全屏唯一强调块：深墨色「这一步可以用」（推荐 AI 资产）。

### A.2 色板

| 用途 | 值 |
|---|---|
| 底色 | `#ECEFF4` |
| 面 / 高亮面 | `rgba(255,255,255,.72)` / `.9`，配背景模糊 |
| 正文三级 + 最淡 | `#151926`、`#363C4E`、`#5A6175`、`#8A90A0` |
| 描边 | `rgba(21,25,38,.07)`、`.11` |
| 强调（主按钮、当前项、链接） | `#4A4ED8`，浅底 `#E7E8FC`，深字 `#3438B8` |
| 强调块 | `#1A1D2C` |
| 领域色（主色 / 浅底 / 深字） | 成长 `#2E9E68`；带教与日程 `#3C8BDB`；团队活动 `#8A68DE`；考核 `#EC7656`；AI `#E0A436`；周期例行 `#7A869C`（浅底、深字见 app.css） |
| 语义：通过 / 提醒 / 逾期 / 信息 | 成长绿 / `#D08A12` / `#E5484D` / 带教蓝 |

- 领域色只用于小面积：图标底、标签、日程事件块、进度端点；文字一律用同色系深字或墨色，保证对比度 ≥ 4.5:1。
- 状态只用语义色；强调色只用于当前项、链接和主操作。首页与日程的事件类型配色必须一致。

### A.3 字体

- 中文：苹方回落（`PingFang SC`、`Noto Sans SC`、`Hiragino Sans GB`、`Microsoft YaHei`）。
- 西文：Geist Sans；**数字：Manrope**（倒计时、指标、日期大字）；代码与安装指令：Geist Mono。不混用其他字体。
- 全部自托管（`web/src/styles/fonts.css`），`@font-face` 必须限定 latin 的 `unicode-range`，否则会挤坏中文全角标点（docs/LESSONS.md L-01）。
- 字号刻度：11 / 12 / 13 / 14.5 / 19 / 24 / 30px；页面标题 30px 细字重加强调色关键词；数字列 `tabular-nums`。

### A.4 组件与动效

- 圆角：面 22–24px，卡内块 12–16px，按钮 9–12px，胶囊全圆角。
- 通用组件：状态胶囊、领域标签、进度环（粗环、渐变端点、可标「按计划」刻度）、阶段条、轮岗站圆点链、竖向日程时间轴、迷你月历、周视图网格、甘特条、右侧抽屉、指标卡、空状态。
- 周视图：工作日列与周末列宽比约 1.25 : 0.6，事件标题换行显示、不截断；当前时间线用强调色；选中项柔和外发光。
- 多人视图和甘特格内的标签放不下时换行，不用省略号截断。
- 动效只用 0.2s 左右的颜色、阴影、位移过渡；不做入场动画；尊重「减少动态效果」设置。
- 只做电脑版（≥1280px）。
