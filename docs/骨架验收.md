# 骨架验收（v2.0 骨架版）

依据 [PRD](PRD.md) 上篇（命令见第 4 节、数据见第 13 节、页面级别见第 10 节）与[页面清单](页面清单.md)。本文有三部分：验收矩阵（第 1 节），用来查对象、命令、页面三者是否连通；八项骨架验收（第 2 节），在骨架做完、第二轮开始前验证；第 1 步的纸面走查记录（第 3 节）。

## 2. 八项骨架验收

骨架做完（第 3 步结束）、第二轮开始前逐项验证。第 2 步把其中与后端有关的部分写成自动化测试（标「自动」），第 3 步在浏览器里走一遍（标「界面」）。

| # | 验收项 | 具体怎么验 | 方式 |
|---|---|---|---|
| 1 | 项目与成果闭环 | 立项 → 新建里程碑 → 提交 V1 → 评审需改进（含「修改再交」行动）→ 提交 V2（行动自动完成）→ 评审通过 → 填写结论 → 结项；每一步的状态都与 PRD 4.3 一致 | 自动 + 界面 |
| 2 | 成果复用 | 里程碑关联两位管培生各自的培养任务；V2 通过时逐条认定，两位的任务各有一条认定记录并变为已通过；没被勾选的任务不变；任何时候都没有第二份成果 | 自动 + 界面 |
| 3 | 带教责任 | 按 PRD 2.4 的顺序推出评审负责人（项目范围 → 主责的默认带教 → 管理者；任务按站范围 → 默认带教 → 管理者）；提交后更换带教关系，已提交的快照不变 | 自动 |
| 4 | 受阻状态 | 标记受阻 → 响应（仍受阻、待办里「受阻待响应」消失）→ 解除；三件事在受阻记录里分开可查 | 自动 + 界面 |
| 5 | 业务结果 | 结项时交付结论 = 达成、验证状态 = 未验证；结项后用 C19 补记为已验证；两次的值和补记人都可查 | 自动 + 界面 |
| 6 | 能力证据 | 从已评审的成果提炼证据，成长档案按能力项列出，并能点回来源里程碑和版本 | 自动 + 界面 |
| 7 | 跨页面一致 | 每条命令执行后，按 1.1「哪些页面要跟着变」核对首页、待办、项目详情、成长档案没有矛盾 | 界面 |
| 8 | 演示数据隔离 | 演示模式只在 127.0.0.1 上能开；关掉演示模式后，未认证的请求拿不到任何业务数据；初始化脚本在非演示模式下拒绝运行 | 自动 |

另外，每条命令的前置条件（PRD 4.5）各有至少一个反例测试：不满足时被拒绝，状态不变，不写事件。

## 3. 第 1 步纸面走查记录（2026-11-08，Claude）

用两个虚构项目，按第 2 节八项走 PRD 上篇的命令和数据模型，找结构冲突。示例数据都是虚构的。

**设定：** 管培生甲、乙；带教 A（有管理权限，是甲、乙的默认带教）；带教 B（乙在「销售」站的站带教，也是乙在项目二的项目范围带教）。项目一「来电归因优化」：主责甲、参与乙，没有项目范围带教；里程碑 N1「问题定义」关联甲的任务 K甲 和乙的任务 K乙（都设「在项目中完成」）。项目二「渠道转化复盘」：主责乙；里程碑 N2。

| # | 走查过程 | 发现 | 处理 |
|---|---|---|---|
| 1 | 项目一：C01（甲）→ C02（A）→ C03 N1 → C04 → C06 V1，评审负责人推出 A → C08 需改进 → C07 V2 → C08 通过 → C14 → C15 | ①没写清 C06 能在哪些状态下提交、里程碑待评审时能不能再交、项目草拟时能不能交；②「修改再交」行动的负责人没定（提交人还是主责） | ①PRD 新增 4.5 最小写入约束；②7.3 写明默认负责人：「修改再交」= 该版本提交人 |
| 2 | V2 通过时 A 对 K甲、K乙 逐条认定 | ③需改进的评审里能否认定、同一任务能否重复认定，没写 | ③3.3 加：认定只在通过的评审里出现；同一任务最多一条已认定记录 |
| 3 | 项目二的里程碑成果：评审负责人应为 B。原文「该项目范围的带教关系」在多人项目里可能有多条，取哪一条不明（GPT 注意事项 B） | ④推导依据不唯一 | ④2.4 改为「项目主责管培生在该项目范围的带教关系」，项目详情显示的项目带教也按这条推 |
| 4 | N2 标记受阻 → B 响应 → 乙解除 | ⑤受阻记录的「当前处理责任人」默认是谁没写 | ⑤5.2 写明默认是项目带教，可改；未解除的受阻每个里程碑最多一条（4.5） |
| 5 | 项目二结项：交付达成、业务未验证；三周后业务部门反馈有效 | ⑥结项后没有命令能补记业务验证，只能停在「未验证」，和真实情况不符（业务效果常在交付后才出来） | ⑥新增 C19「补记业务验证」，结项后可用，记补记人和时间 |
| 6 | 从项目一 V2 的评审为甲、乙各提炼一条证据 | ⑦乙不是 V2 的提交人，能否用它作证据来源没写 | ⑦8.2 写明：来源必须与这位管培生有关（本人成果、对本人成果的评审、本人参与项目里的成果与评审），多人项目分别提炼 |
| 7 | C08 通过后看乙的成长档案 | ⑧「通过的成果」只按提交人算的话，乙看不到项目一的成果；⑨乙的成长时间线里没有项目一的事件（事件「所属管培生」只能填一人） | ⑧8.4 定口径：本人提交且通过的版本 + 对本人任务的认定记录；⑨`event_log` 加「所属项目」，时间线包含本人参与项目的项目事件 |
| 8 | 关掉演示模式后跑初始化脚本 | ⑩脚本可能把示例数据写进正式库 | ⑩4.1 写明：初始化脚本只在演示模式下能运行 |

**结论：** 走查发现 10 处契约缺口（②⑤ 合为一项「默认负责人」），归并为 9 项改动，都已改进 PRD 上篇（修订记录第 8 条）。表结构上只多了 `event_log` 的「所属项目」字段和一条命令 C19，没有发现需要推翻对象模型的冲突。八项验收在纸面上都能走通。

**纸面走查管不到的：** 页面信息组织是否顺手（第 3 步挑版和实测）；性能与并发（两人规模不是问题）；时间、权限、提醒（第二轮）。
