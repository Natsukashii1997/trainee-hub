## 0. 一页结论

1. **方向成立：TraineeOS 做成带教杠杆系统。** 带教只有一人、管培生会增加，系统要让有限的带教注意力用在真正产生培养价值的地方。杠杆不是让每个人得到更少的带教，而是减少重复解释、找上下文、整理材料、追后续行动这些损耗。
2. **眼下最大的风险不是缺功能，是没有真人用过。** 四版 PRD、19 条已建成的后端命令、零真实使用。所以下一步不是再建一套大功能，而是让现有两名管培生跑通一条真实的链：**任务与标准 → 提交成果 → 带教反馈 → 再次验证**。
3. **哪个环节最耗带教，现在并不知道。** 可能是任务不够清楚、标准没讲、成果积压，也可能是反馈说了没被吸收。所以反馈模式库、自检、AI 预审、信任地图都先当作假设，用两周试运行的证据决定做哪个。
4. **v2.1 的地基保留**：对象、业务命令、状态边界、事件日志、已建成的后端都不拆。第一阶段主要用已经建好的项目与里程碑这条链，新增的东西很少。
5. **四个阶段**：一 真实闭环可用 → 二 验证并减少重复工作（含界面上加人）→ 三 支持阶段性的人才判断 → 四 人多之后的带教效率。
6. 推进方式：**按页面推进**，一页一页做，每页单独给常浩看、确认后再做下一页（12.2）。
7. 还缺常浩提供的三样信息，见第 14 节 D–F。

## 1. 问题重述

### 1.1 三个目标，相互关联但不能互相替代

| 目标 | 要回答的问题 | 现在知道多少 |
|---|---|---|
| 培养有效 | 管培生有没有通过真实业务实践，形成可以迁移、可以独立运用的能力 | 目标成立，怎么实现没有验证 |
| 带教高效 | 哪些事消耗带教的注意力，却没有产生相应的培养价值 | 有合理怀疑，损耗在哪不知道 |
| 评估可信 | 去留、定岗、放手让他独立做，这些判断有没有充分、可追溯的证据 | 需求明确，证据链不完整 |

带教用时降了，不等于培养效果好了；评审记录多了，不等于判断更准；能力模型标准了，不等于人更快独立。

**要解决的问题**（按评审意见重写）：

> TraineeOS 能不能把真实业务实践里的任务要求、过程观察、带教反馈、再次实践和能力判断连起来，在不降低培养质量的前提下减少重复协调和信息损耗，让一位带教能持续带更多人，并让关键的人才决定有可信的证据。

### 1.2 把手段当成目标的地方

1. **把「过程可见」当成「人会成长」。** 《TraineeOS》原文的六个「有」（有路径、有计划、有规范、有回应、有记录、有沉淀）是管理上的好处，不直接带来成长。
2. **把「功能全」当成「有价值」。** 2026-11-06 到 11-14 的 9 天里 PRD 出了 4 版，真实使用为零。本文的初稿也犯了同一个错：把还没验证的推断（反馈在重复、判断量是瓶颈）直接做成了一组功能。
3. **把「酷」当成模块数量。** 让人觉得厉害的应该是几个别处没有的时刻（2.4）。
4. **「管培生会加，要能操作」只说了一半。** 加人的界面必须有（6.5），但随人数增长的是带教的工作量；后者不解决，加人越方便带教越被压垮。

### 1.3 带教的损耗可能在四个地方

| 可能的瓶颈 | 表现 | 系统能改变什么 |
|---|---|---|
| 任务供给 | 没有足够多难度合适、有业务价值的任务 | 任务设计与匹配（主要靠培养方案，系统只能辅助） |
| 认知 | 不知道标准、没见过好的样子，反复做错 | 任务标准、样例、提交前自检、反馈复用 |
| 判断 | 成果积压，带教来不及看 | 集中待办、预先整理、分流 |
| 反馈转化 | 点评过了，但没有进入下一次实践 | 反馈留痕、下一步行动、后续验证 |

现有事实能支持的只有两点：反馈大量发生在口头点评和答辩里，原来的评审只有一段文字，**反馈转化这一环有明显的流失风险**；一位带教随人数增加**必然有容量上限**。但没有证据说明将来最耗时间的是评审、答疑、协调还是任务设计。

所以先验证反馈闭环和无价值的时间损耗，再决定要不要大规模建设评审分流。

### 1.4 四个关键假设

| 假设 | 现在的状态 | 什么时候验证 |
|---|---|---|
| H1 核心损耗在反馈没有转化成后续行动 | 有合理依据，影响多大未验证 | 第一阶段 |
| H2 任务标准前置和反馈复用能减少重复工作 | 未验证 | 第一、二阶段 |
| H3 带教的判断处理量会成为主要容量瓶颈 | 将来的风险明确，现在的瓶颈没定位 | 人数增加或出现积压时 |
| H4 按具体活动积累的证据，比抽象能力评分更适合做人才判断 | 方向合理，要结合岗位验证 | 第一阶段开始积累，第三阶段检验 |

H2 不成立不影响 H1；H3 暂时不成立也不影响先把培养闭环建好。方向可以成立，而其中某些杠杆最后可以不做。

## 2. 定位与指标

### 2.1 定位

**TraineeOS 是以真实业务实践为基础的管培生培养与带教杠杆系统：把任务标准讲清楚，让反馈落到下一次实践，把有效的经验复用起来，积累成长证据；在不降低培养质量的前提下，让一位带教带得动更多人，并让关键的人才判断有依据。**

和 v2.1 的关系：v2.1 的定位（业务实践驱动的成长与带教协同）和三条线继续成立；v3.0 明确了约束（单带教、会扩员）和先后顺序（先让一条链真实运行）。

### 2.2 不是什么

- 不是课程平台、绩效系统、项目管理器、办公套件（沿用 v2.1 的 1.3）。
- 不是知识库：标准和问答只在用得上的那一步出现。
- 不给人打一个总分；不拿完成次数、活跃度、签到、聊天次数、上传数量、使用时长当成能力结论或培养成效（沿用）。

### 2.3 指标：先不设北极星

两名管培生、路线不同、没有真实运行数据，现在定不出哪个数最能代表价值。先看一组验证指标，试运行第一周记基线。

| 维度 | 先看这个 | 不要过早优化这个 |
|---|---|---|
| 培养效果 | 关键反馈在后续实践里有没有得到验证（改善了多少条、仍存在多少条） | 首次通过率（任务变简单了它也会升） |
| 带教效率 | 带教每周的带教时间和构成（准备、阅读、判断、沟通、记录），试运行期间由带教粗略记 | 单次评审的处理速度 |
| 反馈及时 | 从提交到拿到可执行反馈的等待时间 | AI 草稿出得多快 |
| 人才判断 | 重要评价有没有可追溯的实例支撑 | 信任等级的平均值 |
| 真实使用 | 完成了几次真实的任务闭环；有没有出现两边重复记录 | 登录量、页面浏览量 |

带教用时只在培养效果不下降的前提下才算改善，不单独作为优化目标。

### 2.4 让人觉得厉害的时刻

「酷」落在下面几处，其余界面只求干净、快。按阶段出现：

1. **「上次说的，这次改了吗」（第一阶段）：** 带教打开一份成果，旁边就是这个人上次被指出、约定这次要验证的几条反馈，勾一下就记下「已改善」或「仍存在」。管培生提交前也看得到这几条。
2. **待我判断清零（第一阶段）：** 带教首页只有必须由他判断的事，每项都带好上下文，处理完就是空的。
3. **评估材料一键成稿（第三阶段）：** 到评估点，系统把带教选定的代表性证据拼成一页，改完就能拿给上级。
4. **独立性地图（第三阶段）：** 每位管培生一张图，按具体活动显示「证据不足、需指导完成、可独立完成」，点一格看证据链。

## 3. 设计原则

1. **先跑通一条真实的链，再加杠杆。** 没有真实使用证据的机制只算假设，不提前做成功能。
2. **带教的注意力是预算，但省的是损耗，不是深度。** 减少找上下文、重复解释、整理材料、追后续；不预设要减少深度点评、关键讨论和必要的一对一。
3. **只有必须由带教判断的事才摆到带教面前。** 影响业务推进、放手程度或重要评价的才是显式的判断任务；辅助性的草稿和建议不生成要处理的卡片。系统里的每一次人工确认都有成本。
4. **只有带教的判断改变状态。** 自检、预审、AI 草稿、同伴意见都是参考（沿用 v2.1 的 4.4）。
5. **反馈说一次就够，并且要有下文。** 带教在哪里给的反馈（评审、会上、日志批注、答疑），就从哪里收进来；值得跟的反馈要在下一次实践里被验证。
6. **任务开始前把标准讲清楚。** 为什么做、交付什么、怎样算好、常见失误、什么情况要及时找带教。这一步不依赖任何未验证的假设。
7. **发展性反馈和阶段性评估分开。** 平时的反馈用来帮人改进，允许试错和暴露困难；阶段性评估只用带教挑选的代表性证据，考虑任务难度、指导程度、前后变化和稳定性，不把过程记录累加成一个分数。管培生可以为评估补充自己的说明和证据。
8. **判断要落在「能不能放手」上，并且从第一天就留证据。** 证据链（任务 → 原始成果 → 判断与依据 → 改进行动 → 后续表现）第一阶段就要完整；评级和地图可以晚做。
9. **一次事实输入，多处派生**（沿用 v2.1 的 1.4）。
10. **用不上的不出现。** 只有一位带教时，交接、改派、多评委的界面都不出现；数据结构保留。

## 4. 角色

| 谁 | 进不进系统 | 做什么 |
|---|---|---|
| 管培生 | 进 | 看任务和标准，提交成果，处理下一步行动，标记受阻，看自己的反馈；评估时补充说明和证据 |
| 带教（现在只有常浩，同时有管理权限） | 进 | 写任务标准，评审，记录反馈并验证，响应受阻；以后加人、排期、做评估决定 |
| 亚古兽（企业带教 Agent） | 经接口，第二阶段起按需接入 | 写入草稿（答疑答案、预审意见、会议纪要里的反馈），带教确认后才生效（第 9 节） |
| 业务带教（各岗位带人的同事） | 不进 | 只记名字 |
| 上级 | 不进 | 看带教导出的评估材料（第三阶段） |

- 角色仍是 v2.1 的两种（管培生、带教）加管理权限字段，不新增角色。
- 带教关系的数据结构保留；只有一位带教时，每位成员默认与这位带教建立全程关系，界面不显示「主带教、业务带教、项目带教」的区分。

## 5. 主链与候选杠杆

```
第一阶段要跑通的主链

  任务与标准 ──► 提交成果 ──► 带教反馈 ──► 再次验证
  （为什么做、     （真实成果     （结论、逐条     （修改再交，或下一个
    交付什么、       和必要的       反馈、下一步、    任务里检查上次的
    怎样算好、       上下文）       哪几条下次要     问题有没有改）
    常见失误）                      验证）
        ▲                                               │
        └────── 口头点评经一个轻量入口记进来 ◄────────────┘

  全程留证据：任务 → 原始成果 → 判断与依据 → 改进行动 → 后续表现


第二阶段以后，按证据加的杠杆（都是候选）

  同类问题反复出现 ──► 提交前自检 / 标准卡 / 反馈复用
  带教准备材料耗时 ──► Agent 预先整理、预审
  口头反馈记不过来 ──► 会议纪要回流
  判断事项积压     ──► 分流、同伴预审
```

主链的后半段（提交、评审、下一步行动、修改再交）v2.1 已经建成；第一阶段要补的是前面的任务标准、反馈按条记录与验证、口头反馈的入口。

## 6. 功能

每一块都标了阶段。第一阶段的内容是定稿后的实现依据；第二阶段以后的内容是方向，做之前按试运行证据再定细节。

### 6.1 任务与标准（第一阶段）

- 每个里程碑（以及以后的培养节点）开始前，写清五件事：为什么做；交付什么；怎样算好（验收标准）；常见失误；什么情况要及时找带教。可以附一两个样例链接。
- 由带教写，或管培生起草、带教确认。v2.1 的里程碑已经有目标和验收标准两个字段，这里加常见失误、升级条件、样例链接三个。
- 管培生在任务详情和提交页都看得到标准。
- 不建课程库、知识库或成套的 SOP，只为真实发生的任务逐个沉淀。

### 6.2 反馈闭环（第一阶段）

**评审时反馈按条记（C08 扩展）**

- 结论、下一步行动、认定沿用 v2.1 的 7.2、7.3。
- 新增：反馈分条写。每条可以勾「下次验证」，表示带教想在这个人之后的成果里看它有没有改；可以写一两个自由标签（如「结论先行」「证据来源」），不要求选自预设的模式库；可以选一个性质（可空）：

| 性质 | 例子 | 以后适合怎么处理 |
|---|---|---|
| 通用标准问题 | 报告没有写证据来源 | 写进任务标准或提交前检查 |
| 个人发展问题 | 这个人反复分不清事实和推断 | 作为他的发展重点，安排再练 |
| 情境性判断 | 方案有道理，但忽略了这块业务的特殊约束 | 留作案例，不急着标准化 |

**再次验证（C40，新）**

- 带教评审某人的下一份成果时，旁边列出这个人所有「下次验证」且尚未验证的反馈。每条选「已改善」「仍存在」或「这次没涉及」，系统记下是在哪份成果上验证的。
- 管培生的首页和提交页也显示这些待验证的反馈，最多 3 条。
- 「仍存在」的反馈保留在待验证里；连续出现由带教决定是否当面谈，系统不自动升级。

**口头反馈的轻量入口（C29，新）**

- 带教在任何页面都能记一条：选人，写一句，可选关联到某个里程碑或成果，可选「下次验证」。目标是 30 秒内记完。
- 用于会上、答辩、一对一里说过的话。第一阶段只做手记；从会议纪要自动提炼属于第二阶段的候选。

**最小证据链**

- 第一阶段必须能从任何一条评价追溯到：是哪个任务、哪一版成果、带教当时的判断和依据、之后的行动、后面的表现。成果版本、评审、下一步行动、修改再交的关联 v2.1 已有；本阶段补上反馈条目和验证记录。

### 6.3 带教首页：待我判断（第一阶段）

- 只放必须由带教判断、否则别人没法往下走的事：待评审的成果、受阻待响应、待确认立项。按已等待的工作日从长到短排。
- 每项带好上下文：任务标准、与上一版相比的修改说明、这个人待验证的反馈。带教不用翻别的页面。
- 多数事项就地处理。
- 第二个视图「我带的人」：每人一行，当前在做什么、等带教的事项数、最近一次反馈、待验证的反馈数。
- **不进这个列表的**：AI 草稿、归并建议、等级建议这类辅助内容。它们以后出现在相关对象的旁边，带教用得上时看，不用时不需要处理，也不产生未读数。
- 待办仍然是对事实对象的查询，不建待办表（沿用 v2.1 第 11 节）。

### 6.4 管培生首页（第一阶段）

只回答三件事：

1. **现在最该做的一件事：** 未完成的下一步行动；没有时是当前的里程碑。
2. **这次要改的：** 待验证的反馈，最多 3 条。
3. **在等带教的：** 已提交等评审的成果、未响应的受阻，各等了多久。

版式（常浩 2026-11-18 选 A 版「原位替换」，见页面清单第 5 行）：第 1 件事放深色「下一步」卡；第 2、3 件事合在「带教点评」卡里，左边在等带教的、右边这次要改的。同一天常浩定：A 版里的本周、进度、资料、团队动态、AI 发现五张卡第一阶段**也保留**，作为这三件事之外的辅助信息，不改变上面三件事的口径；其中还没有数据来源的卡先显示示例或空状态。

### 6.5 加人与路径（第二阶段；硬期限是第三人入职之前）

你明确要求界面上能操作。它不进第一阶段的验收，是因为现有两个人走项目这条链不需要它；但它是第二阶段的第一项，并且**不论阶段进行到哪里，都必须在第三个人入职前可用**（常浩 2026-11-18 确认，第 14 节 C）。

- **加入成员并生成路径（C27）：** 填姓名与飞书账号、入职日、路径模板版本、走哪几条线、批次标签（可空）；带教默认是当前唯一的带教。按工作日日历排出各培养节点的计划起止，先预览、确认后生成。目标 3 分钟内加完一个人。
- **滚动入职：** 每个人按自己的入职日排期。「期次」从必填对象降为可选的批次标签。
- **调整安排（C20）、评审方式与带教确认完成（C21、C22）：** 沿用 v2.1 的设计。
- **增删个人培养节点（C28，新）：** 给某个人加一个模板里没有的节点，或移除一个未开始的节点，写原因并留痕。
- **结束培养（C39，新）：** 把个人路径标为结束，未开始的节点撤销，档案保留。
- **路径模板维护：** 能导入 V2.4 并在界面上修改、另存新版本；不做拖拽编排。
- 现有两个人的路径和历史评审记录，在这一阶段从旧工具导入。

### 6.6 减少重复工作的候选（第二阶段，按试运行证据选）

下面每一项都是假设，后面写的是「看到什么证据才做」。

| 候选 | 做什么 | 看到什么才做 |
|---|---|---|
| 提交前自检 | 提交时列出这类任务的自检项（每类不超过 7 条），逐项勾选 | 试运行里出现了多条「通用标准问题」，而且写进任务标准后仍被忽略 |
| 反馈复用（模式库） | 把自由标签归并成反馈模式；带教决定哪些升成标准或自检项 | 标签在不同人、不同任务之间确实重复出现。出现次数只是提醒，是否升成标准看四点：问题能不能清楚识别、标准能不能有效预防、别的任务用不用得上、维护成本合不合理 |
| 标准卡 | 一张卡讲清一件事怎样算做好（标准、正例、反例、常见错误），在任务详情里按需出现 | 同一段解释带教对不同的人讲了不止一次 |
| Agent 预先整理与预审 | 亚古兽在带教评审前整理要点，或按固定三问给预审意见，附在成果旁，不改状态 | 带教的时间记录显示准备和阅读占了大头；试用后带教的净工作量确实下降 |
| 会议纪要回流 | 亚古兽从纪要里提炼反馈草稿，带教挑着确认 | 手记入口用起来仍然漏掉大量口头反馈 |
| 答疑记录与 Q&A 合集 | 沿用 v2.1（C23–C26）；亚古兽回答前先查已审核的答案 | 决定把答疑从旧工具切过来时 |

### 6.7 可托付活动与独立性判断（第三阶段；证据从第一阶段开始积累）

- **方向：** 不评抽象的能力分，看一个人能不能独立完成一件具体的工作。
- **活动清单从少量开始：** 几项各条线通用的活动，加每条线自己的岗位活动；不一次定死九项。初稿里的九项只作为候选，到第三阶段由常浩结合实际岗位挑和改（常浩 2026-11-18 确认，第 14 节 A）。
- **判断分三个互不混淆的东西**（取代初稿的五级）：

| 是什么 | 取值 | 说明 |
|---|---|---|
| 观察状态 | 证据不足 | 只说明还没看到足够的实例，不代表能力低 |
| 实践状态 | 需指导完成 / 可独立完成 | 「可独立完成」要写明适用的任务情境，一次低难度任务的完成不能无限推广 |
| 进阶属性 | 可指导他人 | 只在这个人实际承担了带人的事时才用，不是比「独立完成」更高的一级 |

  这和 v2.1 的三级判断（尚未观察到充分证据、有指导下完成、可独立完成）基本一致；变化是把证据绑到具体活动上、加上适用情境、加一个独立的「可指导他人」。

- **证据：** 每项活动的判断都能追溯到代表性成果、实际观察和必要的重做记录。
- 等级只由带教确认，系统不自动计算（沿用 v2.1 的 8.2）。地图式的呈现在这一阶段做。

### 6.8 评估点与决定（第三阶段）

- **评估点：** 属于一位管培生，有类型（阶段评估、去留评估、定岗评估、答辩）和计划日期。
- **材料包由带教挑选，不是全量汇总：** 带教从通过的成果、反馈及其验证结果、项目与业务验证、打分的评审点里，选出有代表性的证据；系统帮忙列出候选并标出任务难度、当时的指导程度、前后变化。不生成总分。
- **管培生可以补充：** 自评，以及自己认为该被看到的证据和说明。
- **决定：** 继续培养、限期复核（写日期和复核内容）、停止、定岗（写去向）；理由必填。
- **导出：** 一页可打印的页面给上级，不为上级开账号。
- **可见性：** 决定的结论对本人可见，理由由带教逐次选择是否可见（你 11-18 已按推荐确认）。
- v2.1 的阶段复盘并入评估点。

### 6.9 项目与里程碑、答疑

- 项目与里程碑整体沿用 v2.1 第 5 节，是第一阶段的主战场：项目、里程碑、受阻记录、成果只交一次、项目结论。
- 答疑记录沿用 v2.1 的设计，切换时机见 6.6 和第 12 节。

### 6.10 人多之后（第四阶段）

实际人数和评审压力上来之后再做：同伴预审（带教指派，被指派的人对那一版成果临时只读）、让「可指导他人」的人分担预审、业务带教经亚古兽留观察、更完整的判断分流；出现第二位带教时解冻交接和对象级权限。

## 9. AI 接入

原则沿用 v2.1 第 15 节：工作台自己不调用 AI；AI 产出由亚古兽经机器人接口写入，全部是草稿，带教确认后才生效，或者只是附在旁边供参考；每条产出带执行方、接入方式、模型、时间的留痕。

- **第一阶段：本应用不调用 AI，也没有 AI 写入。** PRD 第 15 节的功能清单、`AGENTS.md`「AI 接入」一节和设置页暂时沿用现有内容（它们列的是规划中的功能和级别）；其中的级别标注按本文的阶段重标，随第一阶段做设置页时三处一起改。
- **第二阶段起按 6.6 的选择逐项接入**，每接一项就在设置页的功能清单里加一行（执行方亚古兽、接入方式 Hermes 派单、读什么、写到哪、谁确认），并标「仅支持亚古兽」及原因。
- **衡量 AI 有没有用**，看它是否实际减少了带教准备材料、核对信息、重复解释的工作，不看它生成了多少草稿。试用后带教的净工作量没有下降的，就关掉。
- 亚古兽不可用时，工作台其余功能照常；不自动换成别的执行方。

## 12. 路线

四个阶段是能力建设的顺序，每个阶段单独验收。加人和排期属于运营前置条件，按实际入职时间走，不机械地等某个阶段。

| 阶段 | 做什么 | 怎样算完 |
|---|---|---|
| 零 · 定稿 | 本文定稿；PRD 正文加 v3.0 对照表；术语表、页面清单同步；issue 按页面重切（等常浩确认 12.2 的页面顺序后执行） | 文档一致（2026-11-18 已完成）；issue 重切待做 |
| 一 · 真实闭环可用 | 项目与里程碑页面接接口；带教「待我判断」和管培生「下一步」首页；任务标准三个字段；反馈按条记、下次验证、口头手记（C08 改、C29、C40）；成员与带教关系页；飞书登录、最小权限、部署；在界面上建好两个人的真实项目和里程碑 | 见 12.1 的试运行门槛 |
| 二 · 验证并减少重复工作 | 加人与路径（6.5），导入两个人的路径与历史记录；从 6.6 的候选里按试运行证据选做；逐步接管旧工具的其他流程 | 第三人能在界面上 3 分钟内加入；选做的每一项都有试运行里的证据，并且试用后带教的净工作量没有增加 |
| 三 · 支持阶段性的人才判断 | 可托付活动、独立性判断与地图、评估点与材料导出（6.7、6.8） | 用它完成一次真实评估，材料能直接拿给上级 |
| 四 · 人多之后的带教效率 | 6.10 | 实际人数和积压出现时再开 |

### 12.1 第一阶段的试运行

- **做法：** 上线后用大约两个自然工作周，两名管培生各自用真实任务（不另造测试项目）走完至少一次「任务与标准 → 提交 → 反馈 → 再次验证」。带教在这两周里粗略记自己带教时间的构成。
- **切换边界（节点待常浩指定，见第 14 节 D、E）：** 从常浩指定的任务节点开始，任务要求、成果提交、正式评审、下一步行动以 TraineeOS 为准；旧工具只管还没迁过来的路径排期记录和答疑。两边不重复记。旧工具里这段时间的关键答疑，切换答疑时一并导入，不从证据链里丢掉。
- **要验证的假设：**

| 假设 | 最小证据 | 不成立时 |
|---|---|---|
| 口头反馈的流失值得解决 | 手记的反馈有没有被下一次实践引用 | 改进记录入口，不扩建模式库 |
| 反馈闭环能改善实践 | 下一份成果有没有针对之前的问题发生可确认的变化 | 回头查任务设计、反馈质量和验证机会 |
| 标准前置能减少反复解释 | 具体任务里管培生反复询问和返工的原因 | 不急着建标准卡体系 |
| 现有评审有明显的无效耗时 | 带教记下的时间构成 | 不优先做预审和复杂的判断分流 |
| 不同路线能共用一部分标准 | 两个人的任务和反馈里真正的交集 | 保留岗位差异，不强求统一的活动清单 |
| 新工具能替下旧工具的一段真实流程 | 这一段有没有结束重复录入并持续使用 | 调整切换边界，不继续加模块 |

  两个人的样本得不出统计结论，这些观察只用来判断哪些机制值得继续投入。

- **进入第二阶段的门槛：** 两个人都完成了真实闭环；关键反馈可以追溯；带教没有因为多出来的记录觉得负担难以接受；至少发现一处确实减少了重复工作或改善了反馈落实的机会。达不到，就不按规模化的设想继续加大模块，先查原因。

## 13. 风险

| 风险 | 说明 | 怎么对付 |
|---|---|---|
| 两个人登不上来 | 真实使用卡在登录和部署上，而部署缺服务器信息（#19 一直是「缺信息」） | 这是离真实使用最近的卡点，需要你提供环境信息（第 14 节 F） |
| 试运行变成两边重复记 | 新旧工具边界不清，带教和管培生都要记两遍 | 定稿时就把切换边界定死（第 14 节 D、E） |
| 多出来的记录成了负担 | 反馈分条、勾验证、手记都要带教动手 | 每一项都是可选的；带教时间构成是试运行必看的数；负担过重是不进第二阶段的理由之一 |
| 评价压制试错 | 管培生知道记录会进评估，就挑容易的做、不暴露困难 | 原则 7；评估材料由带教挑选并可由本人补充；不生成总分 |
| 候选杠杆被当成承诺 | 6.6 的每一项都没验证 | 每项都写了「看到什么才做」；做之前再定细节 |
| 这是第五版 PRD | 再改一次方向，离真人使用又远一步 | 第一阶段几乎全是已建成后端的页面接通，新增只有三处小改动 |
| 一位带教带 10 人以上 | 即使有分流也可能接不住 | 第四阶段靠同伴和「可指导他人」的人分担；再往上需要第二位带教，本文不解决 |

**本文没有解决的：** 多位带教之间的分工与交接；12 人以上的规模；扩展到全公司；业务带教进系统；手机端。
