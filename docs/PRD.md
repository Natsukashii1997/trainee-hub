# 上篇　骨架（实现依据）

## 1. 定位

产品名 **TraineeOS**（AI 管培生培养与实践工作台）。

**一句话：** 业务实践驱动的管培生成长与带教协同系统。以真实业务项目为实践载体，以结构化带教为成长机制，以能力证据为评价依据，以经验沉淀为组织复利，推动管培生从理解业务、解决问题，到独立承担业务与项目。

**设计命题：** 不从「管培生需要管理什么」出发，而从「管培生如何在真实业务中成长并创造价值」出发。

### 1.1 三条线

| 线 | 回答什么 | 主干 | 最终形成什么 |
|---|---|---|---|
| 业务项目推进 | 做成了什么 | 项目 → 里程碑 → 成果 → 评审 → 结论 | 可验收的业务成果 |
| 培养与能力成长 | 人获得了什么成长 | 培养路径 → 培养任务 → 带教反馈 → 能力证据 → 阶段复盘 | 有证据的成长判断 |
| 经验沉淀（横向） | 经验如何帮下一个人 | 已验证的成果 → 案例或资产 → 审核 → 复用 → 反馈改进 | 案例、方法、模板与 AI 资产 |

前两条线通过成果、评审和能力证据相互关联，不互相替代；第三条线从前两条线的产出里取材。

这一结构与飞书知识库《00｜知识库使用说明》里已定的个人能力闭环一致：角色与能力要求 → 阶段训练 → 真实业务实践 → 反馈与结果验证 → 实质修订 → 能力证据 → 阶段评价 → 下一步训练。「完成任务不等于形成能力」。

### 1.2 价值亮点

1. **业务推进与培养成长双线联动：** 一个真实项目同时是工作成果、培养实践和能力证据的来源，不形成两套各自独立的记录。
2. **带教判断驱动的持续改进：** 不只追踪「做完没有」，还追踪「为什么没做成、带教怎么介入、改进有没有发生、下一步谁推动」。
3. **真实项目经验跨期复用：** 已结束的项目沉淀为案例、方法和资产，降低下一批管培生的学习成本。

三者形成飞轮：真实实践提高培养质量 → 带教提高业务产出质量 → 优质成果沉淀为组织经验 → 组织经验支持下一轮实践。

### 1.3 分工与边界

| 系统 | 负责 |
|---|---|
| 工作台 | 保存可信的业务与培养状态：项目、里程碑、培养路径、成果、评审、能力证据、交接；是这些数据的唯一数据源 |
| 飞书文档与知识库 | 文档正文、原始成果、正式知识；访问权限由飞书判断 |
| 亚古兽（企业带教 Agent，飞书里的带教机器人） | 常浩的企业分身（Hermes profile `agumon`，独立的飞书应用，不混入个人分身）。在飞书里提醒、答疑、读管培生日志；经机器人接口（第 14 节）读工作上下文，写入答疑记录、答案草稿和反馈草稿，送达后写回回执。是可替换的外部通道，写入走同一套业务命令 |
| 牛马之家 | 常浩的个人工作台。现有的带教模块（路径排期、记录进度、带教答疑、项目推进）迁入本工作台，切换验收后只读归档；切换前两边不同时写（第 17 节） |

**不做：**

- 不做项目管理器（Jira、Trello 或另一个飞书项目）：不做细任务分解、甘特、工时、评论区；日常协作和沟通留在飞书。
- 不存文件，产出只交飞书文档链接或 GitHub 链接；不支持草稿。
- 不做手机版，只做电脑版（≥1280px）；人不在电脑前时的提醒交给机器人。
- 不写飞书日历；推算出的截止、换站、里程碑不进飞书日历。
- 不做聊天界面；不把规则功能包装成 AI；工作台自己不调用 AI（第 15 节）。和亚古兽的对话在飞书里进行；亚古兽写回的只是草稿，经带教审核才生效。
- 不把完成次数、AI 使用次数、活跃度、签到、聊天次数、上传数量、使用时长当成能力结论或培养成效。
- 不做账号密码登录。
- 积分、排行、兑换在价值被验证前不做。

### 1.4 一次事实输入，多处派生

同一业务对象只维护一份权威记录，不同页面只是不同视角。例如同一项培训：在培养路径里是一个培养节点，在日程里是一段时间，在首页是近期事项，在带教那里是一项指导责任。

用户只在一处录入一件事实；项目进度、待办、成长时间线、能力证据候选、案例候选都从同一事实派生，不要求在飞书、工作台、档案里各填一遍。「用户为维护系统额外付出了多少工作」是试点的验收观察项（第 17 节）。

### 1.5 规模

- 现阶段：两名管培生（2026-05-12 入职，按《管培生培养路径 V2.4》培养中，现由牛马之家记录）、一位带教（常浩）。骨架、迁移和试点都在这个规模上验证。
- 规划：约 12 人一期，多位带教。数据结构预留「团队 / 部门」维度，全公司版不在范围内。

### 1.6 TraineeOS 愿景与模块对照

《TraineeOS》产品文档（[原文](research/2026-11-14-traineeos/TraineeOS-产品文档.pdf)）是本产品的愿景蓝图：让培养有路径、工作有计划、实践有规范、问题有回应、成长有记录、经验有沉淀。它的七个模块与本文的对象和级别对照如下；文档里与本文冲突、经常浩确认维持原定的要求，见[决定记录](research/2026-11-14-traineeos/决定记录.md)第 2 节。

## 2. 角色、环境与授权

### 2.1 两个角色

| 角色 | 能做什么 |
|---|---|
| 管培生 | 看自己的路径、项目和任务，提交成果，处理自己的下一步行动，标记和解除受阻，填写项目结论，使用知识与工具 |
| 带教 | 指导自己带的管培生：确认立项、评审成果、写下一步行动、响应受阻、确认结项、提炼能力证据；也可贡献知识与工具 |

- **管理权限**是 `user` 表上的一个字段，不是第三种角色。有管理权限的带教（下文称**管理者**）还能维护成员与带教关系、能力项，以及期次、路径模板等基础数据。现在只有常浩有管理权限。骨架期不做权限配置界面。
- 没有「同事」角色。以后扩展到全公司时再加。

### 2.2 环境与登录

- **演示模式：** 由明确的环境开关打开；只在本机运行，只监听 127.0.0.1，只用合成数据。顶栏可以切换示例身份（示例管培生、示例带教）。服务监听在非本机地址时，拒绝启动演示模式。
- **非演示模式：** 第二轮完成飞书登录和服务端对象级授权（R1）之前，所有业务接口一律拒绝访问。
- 飞书登录、预置名单、「未开通」页属于第二轮（R1），在试点前完成。

### 2.3 统一授权入口

- 每条业务命令、每个查询都先经过同一个授权判断（操作人、动作、对象）。
- **骨架期只有两条规则：**
  1. 带教（含管理者）可执行全部命令、读取全部数据。
  2. 管培生只能执行第 4 节「发起方」列含管培生的命令；查询只返回本人的数据、本人参与的项目，以及全员可见的内容（站级进度、项目基本信息、知识与工具）。
- 第二轮在这个入口里加对象级规则和历史权限（R1），页面和命令不用改。

### 2.4 带教关系与评审负责人

- **带教关系**只有一种，也是带教信息的**唯一来源**：某位带教在某段时间（起止日）带某位管培生，范围是全程、某一站或某个项目。项目、站上都不另存带教字段。
- **界面叫法：** 范围为全程的叫**主带教**，范围为某一站的叫**业务带教**，范围为某个项目的叫**项目带教**；数据上仍是同一种带教关系。
- **默认带教：** 范围为全程的那位。每位管培生在培养期内应有一位默认带教，没有时由管理者兜底。
- **评审负责人**在**提交成果时**确定，并以快照形式存在成果版本上：
  - 里程碑成果：**项目主责管培生**在该项目范围的带教关系 → 没有时用主责管培生的默认带教 → 再没有时用管理者。多人项目统一以主责管培生为基准；页面上显示的「项目带教」也按这条推出。
  - 培养任务成果：该管培生在任务所属站的带教关系 → 没有时用其默认带教 → 再没有时用管理者。
  - 快照存下后，带教关系变化不会让它自动改变。改派怎么做属于第二轮（R3）。
- 项目的业务验收人（业务部门负责人）只记名字，不进系统、不开账号。

## 3. 核心业务模型

### 3.1 对象关系

```
培养关系   期次 ─ 个人路径 ─ 站 ─ 培养任务（属于某位管培生）
                   │          │
                带教关系（全程 / 某站 / 某项目；唯一来源）
                              │
业务关系   项目 ─ 里程碑 ─ 成果版本 ─ 评审 ─ 下一步行动
              │      │          │
              │   受阻记录      └─ 认定 ─→ 培养任务（一人一任务）
              └─ 项目结论（交付结论 + 业务验证）

证据与沉淀  评审 / 成果 → 能力证据 → 成长档案、阶段复盘
           已结束的项目 → 项目结论 → 业务案例 / AI 资产

底座       人员 · 带教关系 · 业务命令 · 事件日志（只追加） · 统一授权入口
```

### 3.2 三类工作对象的区别

| 对象 | 是什么 | 例子 | 谁定义 | 生命周期 |
|---|---|---|---|---|
| 项目 | 有业务目标和责任人的持续性工作 | 某业务流程优化 | 管培生或带教发起，带教确认立项 | 可跨站，不随站结束关闭 |
| 里程碑 | 项目里需要交出关键成果或作出决定的检查点 | 完成问题定义并通过评审 | 项目成员与带教 | 属于项目 |
| 培养任务 | 对某位管培生提出的学习或能力要求 | 掌握流程分析方法，并在一个项目中应用 | 路径模板（路径任务）或周期规则（周期任务） | 属于个人路径的某一站 |

三者可以关联，但不能合并成同一个对象；否则会出现培养任务结清但项目没完成、跨站项目找不到责任人、同一成果重复提交等问题。

### 3.3 成果只交一次，认定一人一任务

- 成果版本的主挂靠对象是**一个**里程碑或**一个**培养任务。
- 培养任务可以设为「在项目中完成」，并关联项目（和其中的里程碑）。这种任务不单独交成果；评审里程碑成果时，评审人对关联的培养任务逐条写**认定记录**。
- **认定记录** = 一个成果版本 + 一个培养任务实例。培养任务实例只属于一位管培生，所以多人项目里每人的认定各记一条，不会自动给全部参与者认定达标。
- 培养任务的「已通过」只能来自两处：对它自己成果的通过评审，或一条「已认定」的认定记录。
- 认定只能出现在结论为通过（优秀、达标）的评审里；同一个培养任务最多一条「已认定」记录。
- 骨架期认定由里程碑的评审负责人在同一次评审里完成。谁有权认定、两位评审人不同时怎么流转，属于第二轮（R3）。
- 提交、评审结论、里程碑通过、任务认定、项目结项分开记录，不合并成一个笼统的「完成」。

### 3.4 培养节点与里程碑（v2.1 术语）

- **培养节点**是培养任务在界面上的叫法：路径上的一个学习、培训、实践或评审单元，自带要求、计划起止、交付与评审。数据上就是 `task_instance`，加**类型**（学习 / 培训 / 实践 / 评审）、**线**（可空；同一条路径里并行的几条线，例如 V2.4 的业务线、技术线）和**计划起止**。
- **站**仍是轮岗岗位，是培养节点的分组；一个站下有多个培养节点。
- **里程碑**是项目里的检查点（原「关键节点」），只属于项目。
- 两者都能交成果、被评审，但不合并成同一个对象（3.2）。用词以[术语表](GLOSSARY.md)为准。

## 4. 业务命令与状态边界

### 4.1 原则

- 所有写入都通过下面的业务命令完成。每条命令在同一个事务里更新相关对象，并写一条事件日志（只追加，事件类型 = 命令名）。
- 不按表生成通用的增删改接口；业务界面上没有「任意改状态」的入口。
- 本机调试需要时，开发工具里有单独的「状态调试」，只在演示模式下可用，与业务接口分开，写入的事件标记为调试来源。
- 期次、路径模板、个人路径、培养任务实例、示例成员与带教关系、能力项、示例项目，骨架期由**初始化脚本**生成，可一条命令重置。初始化脚本只在演示模式下能运行，避免误写正式库。期次与模板的维护界面是 B 级原型，不写入。

### 4.4 状态边界（含义现在定死，第二轮只加规则、不改含义）

- 已提交、待评审 ≠ 已通过。「已通过」只能由一条评审记录（或认定记录）产生。
- 培养任务的「已通过」只能来自对它自己成果的通过评审，或一条认定记录（3.3）。
- 交付完成 ≠ 业务效果已验证（5.3）。
- 带教已响应受阻 ≠ 受阻已解除。
- 逾期是标记，不是状态；按时提交后等待评审的那段时间算不算逾期，属于 R2。

## 5. 项目与里程碑

### 5.1 项目

- **字段：** 名称；目标（为什么做、要解决什么问题）；主责管培生；参与管培生（可空）；业务验收人（只记名字）；验收条件；关联站（可多个，记录项目发生在哪些站）；项目文档（飞书链接）；状态；项目结论。**项目带教**不存在项目上，由带教关系（范围 = 项目）推出（2.4）。
- **跨站：** 项目不随站结束关闭。
- **不做：** 细任务分解、甘特、工时、评论区、项目内聊天。

### 5.2 里程碑

- **字段：** 项目；名称；里程碑目标；验收标准；原截止；当前截止；截止调整记录；状态；关联的培养任务（可空）；取消原因。
- **截止**由项目成员或带教填写，不按模板推算；调整只能通过 C05，留痕。
- **受阻记录**是挂在里程碑上的独立对象：原因；需要谁决定；当前处理责任人（默认是项目带教，见 2.4，可改）；响应（内容、人、时间，可多条）；解除（人、时间、说明）；状态。一个里程碑同时最多有一条未解除的受阻记录。
- 工作台不提供对话或求助流程（见第 18 节）。

### 5.3 项目结论

| 部分 | 字段 | 取值 |
|---|---|---|
| 交付结论 | 是否达成本项目的验收条件 | 达成 / 部分达成 / 未达成 |
| | 交付证据 | 链接到成果版本 |
| 业务验证 | 验证状态 | 未验证 / 已验证 / 不适用 |
| | 验证结论 | 达成 / 部分达成 / 未达成 / 无法判断（验证状态为「已验证」时填） |
| | 验证来源 | 业务负责人反馈、试点数据、成果文档等 |
| | 验证证据 | 链接、确认人（可以是只记名字的业务验收人）、确认时间 |
| 经验 | 可复用的经验、后续建议 | 文本；是业务案例的来源（第 12 节） |

一个「带教评为优秀、业务尚未采用」的项目，可以正常结项（交付结论 = 达成，验证状态 = 未验证），但不会被算作「已验证业务效果」。

### 5.4 项目模板（远期，C 级）

前身项目的 45 条标准项目模板以后可以改写成「项目模板」，复用路径模板的版本冻结机制。骨架期不做，项目和里程碑手动建。

## 6. 培养路径与培养任务

### 6.1 路径结构

- 三层：**阶段 → 模块（轮岗岗位）→ 任务模板**。阶段示例：入职、通识、轮岗、定岗。
- **路径模板**带版本号：已被期次绑定的版本只读，改动另存新版本。
- **期次**：名称、绑定的模板版本、开学日、结束日、状态（筹备 → 进行中 → 已结束）、预置名单。
- **个人路径**从模板派生，带起止日期、轮岗顺序和站；入职、通识、定岗也各算一站。站上不存带教，带教看带教关系（2.4）。
- 骨架期：上述数据都由初始化脚本生成（4.1）；「我的路径」「任务详情」读真实数据（A 级），期次、模板、轮岗排期的维护界面是 B 级原型。
- 现有培养文档（例如飞书《管培生培养路径 V2.4》）只作为可导入的模板内容，不决定产品的阶段数、周期或结构。
- **调整安排（C20，D 阶段做到 A 级）：** 带教在「我的路径」的排期视图里改某个培养节点的计划起止，后面同一条线上未通过的节点默认按工作日顺延；保存前预览受影响的节点和日期，每个被移动的节点都留截止调整记录。工作日按工作日日历算（R2 的工作日推算随此提前）。

### 6.2 培养任务

- **两种来源：** 路径任务（属于某站，从任务模板派生）和周期任务（由周期任务规则展开，B 级，骨架期不生成实例）。
- **字段：** 管培生；个人路径与站；来源模板或规则；**类型**（学习 / 培训 / 实践 / 评审）；**线**（可空）；**计划起止**；要求与产出形式（培训的时间、地点、会议链接暂写在这里）；**评审方式**（7.4）；开放日；截止、原截止、截止调整记录；状态；是否「在项目中完成」；关联项目与里程碑（可空）。界面上叫「培养节点」（3.4）。
- 「在项目中完成」的任务没有自己的提交入口，通过认定记录完成（3.3）。
- 周期任务的四种完成方式（提交链接、机器人收周报、机器人写成绩、本人声明 + 带教确认）的结构保留在数据模型里，界面为 B 级原型，规则见 R5。
- 尽量不让管培生每天重复填日报：成果提交和里程碑推进本身就是进度。

## 7. 成果、评审与下一步行动

### 7.1 成果版本

- 以飞书文档链接或 GitHub 链接提交，工作台不存文件，不支持草稿。
- **字段：** 主挂靠对象（一个里程碑或一个培养任务）；版本号；飞书链接；提交时间；提交人；渠道（网页 / 机器人）；说明或修改说明（再交时必填）；上一版评审（再交时）；**评审负责人（快照）**；**评审状态**（待评审 / 已评审）。链接字段存飞书或 GitHub 链接。
- 一经提交不可修改；改了就是再交一个新版本。
- 待评审的成果版本就是「评审义务」的事实来源，待办直接查它（第 11 节），不另存一份。

### 7.2 评审（两级反馈）

| | 日常轻反馈 | 里程碑深反馈 |
|---|---|---|
| 用在哪 | 培养任务 | 项目里程碑；带教也可对重要的培养任务选用 |
| 结论 | 三档：优秀 / 达标 / 需改进 | 三档：优秀 / 达标 / 需改进 |
| 文字 | 一两句短评，不设字数下限 | **关键问题**（这份成果说明了什么、还缺什么）；**带教判断**（为什么这样判断）；下一步行动单独记录（7.3） |
| 同时记录 | 下一步行动（需改进时至少一条「修改再交」） | 下一步行动；对关联培养任务的认定；可一键提炼能力证据（C16） |

- **字段：** 成果版本；评审人；三档；短评；关键问题；带教判断；反馈级别（轻 / 深）；评审时间。
- 默认不打分；需要打分的培养节点（如阶段评审、筛选、答辩）用带分数的评审方式（7.4）。细节可留在飞书文档批注里。
- 三栏都是短文本，只在里程碑出现；系统不要求带教填复杂表单。

### 7.3 下一步行动

- 独立的对象，不只是评审里的一段文字。
- **字段：** 来源评审；类型；内容；负责人；关联对象（可空，如后续里程碑）；状态（未完成 / 已完成 / 不再需要）；完成依据或原因；完成时间。
- **负责人默认值：** 「修改再交」= 该成果版本的提交人；「推进后续里程碑」= 评审人指定，默认项目主责管培生；「建议」可不指定。
- **三种类型：**

| 类型 | 什么时候用 | 骨架期怎么完成 | 进不进待办 |
|---|---|---|---|
| 修改再交 | 评审为需改进 | 修改再交（C07）时自动完成 | 进负责人的待办 |
| 推进后续里程碑 | 评审通过，但要进入下一轮业务验证 | 负责人处理（C09）；可关联后续里程碑 | 进负责人的待办 |
| 建议 | 带教给的非强制建议 | 可不处理，留在反馈里 | 不进 |

- 哪类行动什么时候提醒、超时怎么升级，属于第二轮（R4）。

### 7.4 评审方式（v2.1）

- 不同的评审点规则不一样（例如 V2.4：有的看结论；有的「无否决项且 ≥ 70 分才通过」；结论分「通过 / 限期复核 / 不通过」；普通阶段由带教直接确认完成）。所以评审规则不写死，由管理者在管理区自己添加**评审方式**（C22）。
- **一种评审方式只填五项：**
  1. 名称；
  2. 结论选项：每个选项注明算「通过」还是「未通过」；
  3. 是否打分；打分时的合格线（0–100）；
  4. 是否检查否决项（评审时勾选「有否决项」，有则结论只能选算未通过的选项）；
  5. 是否要求先交成果：要求时走 C06 → C08；不要求时由带教直接确认完成（C21）。
- **挂在哪：** 路径模板的阶段或任务模板上（培养节点继承）；里程碑默认用「三档点评」。
- **状态机不变：** 结论算通过 → 已通过；算未通过 → 需修改（4.4「已通过只能由评审产生」不变）。限期复核这类结论就是「需修改」加一条带修改截止的下一步行动。
- **评委：** 骨架期只在评审记录里记评委名字（文本），正式结论由评审负责人一人录入；多位评委各自打分再合并，试点后再定。
- **预置三种：** 「三档点评」（优秀、达标算通过，需改进算未通过，不打分，要求成果）；「评分 70 合格」（通过、限期复核、不通过，打分，合格线 70，查否决项，要求成果）；「带教确认完成」（完成算通过、未完成算未通过，不打分，不要求成果）。
- 已被使用的评审方式只能停用，不能改含义；要改另存一种新的，历史评审仍按原方式解释。

## 8. 能力证据、阶段复盘与成长档案

### 8.1 能力项

- 管理者维护的列表（C18），**起步采用季度答辩的「4+1 主线」**：
  1. 公司、行业与导师侧认知
  2. 用户与服务链路认知
  3. 实际项目推进与交付
  4. 营销线（是否作为通用能力项待定，见第 18 节）
  5. AI 使用与人机协同（贯穿前四条）
- 这是起始框架，不是公司已确认的能力标准；可增删，带版本。每条下面「可观察的能力表现」等 T1、T2 样本到了再写（R8）。

### 8.2 能力证据

- **字段：** 管培生；能力项；来源对象（成果版本 / 评审 / 带教观察）；证据内容；判断；确认人；确认时间；状态。
- **证据内容**按季度答辩的证据链写，按需填，不强制每栏都写：情境与事实 → 判断与依据 → 行动 → 结果与验证 → 反馈后的修改。
- **判断三级：** 尚未观察到充分证据 / 有指导下完成 / 可独立完成。
- 来源对象必须与这位管培生有关：本人提交的成果版本、对本人成果的评审，或本人参与的项目里的成果与评审（多人项目要分别为每人提炼）。
- 骨架期只有一条来源：带教在评审时或从成果「提炼为能力证据」（C16），直接为已确认。管培生自荐、带教确认或退回属于第二轮（R8），界面为 B 级原型。
- **不做：** AI 自动打分；从任务状态、完成次数、活跃度自动推出能力判断。

### 8.3 阶段复盘（B 级）

- 结构：管培生自评（季度答辩 5 问：原来怎么理解 → 哪些经历、事实或冲突改变了理解 → 现在怎么判断 → 为什么现在的判断更完整 → 这个判断能否指导下一步）；带教结论（三档、评语、下一阶段重点要验证的能力）。
- 复盘页自动汇总这个阶段的项目、通过的里程碑与成果、受过的关键反馈、各能力项的证据覆盖。
- 骨架期做成可交互原型，用示例数据展示；建表与命令在第二轮之后。
- 阶段评审、筛选、结业答辩这类**打分的评审点**不等复盘页：它们是类型为「评审」的培养节点，用带分数的评审方式（7.4），D 阶段就是 A 级。

### 8.4 成长档案

- 每位管培生一页。**A 级部分：** 当前阶段与站；项目经历（每个项目的目标、自己的角色、交付结论与验证状态）；通过的成果（本人提交且已通过的成果版本，加上对本人培养任务的认定记录）；能力证据（按能力项，每条能点回来源）；成长时间线（本人相关的事件，加上本人参与项目的项目事件）。
- **B 级部分：** 阶段复盘、交接卡。

## 9. 交接（B 级）

- 只在某位管培生（全程、某一站或某个项目）的带教换人时发生；前后是同一位带教时不交接。
- **对象结构：** 管培生；原带教；新带教；变更日；换前内容（进行中的项目及下一步、已知问题、培养建议、待转交事项）；每个进行中项目的选择（项目带教随之移交 / 保留原带教）；接手确认时间；遗留事项结清状态。
- 交互按三步做原型：换前交接、接手确认、换后结清。各步的触发时间和期限见 R6。
- 培养责任移交和项目带教移交分开处理；交接记录进成长档案的交接卡。

## 10. 信息架构与页面分级

### 10.1 四个工作域

原则：主导航按业务对象和用户目标组织；跨场景的入口用待办、日程、搜索；激励和展示是附属能力。

| 工作域 | 内容 | 级别 |
|---|---|---|
| **工作台** | 首页（按角色组合）；待办 | A |
| | 日程（我的本周、我带的人、轮岗排期） | B |
| **项目实践** | 项目列表、新建项目、项目详情、里程碑详情（成果、评审、下一步行动、受阻） | A |
| **培养成长** | 我的路径、培养节点详情（原任务详情）、成长档案（基础） | A |
| | 我的路径的排期视图与调整安排（C20）、带教答疑（C23–C26） | D 阶段做到 A |
| | 我带的人（带教看板）、阶段复盘、交接 | B |
| **知识与工具** | 知识资料、业务案例、AI 资产（Skill、Prompt、工作流、用例）、模板与 SOP（筛选视图）、贡献与审核 | B |
| | Q&A 合集（答疑记录里已收录的条目） | D 阶段做到 A |
| **管理区**（只对管理者显示） | 成员与带教关系、能力项 | A |
| | 评审方式（C22）、AI 与接入（含亚古兽的接口密钥） | D 阶段做到 A |
| | 期次与启动、路径模板、周期任务规则、工作日日历、轮岗排期、审核 | B |
| | 积分与激励、跨期分析、飞书知识库同步、通知中心、汇报与团队活动 | C |

- **级别含义：** **A** = 真实接口、真实持久化，用示例数据能跑完整流程；**B** = 可交互原型，入口、布局、数据展示和操作流程都确定，暂不建表、不接接口；**C** = 只确定在导航和架构里的位置，页面只放占位说明。
- **侧栏入口（v2.1，对齐 TraineeOS 七个模块）：** 四个工作域的分组不变，入口为：工作台（首页、待办、日程）；项目实践（项目）；培养成长（我的路径 / 我带的人、成长档案、带教答疑、路径总览）；知识与工具（知识资料、AI 资产、Q&A 合集）；管理区。TraineeOS 的七个模块各有一个入口。
- **顶栏：** 待办（A）、日程（B）、全局搜索（C）、通知（C）；演示模式下有身份切换。头像进入自己的成长档案。
- 不设单独的「团队」「激励」入口。成员列表放在管理区和项目成员里。
- **聚合优先，不加页面：** 项目详情一页内就能看到目标、当前里程碑、关联培养任务、最近反馈、下一步行动和阻碍。新结构不以页面数衡量进度。
- 每一页的对象、命令、来去见 [页面清单](页面清单.md)。

### 10.2 工作台首页（A 级，两种角色）

- **管培生：** 本阶段核心目标（当前站 + 主推项目的当前里程碑）→ **最重要的下一步**（未完成的下一步行动）→ 需要协调的事（受阻里程碑、待评审的成果）→ 最新带教反馈 → 进度（能力证据覆盖等基础计数）。
- **带教：** **待我判断**（我是评审负责人的待评审成果、待确认立项的项目、未响应的受阻）→ 我带的人（每人一行：在哪站、当前项目与里程碑、最近一次反馈、风险标记：受阻 / 连续需改进）。
- **管理者额外看到决策看板：** 骨架期放两条基础信号（某项目连续两次未通过同一里程碑；每位带教当前待评审的数量），只做标注清楚的计数；其余信号和指标口径见 R7。

### 10.3 核心场景

| 场景 | 发生什么 | 级别 |
|---|---|---|
| S1 管培生每天打开 | 先看到正在推进的目标、当前阻碍和下一步行动，而不只是待完成事项 | A |
| S2 带教在里程碑评审 | 看到项目目标、上次反馈、本次修改说明和验收标准，给出结论和下一步行动 | A |
| S3 阶段结束复盘 | 复盘页汇总项目、成果、反馈、证据覆盖；管培生自评，带教作综合判断 | B |
| S4 带教换人 | 换前交接传递进行中的项目和培养建议，换后结清遗留 | B |
| S5 下一批复用 | 新管培生进入同一岗位时，能看到上一批的项目案例、遇到的问题、用过的方法和工具 | B |
| S6 遇到问题请求带教判断 | 管培生带上下文发起求助，带教回复后形成下一步行动 | 待验证（第 18 节） |

## 11. 待办、日程与指标（骨架期）

- **待办 = 查询事实对象**，骨架期不自动生成、不提醒、不建待办表。待办页按负责人列出四类：
  1. 待我评审：评审负责人是我、状态为待评审的成果版本；
  2. 我的下一步行动：负责人是我、未完成的「修改再交」和「推进后续里程碑」类行动；
  3. 受阻待响应：我带的人的里程碑上未响应的受阻记录；
  4. 待确认立项：我带的人的草拟项目。
- 第二轮的自动待办、定时扫描、提醒和升级，都从这些事实对象和事件日志长出来（R5），同一份业务责任不存两次。
- **日程**（B 级）是从现有对象推出的视图，不建表：时段（阶段、站、任务开放期）、截止（里程碑、任务、修改截止）、时刻（换站、带教变更）。每条点开跳回所属对象。培训安排暂不建对象，培训的时间、地点、会议链接写在培养节点的要求里；日程创建、导师预约、冲突检测在试点后再定。
- **指标**骨架期只在决策看板和首页做标注清楚的基础计数（10.2）；指标口径、分母和达标线见 R7。

## 12. 知识与工具（B 级）

- **知识资料：** 资料本体留在飞书「管培生知识库」空间；工作台以资料卡片展示（标题、链接、摘要、标签、关联阶段 / 任务 / 项目）。骨架期卡片是原型数据；与飞书同步是 C 级，摘要在同步时截取文档开头一段，管理者可改写，不调用 AI。
- **四维标签：** 阶段 / 模块（引用路径结构）、主题、类型（SOP、模板、案例、培训材料、制度规范、工具指南）、岗位；后三维是固定列表，由管理者维护。
- **业务案例：** 来自已结束项目的结论（5.3）。字段：背景与问题、采用的方法、关键判断、验证结果、可复用做法、已知限制、来源项目、关联资产。由带教或管培生提交，管理者审核后上架；入库前去除个人评价和敏感信息。
- **AI 资产：** 四类：Skill、Prompt、工作流 / SOP、用例。字段含适用条件、典型使用案例、已验证效果、已知限制、维护状态，可关联项目和里程碑。Skill 文件沿用 SKILL.md 格式。
- **模板与 SOP：** 是资料类型「模板 / SOP」和资产类型「工作流 / SOP」的合并筛选视图，不另建对象。
- **Q&A 合集（D 阶段做到 A）：** 答疑记录里归档审核为「已收录」的条目（C25），每条显示「由亚古兽生成 · 某某审核」或「人工回答」（第 15 节）。
- **知识的可信度分三类：** 个人经验 / 待验证假设 / 正式规范，在资料卡片和案例上标明；只有正式规范能当作业务规则引用。
- **复用逻辑：** 按问题复用：实际业务问题 → 关联的知识、案例、模板与 AI 工具（附适用条件和历史案例）→ 实际使用与结果反馈 → 更新资产或沉淀新案例。用项目类型、阶段、问题标签加人工精选实现，不引入模型调用或复杂推荐算法。
- 「这一步可以用 · 推荐 AI 资产」出现在项目详情和任务详情（B 级区块）：取里程碑或任务挂的推荐资产，没有时取同类项目用过的，再没有时取使用人数最多的上架资产。
- 外部发现：Tidings（`https://tidings.natsukashii.cn`）只做跳转入口。

## 14. 带教机器人接口（亚古兽，D 阶段做最小版）

- 机器人负责飞书里的推送和对话，工作台负责可信状态（1.3）。机器人是可替换的外部通道，**不是核心闭环的单点依赖**：机器人不可用时，工作台里的路径、项目、评审照常可用，只是答疑记录不再进来。
- 机器人由**亚古兽**承担（2026-11-14 定）；亚古兽一侧的改造（改接本接口、取日志提问、挂回评论）在亚古兽与牛马之家各自的项目里做，不在本仓库。
- **D 阶段的最小版**只做：签发与吊销密钥；`GET /bot/v1/me/context`；写入答疑记录与答案草稿（C23）；写回送达（C26）。其余接口（提交成果、写入决定、周报、轻测）随试点证据再做。
- **最小接口（草案，随机器人接入时定稿）：**

| 接口 | 用途 | 关键保护 |
|---|---|---|
| `GET /bot/v1/me/context` | 某位成员当前的工作上下文（站、项目与里程碑、今天的日程） | 成员身份与字段权限 |
| `GET /bot/v1/actions` | 待处理事项与待推送提醒 | 按责任关系过滤 |
| `POST /bot/v1/submissions` | 提交成果链接（即 C06 / C07） | 幂等键、对象权限、版本校验 |
| `POST /bot/v1/decisions` | 写入授权范围内的评审或处理决定（即 C08 等命令） | 评审权限、状态冲突校验 |
| `POST /bot/v1/receipts` | 写回消息送达回执（即 C26） | 来源鉴权与去重 |
| `POST /bot/v1/qa` | 写入答疑记录与答案草稿（即 C23） | 幂等键（来源段落 ID）、产出留痕必填 |

- 另有写入（试点后再定）：周报、轻测成绩（含未答）。Q&A 合集不由机器人直接写入，来自答疑记录的归档审核（C25）。
- 机器人的写入同样走第 4 节的业务命令和统一授权入口，事件来源记为「机器人」。
- **授权：** 不只靠一把全权限密钥；按调用方、成员身份、对象权限和功能范围在服务端执行。密钥在管理区「AI 与接入」签发、吊销（15.2）。
- **可靠性：** 重复写入用请求幂等键；业务状态已经变化时返回明确冲突，不默默覆盖；执行结果不明时先查原请求结果，不盲目重放。
- **过渡切换：** 从多维表格「AI管培工作台」（`project_base`）和牛马之家一次性导入历史数据（项目、任务事项、路径与进度、答疑记录；映射见[迁移对照表](research/2026-11-14-traineeos/牛马之家迁移对照表.md)）→ 亚古兽逐个功能切到工作台接口 → 牛马之家带教模块与多维表格只读归档。全程不做双向同步。

## 15. AI 接入

依据全局规则 P-13（常浩 2026-11-07 定）：应用里凡是 AI 产出的东西，都要能在设置里看清谁做的、怎么接进来的、读了什么数据、写到了哪里；换一家时改设置就行，不改代码。本节与 `AGENTS.md`「AI 接入」一节内容一致，改一处要同步另一处。

用词：**执行方** = 真正产出内容的 AI（Claude、Codex、Hermes 等）；**接入方式**只有五种：本机 CLI、官方 API、网页桥、Hermes 派单、MCP 开放；**数据对象** = 应用只展示或采集、不是 AI 替应用产出的东西。

### 15.1 现状：工作台本身不调用 AI

- 已规划的功能里，**工作台自己不调用任何 AI**。名字带「AI」的功能都是人工内容或规则（见 15.3）。
- 会写进工作台的 AI 产出：亚古兽写入的**答疑答案草稿**和**反馈草稿**（D 阶段），都要带教审核后才生效。AI 调用发生在亚古兽里（执行方亚古兽，底层模型在亚古兽的 Hermes 配置里切换）；工作台只负责要求留痕、把留痕显示出来。
- 外部连进来的只有带教机器人接口（第 14 节），现在的接入方是亚古兽，接入方式记「Hermes 派单」。它是普通 HTTP 接口，不是 MCP；归在「对外开放」一块。
- 企业带教 Agent 就是亚古兽（1.3）：常浩的企业分身，用独立的 Hermes profile 和飞书应用，不混入个人数字分身（猛鬼兽）的运行体系。

### 15.2 设置页「AI 与接入」

- 位置：管理区，只有管理者能进；合并原规划的「机器人接口密钥」页。骨架期是 B 级原型（原型里已有）；密钥签发、吊销随机器人接口最小版在 D 阶段实现。
- 四块：
  1. **默认执行方**：写明「本应用当前不调用 AI」，不放切换按钮（不能假装能切）。列出以后接入时支持的执行方（Claude、Codex），状态都是「未启用」。第一次加 AI 功能时，这一块改为可切换，并照 15.4 执行。
  2. **功能清单**：每个带「AI」字样或用到 AI 产出的功能一行：功能名｜实际是什么｜执行方｜接入方式｜读哪些数据｜产出写到哪里｜谁能看到｜级别。内容见 15.3。
  3. **对外开放**：每个接入方一行：对谁开放、能读什么、能写什么、密钥状态（只显示「已配置 / 未配置」）、签发时间、最近调用时间、在哪关掉（「吊销」按钮，吊销后立即失效）。新签发的密钥只在签发当下显示一次。
  4. **数据对象**：AI 资产库、Tidings 入口，写明来源、是否由 AI 产出，不放进可切换项。
- 自检：不读代码，只看本页，能答出每个功能「谁做、怎么接、读什么、写到哪、现在能不能用」。

- 切换在下一次调用生效；已经在跑的任务按原执行方跑完。必须重启才生效的，在设置页写明。

### 15.5 留痕与对外开放的要求（随机器人接口起）

- 权限范围按第 14 节的读写清单逐项勾选；越权调用返回错误，并记进事件日志。

## 16. 技术方案与工程约束

- 自己开发网站：前端 React + Vite，后端 Node（TypeScript），数据库 PostgreSQL，用 Docker Compose 打包。开发期在本机运行（只监听 127.0.0.1）；上线部署到公司服务器（环境待定）。
- 只做电脑版（≥1280px）。页面时间统一按北京时间格式化显示；工作日推算（第二轮）只在服务端做。
- **四个统一入口**（第二轮补规则时不返工结构的保证）：
  1. **业务命令写入：** 按业务动作组织写入（第 4 节），同一事务里更新对象并写事件日志。
  2. **统一授权入口：** 每条命令、每个查询都先过授权判断（2.3）；第二轮在这里加对象级规则，并在查询层加数据过滤。
  3. **待办来自事实对象：** 评审义务来自待评审的成果版本，修改与推进义务来自未完成的下一步行动，受阻义务来自未响应的受阻记录（第 11 节）。
  4. **演示环境开关：** 宽松权限和身份切换只存在于这个开关之下（2.2）。
- **对 v1.1 技术决策的复核：**

| 决策 | 结论 | 说明 |
|---|---|---|
| 事件日志只追加 | 保留 | 作为审计与投影来源，不替代业务对象的当前状态 |
| 待办由事件驱动 | 改 | 骨架期待办是对事实对象的查询；第二轮再加事件即时触发和定时扫描，外发走 outbox（R5） |
| 工作日推算 | 第二轮 | 统一由服务端计算，记录日历版本和截止调整历史（R2） |
| 日程不单独建表 | 保留 | 查询视图可缓存，但不维护第二套业务事实 |
| 权限服务端执行 | 保留 | 骨架期在演示模式下只有两条规则；第二轮按角色、资源关系、时间范围细化（R1） |
| 机器人通过接口接入 | 保留 | 是可替换的外部通道，写入走同一套业务命令；现在的接入方是亚古兽 |
| 集成失败要显示 | v2.1 新增 | 同步或写回失败时显示同步状态和重试入口，不把本地操作显示成已同步到外部系统 |
| 模板版本冻结 | 保留 | 新旧版本必须可追溯；调整不覆盖历史 |
| 所有能力一开始完整实现 | 不采用 | 只建必要的扩展点，A/B/C 分级施工 |

# 下篇　精细规则池（第二轮设计和实现，现在不实现）

以下是草案，来源是 v2.0 草案的规则部分和 GPT 两轮审核。第 4 步逐条定稿：定稿的条目移进上篇，并补对应的测试。上篇已定的状态含义（4.4）不能在这里改。

### R1 权限与可见性

- 飞书登录（飞书内免登，只有公司飞书成员能进）；预置名单里的人首次登录直接成为该期次的管培生；带教由管理者开通；其他人登录看到「未开通」页，并生成待办给管理者。
- 非演示模式下，服务端按对象过滤，无权看的条目接口直接不返回。可见性草案：

| 内容 | 管培生本人 | 其他管培生 | 带教 | 管理者 |
|---|---|---|---|---|
| 站级进度（在哪站、换站） | 是 | 是 | 是 | 是 |
| 项目基本信息（名称、目标、状态、成员） | 是 | 是 | 是 | 是 |
| 项目的成果、评审、阻碍 | 项目成员可看 | 否 | 项目带教、成员的带教 | 是 |
| 培养任务状态、逾期 | 是 | 否 | 有带教关系的 | 是 |
| 成果、评审 | 是 | 否 | 有带教关系的 | 是 |
| 能力证据、阶段复盘 | 是 | 否 | 有带教关系的 | 是 |
| 交接记录 | 待定 | 否 | 交接双方 | 是 |
| 知识与工具（上架内容） | 是 | 是 | 是 | 是 |

- **历史权限（待定）：** 草案曾写「关系结束后保留只读；新带教从换前交接开始可只读此前全部记录」。GPT 复审指出这样可能权限过宽，建议：离任带教只看自己负责期间和负责项目的必要记录；接任带教获得交接摘要和相关成果，不默认开放全部敏感评价。第 4 步定。
- 管理权限拆成可配置的开关（出现第二位带教时）。
- **真实数据进来之前必须完成并验收本条。**

### R2 时间规则

- **工作日日历**由管理者维护法定假期与调休；所有期限按工作日推算，由服务端计算，并记录日历版本。
- **截止规则：** 任务模板写「锚点（站开始或站结束）+ 偏移 N 个工作日 + 时刻」和「建议用时（天）」；开放日 = 截止 − 建议用时；到开放日任务自动从未开始变为进行中。
- **三个时限分开**（GPT 复审 P0-03）：成果提交截止（衡量管培生是否按时提交）；评审时效（衡量带教是否按时评审，草案为提交后 2 个工作日，超时提醒评审人，再过 3 个工作日提醒管理者）；修改再交截止（草案为评审需改进后 3 个工作日，带教可改）。
- **逾期判定：** 首次成果按时提交后，等待评审期间不算管培生逾期；评审超时记在带教一侧；修改期限逾期单独记录，不覆盖原始提交的及时性。
- **调整截止：** 必须写原因并留痕；指标按原计划和调整后分开报告。

### R3 评审、认定与改派

- 谁有权认定培养任务达标：草案为该培养任务的评审负责人。里程碑评审人和任务评审人是同一人时一次完成；不是同一人时，成果自动转给任务评审人认定，不需要重新提交（GPT 复审 P0-01）。
- 多人共用成果时需写明各自贡献，不能自动认定所有参与者达标。
- 评审改派：带教关系变更时，已创建的待评审成果锁定当前负责人，变更时写显式的改派事件；已写的评审保留原评审人。
- 立项退回（带教不同意立项时退回草拟并写原因）。

### R4 下一步行动与受阻的自动化

- 各类下一步行动的提醒时间与超时升级。
- 受阻：带教在一定时限内响应（草案为 2 个工作日）；「已响应」关闭带教的响应待办，里程碑保持受阻直到解除；受阻超时升级给管理者。

### R5 待办规则

- **待办 = 触发 × 规则：** 一条触发按一条规则生成一条待办，由另一事件关闭或撤销。两种触发：事件即时触发；定时扫描时间条件（今明到期、逾期、交接期限、开站预告）。
- **一致性：** 业务状态更新、事件日志写入和待办生成在同一事务内完成；对外推送走事务型 outbox 异步投递。
- **唯一性：** 同一规则、同一对象、同一负责人只有一条未关闭的待办；同一扫描重复执行也只生成一次。
- **兜底：** 负责人为空时落到管理者；中止培养的人，其个人培养待办全部撤销。
- **规则草案：**

| 规则 | 触发 | 负责人 | 期限 | 关闭 | v1.1 对应 |
|---|---|---|---|---|---|
| T01 成果待评审 | 提交里程碑成果，或提交需评审的培养任务 | 评审负责人快照 | 2 个工作日；再过 3 个工作日提醒管理者 | 评审写入 | R02 |
| T02 按下一步行动修改 | 评审为需改进 | 管培生 | 修改截止 | 再次提交 | R03 |

| T04 逾期跟进 | 过截止仍未提交（需修改看修改截止） | 管培生补交；评审人一条跟进 | 立即 | 提交；截止调到未来后撤销 | R05 |

| T09 接手确认 | 换前交接写入 | 新带教 | 变更日 | 点「已接手」；逾期提醒管理者 | R06 改 |
| T10 换后结清 | 带教变更后仍有遗留 | 原带教 | 变更后 2 个工作日，超时转管理者 | 遗留都有结论或已转交 | R09 改 |

| 场景 | 应有结果 |
|---|---|

| 只用骨架范围 | 不依赖规则池以外的未实现功能 |

- 领域色只用于小面积：图标底、标签、日程事件块、进度端点；文字一律用同色系深字或墨色，保证对比度 ≥ 4.5:1。
- 状态只用语义色；强调色只用于当前项、链接和主操作。首页与日程的事件类型配色必须一致。

### A.3 字体

- 中文：苹方回落（`PingFang SC`、`Noto Sans SC`、`Hiragino Sans GB`、`Microsoft YaHei`）。
- 西文：Geist Sans；**数字：Manrope**（倒计时、指标、日期大字）；代码与安装指令：Geist Mono。不混用其他字体。
- 全部自托管（`web/src/styles/fonts.css`），`@font-face` 必须限定 latin 的 `unicode-range`，否则会挤坏中文全角标点（docs/LESSONS.md L-01）。
- 字号刻度：11 / 12 / 13 / 14.5 / 19 / 24 / 30px；页面标题 30px 细字重加强调色关键词；数字列 `tabular-nums`。

### A.4 组件与动效

- 圆角：面 22–24px，卡内块 12–16px，按钮 9–12px，胶囊全圆角。
- 通用组件：状态胶囊、领域标签、进度环（粗环、渐变端点、可标「按计划」刻度）、阶段条、轮岗站圆点链、竖向日程时间轴、迷你月历、周视图网格、甘特条、右侧抽屉、指标卡、空状态。
- 周视图：工作日列与周末列宽比约 1.25 : 0.6，事件标题换行显示、不截断；当前时间线用强调色；选中项柔和外发光。
- 多人视图和甘特格内的标签放不下时换行，不用省略号截断。
- 动效只用 0.2s 左右的颜色、阴影、位移过渡；不做入场动画；尊重「减少动态效果」设置。
- 只做电脑版（≥1280px）。
